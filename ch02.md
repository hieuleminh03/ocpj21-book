## Biến {#variables}

### Scope của biến {#variable-scopes}
Chúng ta có thể nghĩ về scope của một biến như khả năng hiển thị của nó, nơi nó có thể được nhìn thấy và truy cập trong code. Quản lý tốt scope của biến giúp chúng ta viết code sạch hơn, dễ bảo trì hơn và tránh các bug liên quan đến việc truy cập biến sai ngữ cảnh. 

Ở mức cao nhất, scope của một biến được quyết định bởi nơi nó được khai báo. Trong Java, có năm loại scope chính cần lưu ý:
- Block variable
- Local variable
- Method parameter
- Field (instance variable)
- Class variable (static field)

Đây là sơ đồ minh họa:
```
┌───────────────────────────────────────────────┐
│ Class                                         │
│ ┌───────────────────────────────────────────┐ │
│ │ Static/Class Variables                    │ │
│ │ ┌───────────────────────────────────────┐ │ │
│ │ │ Instance Variables                    │ │ │
│ │ │ ┌───────────────────────────────────┐ │ │ │
│ │ │ │ Method                            │ │ │ │
│ │ │ │ ┌───────────────────────────────┐ │ │ │ │
│ │ │ │ │ Method Parameters             │ │ │ │ │
│ │ │ │ │ Other Local Variables         │ │ │ │ │
│ │ │ │ │ ┌───────────────────────────┐ │ │ │ │ │
│ │ │ │ │ │ Block                     │ │ │ │ │ │
│ │ │ │ │ │ ┌───────────────────────┐ │ │ │ │ │ │
│ │ │ │ │ │ │ Block Variables       │ │ │ │ │ │ │
│ │ │ │ │ │ └───────────────────────┘ │ │ │ │ │ │
│ │ │ │ │ └───────────────────────────┘ │ │ │ │ │
│ │ │ │ └───────────────────────────────┘ │ │ │ │
│ │ │ └───────────────────────────────────┘ │ │ │
│ │ └───────────────────────────────────────┘ │ │
│ └───────────────────────────────────────────┘ │
└───────────────────────────────────────────────┘
```

Local variable được khai báo bên trong method nơi chúng được định nghĩa, còn block variable chỉ có thể truy cập được trong block nơi chúng được định nghĩa. Chúng đi vào scope tại điểm khai báo và ra khỏi scope ở cuối method/block bao quanh:

```java
void myMethod() {
    int x = 1;
    if (x > 0) { 
        int y = 2;
        System.out.println(x + y); // Cả x và y đều nằm trong scope ở đây
    }
    System.out.println(x); // Chỉ x nằm trong scope ở đây
    System.out.println(y); // Compile error! y nằm ngoài scope
}
```

Như bạn thấy, `y` chỉ hiển thị bên trong block `if` nơi nó được khai báo. Cố truy cập nó bên ngoài block đó sẽ dẫn đến compile error.

Nếu bạn khai báo một biến bên trong vòng lặp, bạn không thể truy cập nó bên ngoài vòng lặp. Kể cả khi tất cả đều nằm trong cùng một method, scope vẫn kết thúc ở dấu `}` đóng của vòng lặp. Ví dụ:

```java
void myLoopingMethod() {
    for (int i = 0; i < 10; i++) { 
        System.out.println(i);
    }
    System.out.println(i); // Compile error! i nằm ngoài scope
}
```

Tương tự, các biến được khai báo trong phần initializer của for-loop, như `int i` ở trên, chỉ có scope trong thân vòng lặp, không phải toàn bộ method bao quanh.

Khái niệm này cũng áp dụng cho các block khác như `if/else`. Một biến được khai báo bên trong `if` không hiển thị trong `else` tương ứng:

```java
void myIfElseMethod(int x) {
    if (x > 0) {
        int y = 1; 
    } else {
        System.out.println(y); // Compile error! y không nằm trong scope
    }
}
``` 

Tiếp theo là method parameter. Chúng cũng được xem là local variable, nhưng có scope bao trùm toàn bộ thân method. Chúng đi vào scope khi method được gọi và ra khỏi scope khi method kết thúc.

Parameter là cục bộ trong method, không method nào khác có thể thấy chúng, kể cả khi method đang thực thi:

```java
void methodA(int x) {
    methodB();
    System.out.println(x); // x nằm trong scope
}

void methodB() {
    System.out.println(x); // Compile error! x không nằm trong scope
}
```

Field, hay instance variable, là các biến được khai báo ở cấp class, bên ngoài mọi method. Chúng đi vào scope khi object được khởi tạo và vẫn trong scope chừng nào object còn trong bộ nhớ:  

```java
class MyClass {
    private int x; // Instance variable (field)

    void myMethod() {
        System.out.println(x); // x nằm trong scope ở đây
    }
}
```

Vì instance variable thuộc về một object instance, chúng không thể được truy cập từ static context, nhưng có thể được truy cập bởi bất kỳ instance method nào trong class.

Một hiểu lầm phổ biến là instance variable bị garbage collection ngay khi method sử dụng chúng kết thúc, nhưng thực tế không phải vậy. Field của một object vẫn ở trong bộ nhớ cho đến khi chính object đó đủ điều kiện bị garbage collection, có thể rất lâu sau khi một lời gọi method cụ thể kết thúc.

Ngoài ra, hãy nhớ rằng nếu biến hoặc class của nó được khai báo `private`, thì chỉ class khai báo mới truy cập được. Nhưng nếu chúng có `public`, `protected` hoặc default (package) access, các class khác cũng có thể truy cập chúng.

Cuối cùng, class variable, hay static field, là các biến `static` được khai báo ở cấp class. Chúng đi vào scope khi class được load và ở trong scope cho đến khi chương trình kết thúc. Chỉ có một bản sao duy nhất của class variable được chia sẻ giữa tất cả instance của class.

Class variable thuộc về chính class, không thuộc về một object instance cụ thể. Và không giống instance variable, class variable có thể được truy cập từ cả static context lẫn instance context:

```java
class MyClass {
    private static int x; // Class variable

    void myMethod() {
        System.out.println(x); // x nằm trong scope 
    }

    static void myStaticMethod() {
        System.out.println(x); // x cũng nằm trong scope
    }
}
```

Class variable có thể được truy cập từ bất kỳ đâu trong chương trình, kể cả khi không tạo instance của class. Nhưng chúng vẫn chịu sự kiểm soát của access modifier như `private` và `public`.

Một trường hợp thú vị là khi bạn có hai biến cùng tên nhưng khác scope:

```java
class MyClass {
    private int x; // Instance variable 
    
    void myMethod() {
        int x = 1; // Local variable
        System.out.println(x); // In ra 1 (local variable)
        System.out.println(this.x); // In ra 0 (instance variable) 
    }
}
```

Trong tình huống này, local variable che khuất (shadow) instance variable trong scope của nó. Để truy cập instance variable, chúng ta phải dùng keyword `this`. Chúng ta sẽ nói về điều này ở phần sau của chương, nhưng như bạn thấy, việc giới hạn scope đúng cách không phải để cải thiện hiệu năng, mà là để tổ chức code và kiểm soát việc truy cập biến.


### Khai báo biến {#variable-declarations}
Khi mới học Java, bạn dễ nghĩ rằng field và local variable gần như giống hệt nhau. Suy cho cùng, cả hai đều chỉ là biến, đúng không? Bạn khai báo chúng, gán cho chúng một type và một tên, có thể gán giá trị, rồi dùng chúng trong code. Có gì to tát đâu?

Hóa ra, có một số khác biệt khá quan trọng giữa field và local variable trong Java. 

Field được khai báo trực tiếp bên trong class, nhưng bên ngoài mọi method hoặc constructor. Chúng là một phần state của class, và mỗi instance của class có bản sao riêng của các field này.

Ngược lại, local variable được khai báo bên trong một method hoặc constructor. Chúng chỉ tồn tại trong suốt thời gian method hoặc constructor đó được gọi, và không thể truy cập từ bên ngoài. Khi method thực thi xong, local variable biến mất.

Đây là một ví dụ:

```java
public class MyClass {
    private int myField; // Đây là một field

    public void myMethod() {
        int myLocalVar = 25; // Đây là một local variable
        // Làm gì đó với myLocalVar...
    } // myLocalVar không còn tồn tại sau điểm này
}
```

Bây giờ, bạn có thể nghĩ: "Được rồi, field nằm trong class, còn local variable nằm trong method. Nhưng ngoài ra tôi có thể dùng chúng thay thế cho nhau được không?" Không hẳn. Có một số khác biệt then chốt trong cách chúng hoạt động.

Thứ nhất, field tự động nhận default value nếu bạn không khởi tạo chúng một cách tường minh. Với numeric type (như `int`, `long`, `float`, `double`), mặc định là `0`. Với `boolean`, là `false`. Với reference type (như `String` hay bất kỳ object nào), là `null`.

Ngược lại, local variable không nhận bất kỳ default value nào. Nếu bạn cố dùng một local variable trước khi khởi tạo nó, bạn sẽ nhận compile error. Nói cách khác, Java compiler muốn bạn thể hiện rõ ràng ý định của mình với local variable:

```java
public void myMethod() {
    int uninitialized;
    System.out.println(uninitialized); // Compile error!
}
```

Vậy Java yêu cầu bạn khởi tạo local variable trước khi dùng. Nhưng chính xác thì khi nào bạn cần khởi tạo? Quy tắc rất đơn giản: việc khởi tạo phải diễn ra trên mọi nhánh thực thi có thể trước lần sử dụng đầu tiên của biến:

```java
int myVar;
if (someCondition) {
    myVar = 1;
} else {
    myVar = 2;
}
System.out.println(myVar); // Đoạn này ổn

int myOtherVar;
if (someCondition) {
    myOtherVar = 1;
}
System.out.println(myOtherVar); // Compile error! Không được khởi tạo trên nhánh else.
```

Trong ví dụ đầu tiên, `myVar` chắc chắn được khởi tạo trước khi sử dụng, bất kể `if/else` đi theo nhánh nào. Nhưng trong ví dụ thứ hai, nếu `someCondition` là `false`, `myOtherVar` sẽ không được khởi tạo trước lần sử dụng đầu tiên, do đó có compile error.

Dù là field hay local variable, Java đều cho phép bạn khai báo nhiều biến cùng type trên một dòng, phân tách bằng dấu phẩy:

```java
int a, b, c;
```

Nhưng điều này không có nghĩa là các biến chia sẻ cùng giá trị. Chúng là những biến hoàn toàn độc lập, chỉ tình cờ được khai báo cùng nhau. Bạn có thể gán cho chúng những giá trị khác nhau:

```java
int a = 1, b = 2, c = 3;
```

Thực tế, bạn không cần gán giá trị cho tất cả ngay lập tức. Hoàn toàn ổn khi làm thế này:

```java
int a, b, c;
a = 1;
b = 2;
// c vẫn chưa được khởi tạo ở thời điểm này
```

Chỉ cần nhớ rằng bạn không thể dùng `c` cho đến khi khởi tạo nó với một giá trị, nếu không bạn sẽ nhận compile error.

Bây giờ, khi bạn muốn khai báo nhiều biến khác type thì sao? Bạn không thể làm điều đó trên một dòng như với các biến cùng type. Bạn phải khai báo từng biến riêng:

```java
int a = 1;
String b = "hello";
// Đoạn này sẽ không compile: int a = 1, String b = "hello";
```

Một khác biệt nữa giữa local variable và field là cách dùng `final`. Đánh dấu một field là `final` nghĩa là nó phải được khởi tạo khi object được khởi tạo, và sau đó không bao giờ có thể thay đổi nữa. Với local variable, `final` chỉ có nghĩa là bạn chỉ được gán giá trị cho nó một lần. Nhưng việc gán đó không nhất thiết phải diễn ra lúc khai báo biến:

```java
public class MyClass {
    private final int myFinalField = 42; // Phải khởi tạo ở đây

    public void myMethod(int arg) {
        final int myFinalVar; // Có thể khởi tạo sau cũng được
        if (arg > 0) {
            myFinalVar = arg;
        } else {
            myFinalVar = 0;
        }
        // Không thể gán lại cho myFinalVar sau điểm này
    }
}
```

Việc gán phải diễn ra trước lần sử dụng đầu tiên của biến, và chỉ được xảy ra một lần. Điều này thường hữu ích khi bạn muốn gán giá trị có điều kiện, như trong ví dụ trên. Hoặc khi bạn muốn gán giá trị trong vòng lặp nhưng đảm bảo nó không thay đổi sau vòng lặp:

```java
final int myFinalVar;
for (int i = 0; i < 10; i++) {
    // Một vài tính toán...
    myFinalVar = result;
    // Không thể gán lại cho myFinalVar sau điểm này
}
```

Tuy nhiên, khi làm việc với reference và object, nếu bạn khai báo một local variable là `final`, bạn vẫn có thể thay đổi thuộc tính của object mà nó reference. `final` chỉ ngăn bạn gán giá trị mới cho chính biến đó. Nếu biến là reference tới một object, bạn vẫn có thể thay đổi object đó:

```java
final StringBuilder sb = new StringBuilder();
sb.append("Hello"); // Đoạn này ổn
sb = new StringBuilder(); // Đoạn này sẽ không compile
```

Trong ví dụ này, chúng ta có thể gọi các method trên `sb` để thay đổi object `StringBuilder`, nhưng không thể gán một instance `StringBuilder` mới cho `sb`.

### Type inference của biến {#variable-type-inference}
Java 10 và các phiên bản sau giới thiệu một tính năng mới, `var`. Nó cho phép bạn khai báo local variable mà không cần chỉ định type:

```java
var myVar = 42;
```

Đây được gọi là local variable type inference. Compiler nhìn vào giá trị bạn gán cho biến và tự xác định type phù hợp cho bạn. Trong trường hợp này, nó suy luận rằng `myVar` phải là `int`.

Theo cách truyền thống, việc khai báo local variable thường dẫn đến code dài dòng và lặp lại. Ví dụ:
```java
HashMap<Integer, String> map = new HashMap<>();
List<String> list = new ArrayList<>();
AtomicInteger counter = new AtomicInteger(0);
```

Trong mỗi trường hợp, type được nhắc đến hai lần, một lần ở vế trái và một lần ở vế phải. Đây là lúc keyword `var` phát huy tác dụng.

Bằng cách dùng `var`, đoạn code trên có thể được viết lại thành:
```java
var map = new HashMap<Integer, String>();
var list = new ArrayList<String>();
var counter = new AtomicInteger(0);
```

Type của `map`, `list` và `counter` được compiler suy luận dựa trên các initializer expression. Điều này làm code ngắn gọn và dễ đọc hơn mà vẫn đảm bảo type safety.

Cần lưu ý rằng `var` hoạt động như một keyword trong ngữ cảnh sử dụng, dù về mặt kỹ thuật nó là reserved type name cho local variable type inference. Điều này có nghĩa là code dùng `var` làm tên biến, method hay package sẽ không bị ảnh hưởng.

`var` bị giới hạn cho local variable trong method, constructor hoặc initializer block. Nó không thể dùng để khai báo instance variable (field) hay class (static) variable. Hạn chế này đảm bảo rằng type của class variable và instance variable luôn rõ ràng từ API của class, không chỉ từ implementation của nó:
```java
public class MyClass {
   var myVar = "Hello"; // Đoạn này sẽ không compile
}
```

Tương tự instance variable và class variable, `var` không thể dùng để khai báo method parameter. Method signature là một phần của public API của class và cần nêu rõ type của parameter để rõ ràng và đảm bảo tính ổn định của contract:
```java
public void myMethod(var param) { // Đoạn này sẽ không compile
   // ...
}
```

Ngoài ra, `var` có thể dùng trong các tình huống khác. Ví dụ trong index của vòng lặp `for`:
```java
var numbers = Arrays.asList(1, 2, 3, 4, 5);
for (var num : numbers) {
    System.out.println(num);
}

// Hoặc

for (var i = 1; i <= 10; i++) {
    System.out.println(i);
}
```

Trong câu lệnh `try-with-resources`:
```java
try (var stream = Files.lines(Path.of("file.txt"))) {
    stream.forEach(System.out::println);
}
```

Hoặc cho parameter của biểu thức lambda được định type ngầm định:
```java
Function<Integer, String> toString = (var i) -> String.valueOf(i);
```

Hãy nhớ rằng trong một biểu thức lambda, hoặc tất cả parameter phải được khai báo với `var`, hoặc không parameter nào cả. Không được trộn `var` với manifest type hay inferred type.

Tuy nhiên, hãy cẩn thận với `var`, nó không phải lúc nào cũng là lựa chọn tốt nhất. Đôi khi khai báo type một cách tường minh có thể làm code dễ đọc và dễ bảo trì hơn. Bạn chỉ có thể dùng `var` khi khởi tạo biến ngay tại chỗ khai báo:

```java
var myVar; // Đoạn này sẽ không compile
var myOtherVar = someMethodThatReturnsAnObject(); // Ổn, miễn là return type của method rõ ràng
```

Tương tự, `var` không thể dùng khi khởi tạo một biến với giá trị `null` mà không chỉ định type, vì compiler không thể suy luận type của biến:
```java
// Đoạn này sẽ không compile vì không thể suy luận được type
var myVar = null;
```

Tuy nhiên, sau khi `var` đã được dùng để khai báo một biến với type cụ thể, biến đó có thể được gán lại giá trị `null`:
```java
var myString = "Hello, World!"; // Được suy luận là String
myString = null; // Điều này được phép
```

Cuối cùng, khi dùng `var` với array initializer, cần khởi tạo một cách tường minh. Bạn không thể dùng cú pháp viết tắt vì type không thể được suy luận:
 ```java
var numbers = new int[] {1, 2, 3}; // Đoạn này hoạt động
// var numbers = {1, 2, 3}; // Đoạn này sẽ không compile
 ```


## Inheritance {#inheritance}

### Introducing Inheritance {#introducing-inheritance}
Inheritance là một trong những khái niệm cốt lõi của lập trình hướng đối tượng. Nó cho phép bạn định nghĩa một class mới dựa trên một class đã tồn tại. Class mới kế thừa các attribute và method của class đã có, giúp bạn tái sử dụng code và xây dựng các quan hệ phân cấp giữa những class của mình.

Bạn có còn nhớ class `Cookie` ở đầu chương trước không?

```java
public class Cookie {
    // Thuộc tính
    String flavor; 
    int size;
                     
    // Hành vi (Method)
    public void eat() {
        System.out.println("That was yummy!");
    }
}
```

Bạn sẽ định nghĩa class cho chocolate chip cookie như thế nào?

Chocolate chip cookie có flavor, có số lượng chip và có thể được ăn như cookie thông thường. Nhưng chúng cũng có thêm những thuộc tính khác, chẳng hạn số chip trên mỗi cookie. Vậy class `ChocolateChipCookie` ngây thơ ban đầu của chúng ta có thể trông như sau:

```java
public class ChocolateChipCookie {

  String flavor;  
  int size;

  void eat() {
    System.out.println("That was yummy!"); 
  }

  int chips;

}
```

Chúng ta đã lặp lại các attribute và method của cookie! Đây không phải là một thiết kế tốt.

Đây chính là lúc khái niệm inheritance bước vào OOP.

Mọi loại cookie đều chia sẻ những thuộc tính chung như có flavor và ăn được. Chúng ta có thể biểu diễn điều này bằng một class cha `Cookie` chứa `flavor`, `size` và một method `eat()`.

Các child class, như `ChocolateChipCookie`, sau đó có thể kế thừa những thành phần cookie chung này từ class cha `Cookie`. Bằng cách này, chúng ta có thể tạo ra nhiều loại cookie cụ thể cùng kế thừa những thuộc tính chung. Các child class vẫn có thể định nghĩa những attribute riêng, chẳng hạn số chocolate chip, nhưng tái sử dụng code đã kế thừa từ class cha.

Trong Java, bạn dùng keyword `extends` để tạo một subclass kế thừa từ một superclass. Đây là cách class `ChocolateChipCookie` có thể được định nghĩa bằng inheritance:  

```java
public class ChocolateChipCookie extends Cookie {

  int chips;

  public void addChips(int chipsPerCookie) {
    this.chips += chipsPerCookie;
  }

}  
```

Ở đây, `ChocolateChipCookie` là một subclass của `Cookie`. Nó kế thừa các field `flavor`, `size` và method `eat()`. Subclass có thể khai báo các method riêng của nó, giống như `ChocolateChipCookie` khai báo method `addChips()`.

Tuy nhiên, một subclass không thể truy cập trực tiếp các member `private` của superclass. Nó có thể truy cập trực tiếp các member `public` và `protected`. Nó cũng có thể truy cập các member package-private (default) khi subclass nằm trong cùng package. Để chạm tới các field `private`, superclass phải cung cấp accessor `public` hoặc `protected`.

Một điều quan trọng cần biết là trong Java, một class chỉ có thể extends từ một class duy nhất, do quyết định thiết kế nhằm tránh sự phức tạp và mơ hồ gắn với multiple inheritance. Nói cách khác, multiple inheritance — khi một class có thể extends nhiều hơn một class — có thể dẫn tới:

1. **Diamond Problem:** Đây là một vấn đề phức tạp nổi tiếng, xảy ra khi một class kế thừa từ hai class có chung một base class. Tình huống này tạo ra sự mơ hồ trong hệ thống phân cấp inheritance khi hai class cha có các method cùng signature, vì hệ thống có thể không xác định được nên dùng phiên bản nào của method được kế thừa.

2. **Increased Complexity:** Việc cho phép multiple inheritance có thể khiến việc thiết kế và bảo trì chương trình phức tạp hơn. Việc hiểu luồng chạy của method và variable trở nên khó hơn, đặc biệt trong những codebase lớn.

Một số class modifier quan trọng liên quan tới inheritance là `final`, `abstract` và `sealed`.

Final class không thể bị subclass. Nếu bạn cố extends một class `final`, bạn sẽ nhận compile error. Lấy ví dụ cookie, nếu class `Cookie` được khai báo là `final`:

```java
public final class Cookie {
    // ...
}
```

Khai báo của class `ChocolateChip` sẽ tạo ra compilation error.

Đánh dấu một class là `final` đảm bảo rằng implementation của nó không thể bị thay đổi thông qua subclassing. Tuy nhiên, trái với một hiểu lầm phổ biến, class `final` không chạy hiệu quả hơn tại runtime chỉ vì chúng là `final`. Modifier `final` liên quan tới inheritance, không phải performance.

Abstract class không thể được khởi tạo, chỉ có thể được subclass. Bản thân chúng là không hoàn chỉnh và cần được extends để sử dụng. Abstract class thường chứa các abstract method không có implementation trong abstract class và phải được hiện thực bởi các concrete subclass. Cố tạo một instance của abstract class bằng `new` sẽ dẫn tới compile error.

Sealed class cung cấp một giải pháp trung gian giữa final class và non-final class. Sealed class có thể được extends, nhưng chỉ bởi những class được cho phép rõ ràng trong khai báo của sealed class. Điều này cho bạn quyền kiểm soát inheritance ở mức chi tiết. Các subclass của sealed class phải được khai báo là sealed, non-sealed hoặc final. Sealed class hạn chế inheritance nhưng không cấm hoàn toàn như final class.

Hãy xem xét chi tiết hơn về abstract class và sealed class.

### Abstract Classes {#abstract-classes}
Abstract class là class không thể được khởi tạo, nghĩa là bạn không thể tạo instance mới của abstract class. Nó đóng vai trò base cho các subclass:
```java
abstract class Cookie {
    abstract void flavor(); 
}
```

Bạn phải dùng keyword `abstract` để khai báo một class hoặc một method là abstract. Một abstract class có thể có hoặc không có abstract method.

Abstract method được khai báo không có implementation (không có dấu ngoặc nhọn, và kết thúc bằng dấu chấm phẩy):
```java
abstract void flavor();
```

Abstract method tương tự method thông thường ở chỗ bạn khai báo chúng có hoặc không có parameter, có giá trị trả về hoặc `void`, và dùng bất kỳ access modifier nào như `public`, `protected` hay default. Khác biệt duy nhất là abstract method không có implementation, chúng không thể có thân method, do đó chúng kết thúc bằng dấu chấm phẩy (`;`) chứ không phải cặp ngoặc (`{}`).

Để dùng một abstract class, bạn phải kế thừa nó từ một class khác bằng keyword `extends`. Hãy xem một ví dụ:
```java
class OatmealRaisinCookie extends Cookie {
    void flavor() {
        System.out.println("Oatmeal and raisin flavor");
    }
}
```

Khi kế thừa từ một abstract class, subclass thường cung cấp implementation cho tất cả abstract method trong class cha. Nếu không, subclass cũng phải được khai báo là abstract:
```java
abstract class Cookie {
    abstract void flavor();
    
    public void bake() {
        System.out.println("Cookie is baking");
    }
}

abstract class OatmealRaisinCookie extends Cookie {
    // Abstract method khiến class trở thành abstract
    // (Nếu không thì sẽ không compile)
    abstract void flavor();
    
    // Kể cả khi nó định nghĩa (các) concrete method
    public void addRaisins() {
        System.out.println("Adding raisins");
    }
}
```

Tại sao?

Bởi vì một abstract class là (hoặc được dự định là) không hoàn chỉnh. Tạo một object từ một class không hoàn chỉnh sẽ là sai.  Một abstract class cần được extends để sử dụng, giống như một template vậy.

Abstract class hữu ích để chia sẻ code giữa các class có quan hệ gần gũi. Quan trọng nhất, abstract class có thể định nghĩa những method mà các subclass bắt buộc phải hiện thực, thiết lập một contract hoặc một protocol mà subclass phải tuân theo.

Sẽ rất hữu ích khi coi concrete class là sự chuyên biệt hóa của abstract class. Cũng giống như một chiếc xe compact là sự chuyên biệt hóa của khái niệm chung về xe hơi, abstract class là khái niệm chung còn concrete class là một implementation cụ thể của khái niệm đó.

Concrete class phải hiện thực tất cả abstract method nhưng cũng có thể định nghĩa thêm các method mới của riêng mình. Không phải mọi method trong concrete class đều phải là abstract, chỉ những method được khai báo abstract trong abstract class cha mới cần. Đây là một ví dụ minh họa:

```java
abstract class Cookie {
    abstract void flavor();
    
    public void bake() {
        System.out.println("Cookie is baking");
    }
}

class ChocolateCookie extends Cookie {
    // Triển khai abstract method
    void flavor() {
        System.out.println("Chocolate flavor");
    }
    
    // Định nghĩa method mới của riêng nó
    public void addChocolateChips() {
        System.out.println("Adding chocolate chips");
    }
}

class OatmealRaisinCookie extends Cookie {
    // Triển khai abstract method
    void flavor() {
        System.out.println("Oatmeal and raisin flavor");
    }
    
    // Định nghĩa method mới của riêng nó
    public void addRaisins() {
        System.out.println("Adding raisins");
    }
}
```

Trong ví dụ này, `Cookie` là một abstract class với một abstract method `flavor()` và một concrete method `bake()`.

Các class `ChocolateCookie` và `OatmealRaisinCookie` là những concrete class extends abstract class `Cookie`. Cả hai đều hiện thực abstract method `flavor()` mà chúng kế thừa từ `Cookie`. Một lần nữa, đây là bắt buộc, nếu không chúng cũng sẽ phải được khai báo là abstract.

Nhưng `ChocolateCookie` và `OatmealRaisinCookie` cũng định nghĩa các method mới của riêng chúng, lần lượt là `addChocolateChips()` và `addRaisins()`. Những method này đặc thù cho từng loại cookie và không liên quan tới abstract class.

Khi bạn tạo instance của `ChocolateCookie` và `OatmealRaisinCookie`, bạn có thể gọi tất cả method của chúng:

```java
ChocolateCookie chocolateCookie = new ChocolateCookie();
chocolateCookie.flavor();          // Output: Chocolate flavor
chocolateCookie.addChocolateChips();  // Output: Adding chocolate chips
chocolateCookie.bake();            // Output: Cookie is baking

OatmealRaisinCookie oatmealRaisinCookie = new OatmealRaisinCookie();
oatmealRaisinCookie.flavor();      // Output: Oatmeal and raisin flavor
oatmealRaisinCookie.addRaisins();  // Output: Adding raisins
oatmealRaisinCookie.bake();        // Output: Cookie is baking
```

Abstract class có thể có constructor. Bạn cần chúng để khởi tạo attribute và thực thi bất kỳ logic nào cần chạy khi một instance của concrete (sub)class được tạo. Abstract class là một class, và như mọi class khác, nó có thể có attribute và những attribute đó có thể cần được khởi tạo khi một instance (của concrete class) được tạo. Đây là một ví dụ:

```java
abstract class Cookie {
    protected String name;
    
    public Cookie(String name) {
        this.name = name;
        System.out.println("Cookie constructor is called");
    }
    
    abstract void flavor();
    
    public void bake() {
        System.out.println(name + " is baking");
    }
}
```

Trong ví dụ đã cập nhật này, abstract class `Cookie` giờ có một constructor nhận parameter `name`. Nó khởi tạo attribute `name` của cookie. Attribute `name` được khai báo là `protected`, nghĩa là nó có thể được truy cập bởi các subclass.

Bằng cách này, các concrete class `ChocolateCookie` và `OatmealRaisinCookie` có thể gọi constructor của abstract class `Cookie` bằng `super()`, truyền vào tên cụ thể cho từng loại cookie. Chúng ta sẽ thấy cách dùng `super()` ở phần sau của chương này.

Khi bạn coi abstract class như một contract hay một template mà các subclass phải tuân theo và hoàn thiện để đảm bảo một behavior chung, những quy tắc sau đây trở nên hợp lý:

- Một abstract class không thể là final. Modifier `final` ngăn một class bị subclass, và điều này mâu thuẫn với bản chất của abstract class là phải được kế thừa để sử dụng. Vậy nên không, đánh dấu một abstract class là `final` sẽ không làm nó an toàn hơn, mà làm nó trở nên vô dụng.

- Abstract method cũng không thể là final, vì lý do tương tự, chúng phải được override trong một subclass. 

- Abstract method không thể là native hoặc synchronized, vì những lý do hơi khác. Một native method được hiện thực bằng ngôn ngữ khác như C++ trong JVM, nên nó đã có implementation rồi. Chúng ta sẽ nói về synchronized method trong một chương sau, nhưng modifier `synchronized` được dùng để phối hợp truy cập đa luồng, và để làm được điều đó, method cần có thân, tức một implementation.

- Một abstract method không thể là `private`. Thật vô lý khi một method phải được hiện thực bởi một subclass ở class khác lại không thể được class đó nhìn thấy. Vậy nên không, abstract method `private` không thể tồn tại.

- Cuối cùng, một abstract method cũng không thể là static. Static method thuộc về chính class, không thuộc về instance nào. Một abstract method chỉ hữu ích khi một subclass hiện thực nó, nghĩa là một instance dùng nó.

Tóm lại, đây là các quy tắc để khai báo abstract class và method đúng cách:

- Nếu một class chứa một hoặc nhiều abstract method, class đó phải được khai báo là abstract.

- Một abstract class có thể có cả abstract method lẫn non-abstract (concrete) method.

- Một abstract class có thể extends một abstract class hoặc concrete class khác, và một abstract class có thể được extends bởi một abstract class hoặc concrete class khác.

- Một subclass có thể override một concrete method trong superclass và khai báo nó là abstract.

- Một abstract subclass có thể override một số hoặc không override abstract method nào trong superclass của nó, nhưng concrete subclass đầu tiên phải hiện thực tất cả chúng.

Bây giờ, trước khi nói về sealed class, hãy ôn lại chủ đề interface.

### Interfaces {#interfaces}
Trong lập trình hướng đối tượng, ngoài class, Java còn cung cấp một công cụ mạnh mẽ: interface. Interface trong Java thực chất là một contract định nghĩa tập method mà một class phải hiện thực. Nó giống như thực đơn ở nhà hàng. Thực đơn liệt kê những món có sẵn nhưng không cung cấp chi tiết cách chúng được chế biến. Khi bạn gọi một món từ thực đơn, nhà bếp (class) cung cấp một implementation cụ thể của món đó (method).

Vậy chính xác thì interface là gì và nó khác gì so với một class thông thường hay thậm chí một abstract class?

Interface trong Java là một reference type, tương tự class, chỉ có thể chứa constant, method signature, default method, static method và nested type. Interface không thể được khởi tạo, chúng chỉ có thể được hiện thực bởi class hoặc được extends bởi interface khác.

Để khai báo một interface, bạn dùng keyword `interface` thay vì keyword `class`. Đây là một ví dụ:

```java
public interface Drawable {
    void draw();
}
```

Mọi class hiện thực interface `Drawable` đều phải cung cấp implementation cho method `draw()`.

Thoạt nhìn, interface có vẻ rất giống abstract class. Suy cho cùng, cả hai đều có thể chứa abstract method, tức method không có thân. Tuy nhiên, có một số khác biệt quan trọng:
- Abstract class có thể có instance variable và constructor, còn interface thì không.

- Abstract class có thể có non-abstract method, còn mọi method trong interface đều mặc nhiên là abstract (ngoại trừ default method và static method, sẽ được đề cập sau).

- Một class chỉ có thể extends một abstract class, nhưng có thể implements nhiều interface.

Vậy nên dù có phần trùng lặp, interface và abstract class phục vụ những mục đích khác nhau và không thể thay thế cho nhau.

Để dùng một interface, một class phải hiện thực nó. Keyword `implements` được dùng để hiện thực một interface:

```java
public class Circle implements Drawable {
    public void draw() {
        System.out.println("Drawing a circle");
    }
}
```

Nếu một class hiện thực một interface nhưng không hiện thực tất cả method, nó phải được khai báo là `abstract`.

```java
public abstract class Shape implements Drawable {
    // Nội dung của class
}
```

Mọi method trong interface đều mặc nhiên là `public` và `abstract`. Bạn không cần dùng keyword `public` hay `abstract` khi khai báo method trong interface. 

Mọi variable được khai báo trong interface đều mặc nhiên là `public`, `static` và `final`.

Vậy nên đoạn này:

```java
public interface MyInterface {
    int NUMBER = 10;
    void method();
}
```

Tương đương với đoạn này:

```java
public interface MyInterface {
    public static final int NUMBER = 10;
    public abstract void method();
}
```

Điều quan trọng cần lưu ý là vì method của interface là `abstract`, chúng không thể được khai báo là `private`, `protected`, `final` hoặc `static` (ngoại trừ `static` method, sẽ được đề cập sau).

Một interface có thể extends một interface khác, tương tự cách một class có thể extends một class khác. Keyword `extends` được dùng cho việc này:

```java
public interface Moveable {
    void move();
}

public interface Drawable extends Moveable {
    void draw();
}
```

Trong trường hợp này, mọi class hiện thực `Drawable` đều phải cung cấp implementation cho cả `draw()` và `move()`.

Một class chỉ có thể extends từ một class. Tuy nhiên, một class có thể implements nhiều interface. Đây là một cách để đạt được một dạng multiple inheritance trong Java:

```java
public interface Moveable {
    void move();
}

public interface Drawable {
    void draw();
}

public class Circle implements Drawable, Moveable {
    public void draw() {
        System.out.println("Drawing a circle");
    }

    public void move() {
        System.out.println("Moving a circle");
    }
}
```

Điều này không vi phạm quy tắc single inheritance của Java vì interface không chứa implementation nào. Nếu một class implements hai interface có cùng một method, đó không phải là vấn đề. Class chỉ đơn giản cung cấp một implementation duy nhất cho method đó, giải quyết các vấn đề mơ hồ và phức tạp:

```java
public interface A {
    void method();
}

public interface B {
    void method();
}

public class C implements A, B {
    public void method() {
        System.out.println("Method implementation");
    }
}
```

Ngoài ra, interface có thể có default method. Đây là những method có thân, cung cấp một implementation mặc định nếu một class không override chúng:

```java
public interface Drawable {
    void draw();
    default void print() {
        System.out.println("Printing...");
    }
}
```

Các class hiện thực `Drawable` có thể override method `print()`, nhưng không bắt buộc.

Nếu một class implements hai interface và cả hai đều có cùng default method, class đó phải override method này. Nếu nó muốn gọi default method từ một trong các interface, nó có thể làm vậy bằng keyword `super`:

```java
public interface A {
    default void method() {
        System.out.println("A's method");
    }
}

public interface B {
    default void method() {
        System.out.println("B's method");
    }
}

public class C implements A, B {
    public void method() {
        A.super.method();
    }
}
```

Interface cũng có thể có static method, tương tự static method trong class:

```java
public interface Drawable {
    static void staticMethod() {
        System.out.println("Static method");
    }
}
```

Static method trong interface không được kế thừa bởi các class hay interface extends interface đó.

Với ví dụ trên, bạn sẽ dùng interface `Drawable` để gọi `staticMethod` như sau:

```java
Drawable.staticMethod();
```

Ngoài default method và `static` method, interface cũng có thể có `private` method. Những method này hữu ích để chia sẻ code giữa các default method trong interface:

```java
public interface Drawable {
    default void print() {
        printLine();
        System.out.println("Printing...");
    }

    private void printLine() {
        System.out.println("---");
    }
}
```

Private method trong interface không thể được truy cập bởi các class hiện thực interface đó.

### Sealed Classes {#sealed-classes}
Hãy tưởng tượng một hoàng gia với quy tắc nghiêm ngặt: chỉ một số người nhất định mới có thể trở thành vua hay nữ hoàng tương lai, và quy tắc này không thể thay đổi. Trong Java, sealed class giống như hoàng gia này. Chúng cho phép một class kiểm soát chặt chẽ những class khác được extends nó, giống như hoàng gia kiểm soát ai được nằm trong danh sách kế vị ngai vàng.

Vậy nếu một class là sealed, có nghĩa là nó bị khóa hoàn toàn và không ai có thể extends nó sao? Không hẳn. Một sealed class chỉ đơn giản hạn chế ai được phép extends nó, chứ không hoàn toàn cấm đoán. Bạn được quyền chỉ định một tập các subclass được phép.

Tính năng này hữu ích vì nhiều lý do:
- Nó cho phép tác giả của thư viện phát triển API theo thời gian mà vẫn tránh được những extension ngoài ý muốn.
- Nó cho phép mô hình hóa các hệ thống phân cấp và state machine với một tập subclass hữu hạn.
- Nó mang lại sự an toàn ở compile-time bằng cách giới hạn những khả năng của code bên ngoài.

Để tạo một sealed class, bạn dùng modifier `sealed` trên khai báo class, cùng với mệnh đề `permits` để chỉ định các subclass được phép:

```java
public sealed class Vehicle permits Car, Truck, Motorcycle {
    public void startEngine() {
        System.out.println("Starting the vehicle's engine.");
    }
}

final class Car extends Vehicle {
    @Override
    public void startEngine() {
        System.out.println("Starting the car's engine.");
    }
}

final class Truck extends Vehicle {
    @Override
    public void startEngine() {
        System.out.println("Starting the truck's engine.");
    }
}

final class Motorcycle extends Vehicle {
    @Override
    public void startEngine() {
        System.out.println("Starting the motorcycle's engine." );
    }
}
```

Modifier `sealed` cho biết class này là sealed. Mệnh đề `permits` liệt kê những class được phép extends sealed class.

Sealed class và các subclass của nó phải được khai báo trong cùng package (hoặc named module) với các direct subclass của chúng. Điều này đảm bảo mối quan hệ gắn bó giữa sealed class và những subclass được phép của nó.

Mọi class trực tiếp extends một sealed class đều phải chỉ định đúng một trong ba modifier sau: `final`, `sealed` hoặc `non-sealed`:

- `final`: Subclass không thể bị extends thêm nữa. Đây là lựa chọn hạn chế nhất.
- `sealed`: Subclass cũng là sealed và phải chỉ định các subclass được phép của riêng nó.
- `non-sealed`: Subclass mở cho bất kỳ subclass chưa biết nào extends. Đây là lựa chọn thoáng nhất.

Nếu bạn không chỉ định một trong những modifier này trên một direct subclass của sealed class, bạn sẽ nhận compilation error. Compiler bắt buộc điều này để đảm bảo hệ thống phân cấp được định nghĩa rõ ràng.

Đánh dấu một subclass là `non-sealed` chỉ đơn giản nghĩa là nó mở cho việc extends. Điều đó không bắt buộc bạn phải thực sự tạo ra các subclass mới. Việc vô tình dùng `non-sealed` khi bạn không thêm subclass nào sẽ không làm hỏng gì, nhưng nó báo hiệu cho các lập trình viên khác rằng ý định của bạn là cho phép class được extends.

Mệnh đề `permits` là tùy chọn nếu sealed class và các direct subclass của nó được khai báo trong cùng một file hoặc các subclass được nested bên trong sealed class. Trong những trường hợp này, compiler có thể suy ra các subclass được phép, nên bạn có thể bỏ qua phần liệt kê tường minh.

Đây là một ví dụ trong đó mệnh đề `permits` được bỏ qua:

```java
// Beverage.java
public sealed class Beverage {
    void pour();
}

final class Coffee implements Beverage {
    public void pour() {
        System.out.println("Pouring coffee");
    } 
}

final class Tea implements Beverage {
    public void pour() {
        System.out.println("Pouring tea");
    }
}
```

Vì `Coffee` và `Tea` được khai báo trong cùng file với sealed class `Beverage` (`Beverage.java`), mệnh đề `permits` có thể được compiler suy ra.

Vậy sealed class chỉ có thể được dùng trong cùng file? Không, sealed class và các subclass của nó có thể nằm ở những file khác nhau, miễn là chúng ở cùng package hoặc module. Ràng buộc cùng file chỉ liên quan tới việc bỏ qua mệnh đề `permits`.

Và để trả lời một câu hỏi phổ biến khác: "Nếu tôi seal một class, tôi không thể dùng nó ở package khác, đúng không?" Bạn vẫn có thể dùng một sealed class từ package khác, nhưng bạn không thể khai báo các subclass của nó ở package khác. Việc sử dụng không bị hạn chế, chỉ việc extends mới bị.

Trong mọi trường hợp, một khi class đã được seal, tập subclass được phép là cố định. Bạn không thể thêm subclass mới ngoài những gì được chỉ định trong mệnh đề `permits`. Nếu sau này bạn cần mở rộng hệ thống phân cấp, bạn sẽ phải sửa sealed class để cho phép thêm subclass. Việc này đòi hỏi biên dịch lại sealed class và các subclass hiện có của nó.

Nếu bạn thắc mắc liệu có giới hạn về số lượng subclass mà một sealed class có thể cho phép, câu trả lời là không, không có giới hạn cứng nào cho số subclass bạn có thể cho phép. Tuy nhiên, ý định của sealed class là có một tập subclass hữu hạn và dễ quản lý. Việc cho phép hàng trăm subclass sẽ đi ngược lại tinh thần đó và có khả năng chỉ ra một vấn đề trong thiết kế. Hãy giữ một con số hợp lý, phù hợp với use case của bạn.

Sealing không chỉ giới hạn ở class. Bạn cũng có thể seal interface.

Interface có thể được seal để giới hạn những class hiện thực chúng hoặc những interface extends chúng. Đây là một ví dụ:

```java
public sealed interface Shape permits Circle, Rectangle, Triangle, Polygon {
    double getArea();
}

final class Circle implements Shape {
    public double getArea() {
        // Triển khai getArea() cho hình tròn
    }
}

final class Rectangle implements Shape {
    public double getArea() {
        // Triển khai getArea() cho hình chữ nhật
    }
}

final class Triangle implements Shape {
    public double getArea() {
        // Triển khai getArea() cho hình tam giác
    }
}

sealed interface Polygon extends Shape permits RegularPolygon, IrregularPolygon {
    int getNumberOfSides();
}

final class RegularPolygon implements Polygon {
    public double getArea() {
        // Triển khai getArea() cho đa giác đều
    }
    
    public int getNumberOfSides() {
        // Triển khai getNumberOfSides() cho đa giác đều
    }
}

final class IrregularPolygon implements Polygon {
    public double getArea() {
        // Triển khai getArea() cho đa giác không đều
    }
    
    public int getNumberOfSides() {
        // Triển khai getNumberOfSides() cho đa giác không đều
    }
}
```

Trong ví dụ này, interface `Shape` là sealed và cho phép bốn class hiện thực nó: `Circle`, `Rectangle`, `Triangle` và `Polygon`. Nghĩa là chỉ bốn class này mới có thể trực tiếp implements interface `Shape`.

Nhưng interface `Polygon` cũng là sealed và extends interface `Shape`. Nó cho phép hai class hiện thực nó: `RegularPolygon` và `IrregularPolygon`. Điều này minh họa cách sealing được dùng để kiểm soát những interface nào được extends một sealed interface.

Bằng cách seal interface `Polygon`, chúng ta giới hạn các class có thể hiện thực nó chỉ còn `RegularPolygon` và `IrregularPolygon`. Không class nào khác có thể trực tiếp implements `Polygon`. Tuy nhiên, vì `Polygon` extends `Shape`, hai class `RegularPolygon` và `IrregularPolygon` cũng gián tiếp implements `Shape`.

Điều này cho phép một cấu trúc inheritance được định nghĩa rõ ràng và bị giới hạn. 

Điều trên cũng áp dụng cho class, bạn có thể đổi interface `Shape` thành một class và thực hiện những sửa đổi cần thiết cho các class khác để đạt được cấu trúc phân cấp tương tự.

Tóm lại, đây là những quy tắc chính cho sealed class:

1. Sealed class được khai báo với modifier `sealed` và `permits`.

2. Sealed class phải được khai báo trong cùng package hoặc named module với các direct subclass của chúng. 

3. Direct subclass của sealed class phải được đánh dấu `final`, `sealed` hoặc `non-sealed`.

4. Mệnh đề `permits` là tùy chọn nếu sealed class và các direct subclass của nó được khai báo trong cùng một file hoặc các subclass được nested bên trong sealed class.

5. Interface có thể được seal để giới hạn những class hiện thực chúng hoặc những interface extends chúng.


### The `this` Reference {#the-this-reference}
Khi viết code Java, bạn sẽ thường thấy keyword `this` xuất hiện rải rác trong các method và constructor. Nhưng chính xác thì `this` là gì, và tại sao chúng ta dùng nó?

`this` là một reference tới instance hiện tại của một class. Nói cách khác, khi bạn đang ở bên trong một method hoặc constructor của một class, `this` tham chiếu tới object cụ thể mà method hay constructor đó thuộc về. Đây là một ví dụ đơn giản:

```java
public class Person {
    private String name;
    
    public Person(String name) {
        this.name = name;
    }
}
```

Trong constructor, chúng ta dùng `this.name` để chỉ rõ rằng chúng ta đang nói về field `name` của object `Person` cụ thể này, chứ không phải một biến `name` nào khác.

Nhưng khoan, bạn có thể đang nghĩ: "Vậy `this` chỉ là một biến khác mà tôi có thể thay đổi, đúng không?" Không hẳn. `this` là một final reference, nghĩa là bạn không thể gán nó cho thứ gì khác. Nó luôn trỏ tới instance hiện tại của object.

`this` không thể được dùng ở mọi nơi trong code, chẳng hạn trong static method. Nó chỉ có ý nghĩa trong ngữ cảnh của một instance method hoặc constructor. Static method thuộc về chính class, không thuộc về một instance cụ thể, nên `this` không có ý nghĩa gì ở đó.

Vậy có phải lúc nào bạn cũng phải dùng `this` mỗi khi tham chiếu tới một attribute hay method không? Không nhất thiết. Nếu không có sự mơ hồ, bạn thường có thể bỏ qua `this`. Tuy nhiên, có những lúc dùng `this` giúp code rõ ràng hơn và tránh nhầm lẫn. Ví dụ:

```java
public class Person {
    private String name;
    
    public Person(String name) {
        this.name = name;
    }
    
    public void introduce(Person other) {
        System.out.println("Hi " + other.name + ", I'm " + this.name);
    }
}
```

Ở đây, dùng `this.name` làm rõ rằng chúng ta đang tham chiếu tới `name` của instance `Person` hiện tại, chứ không phải `Person` `other`. 

Dưới đây là một vài tình huống mà `this` là cần thiết:
- Để phân biệt giữa local variable và instance variable có cùng tên
- Để truyền instance hiện tại làm argument cho một method
- Để gọi một constructor khác từ bên trong một constructor

Nói về constructor, bạn không thể dùng `this` để gọi một constructor từ bất kỳ đâu trong class. Bạn chỉ có thể dùng `this` để gọi một constructor khác từ bên trong một constructor, và nó phải là câu lệnh đầu tiên:

```java
public class Person {
    private String name;
    private int age;
    
    public Person(String name) {
        this(name, 0);
    }
    
    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }
}
```

Điều này hữu ích khi bạn có nhiều constructor và muốn tránh lặp lại code.

Tuy nhiên, có một quy tắc: nếu bạn dùng `this` để gọi một constructor khác, nó phải là câu lệnh đầu tiên trong constructor. Quy tắc này đảm bảo constructor kia được gọi trước khi thực thi bất kỳ code nào trong constructor chứa lời gọi this, ngăn việc dùng field chưa được khởi tạo hoặc lặp lại code khởi tạo. Ví dụ, đoạn sau sẽ không compile:
```java
public class Person {
    private String name;
    private int age;
    
    public Person(String name) {
        System.out.println("Person(String) Constructor Called");
        // Dòng sau sẽ gây ra compile-time error
        this(name, 0); // ERROR: Constructor call phải là câu lệnh đầu tiên trong một constructor
    }
    
    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }
}
```

Ngoài ra, hãy nhớ rằng `this` không tham chiếu tới chính class. `this` tham chiếu tới instance hiện tại. Mỗi instance có reference `this` riêng của nó. Nó không thể là `null`.

Điều này cũng có nghĩa là `this` được dùng cho instance member. Static field và static method thuộc về chính class, không thuộc về một instance cụ thể, nên `this` không áp dụng được.

Ngoài ra, khi bạn dùng `this` bên trong một method, bạn đang tham chiếu tới instance của object mà method thuộc về, chứ không phải chính method đó.

Cuối cùng, truyền `this` làm argument rất hữu ích khi bạn muốn cho một method khác quyền truy cập instance hiện tại. Ví dụ, bạn có thể truyền `this` cho một method của class khác để nó có thể gọi ngược lại object gốc:

```java
public class Person {
    private String name;
    
    public Person(String name) {
        this.name = name;
    }
    
    public void introduceYourselfTo(IntroductionService service) {
        service.introduce(this);
    }
    
    public String getName() {
        return name;
    }
}

public class IntroductionService {
    public void introduce(Person person) {
        System.out.println("Hello, my name is " + person.getName());
    }
}
```

Trong ví dụ này, chúng ta có hai class: `Person` và `IntroductionService`.

Class `Person` có một method tên `introduceYourselfTo`, nhận một `IntroductionService` làm parameter. Bên trong method này, `this` (tham chiếu tới instance `Person` hiện tại) được truyền làm argument cho method `introduce` của `IntroductionService`.

Class `IntroductionService` có một method `introduce` nhận một `Person` làm parameter. Method này sau đó có thể truy cập method `getName()` của `Person` để in ra lời giới thiệu.

Đây là cách bạn có thể dùng những class này:

```java
Person alice = new Person("Steve");
IntroductionService service = new IntroductionService();
alice.introduceYourselfTo(service);
```

Và đây là output:
```
Hello, my name is Steve
```

### The `super` Reference {#the-super-reference}

Vậy keyword `this` được dùng để tham chiếu tới instance hiện tại của class. Nhưng nếu bạn muốn tham chiếu tới superclass mà class hiện tại kế thừa thì sao? Đó là lúc `super` xuất hiện.

Keyword `super` đóng vai trò reference tới class cha (superclass) của class hiện tại. Nó cho phép truy cập các member của superclass (field, method và constructor).

Mục đích chính của `super` là phân biệt giữa member của superclass và member của class hiện tại khi chúng có cùng tên. Bằng cách thêm tiền tố `super` trước tên member, bạn chỉ định rằng mình muốn dùng phiên bản của member đó từ superclass, thay vì phiên bản của class hiện tại.

Cú pháp dùng `super` rất đơn giản:
```java
super.memberName
```

Ở đây, `memberName` có thể là field, method hoặc constructor của superclass.

Overriding trong Java là một tính năng cho phép một subclass hay child class cung cấp implementation cụ thể cho một method đã được cung cấp bởi một trong các superclass hay parent class của nó. 

Khi bạn override một method trong subclass, bạn không xóa bỏ hay thay thế method gốc trong superclass. Method của superclass vẫn ở đó, nhưng khi bạn gọi method trên một object của subclass, phiên bản bị override trong subclass sẽ được thực thi thay vào đó. Vì vậy, khi override một method trong subclass, có thể bạn muốn gọi implementation gốc của method từ superclass. 

Trong trường hợp đó, bạn có thể dùng `super` để gọi phiên bản method của superclass:
```java
@Override
public void someMethod() {
    super.someMethod(); // Gọi phần implementation của superclass
    // Code bổ sung riêng cho subclass
}
```

Một use case phổ biến khác của `super` là khi bạn muốn gọi constructor của superclass từ constructor của class hiện tại. Cũng như với `this`, bạn phải gọi `super()` ở câu lệnh đầu tiên trong constructor:
```java
public class SubClass extends SuperClass {
    public SubClass() {
        super(); // Gọi superclass constructor
        // Code khởi tạo khác
    }
}
```

Nếu không, bạn sẽ nhận compilation error. 

Nếu superclass của bạn không có default constructor (không tham số), bạn sẽ cần gọi tường minh một constructor có tham số bằng `super(arguments)`. Bạn không thể dùng `super` mà không chỉ định các argument cần thiết.

Xét ví dụ sau:
```java
// Superclass không có default constructor
public class Person {
    private String name;
    private int age;

    // Constructor yêu cầu tham số
    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    // Các getter method cho name và age
    public String getName() {
        return name;
    }

    public int getAge() {
        return age;
    }
}

// Subclass extends Person
public class Student extends Person {
    private String studentID;

    // Vì Person không có default constructor, chúng ta phải gọi tường minh một parameterized constructor
    public Student(String name, int age, String studentID) {
        super(name, age); // Gọi superclass constructor với các tham số
        this.studentID = studentID;
    }

    // Getter method cho studentID
    public String getStudentID() {
        return studentID;
    }
}
```

Trong constructor của `Student`, `super(name, age);` được dùng để gọi tường minh constructor có tham số của class `Person`. Điều này là cần thiết vì `Person` không có constructor không tham số. Nếu lời gọi `super` này bị bỏ qua, code sẽ không compile, vì Java sẽ cố gọi một default constructor trong class `Person`, mà trong trường hợp này không tồn tại.

Bây giờ, có thể bạn thắc mắc: nếu tôi dùng `super`, có nghĩa là tôi không thể dùng `this` trong cùng method sao? Câu trả lời là không. Bạn có thể dùng cả `this` lẫn `super` trong cùng một method, vì chúng phục vụ những mục đích khác nhau. `this` tham chiếu tới instance hiện tại, còn `super` tham chiếu tới superclass.

Tuy nhiên, điều quan trọng cần ghi nhớ là `super` không thể được dùng để truy cập trực tiếp các private member (field hay method) của superclass. Private member chỉ có thể được truy cập trong cùng class. Nếu bạn cần truy cập chúng, bạn sẽ phải dựa vào các method `public` hay `protected` do superclass cung cấp.

Cuối cùng, cũng đáng lưu ý rằng dù `super` chủ yếu được dùng để gọi method hoặc truy cập field từ class cha trực tiếp, nó gián tiếp cho phép tương tác với hệ thống phân cấp inheritance rộng hơn. Cụ thể, nếu class cha trực tiếp kế thừa method từ các ancestor của nó (class ông bà và xa hơn), `super` cũng có thể gián tiếp truy cập những method này. Điều này là vì các method được kế thừa từ class cha — mà `super` có thể gọi — có thể tự chúng gọi method từ các ancestor trong chuỗi inheritance. Tuy nhiên, việc gọi trực tiếp method hoặc truy cập field của class ông bà hay cao hơn bằng `super` là không thể. Để truy cập trực tiếp những method như vậy, bạn thường phải dựa vào các method được kế thừa, vốn đóng gói chức năng này bên trong superclass trực tiếp của bạn.

Xét ví dụ sau, mở rộng ví dụ trước bằng cách thêm một class mới `GraduateStudent` kế thừa từ `Student`, và một class ông bà `Human` mà `Person` kế thừa từ đó:

```java
// Class ông
public class Human {
    private String nationality;

    public Human(String nationality) {
        this.nationality = nationality;
    }

    protected void sayHello() {
        System.out.println("Hello from Human!");
    }
}

// Class cha
public class Person extends Human {
    private String name;
    private int age;

    public Person(String name, int age, String nationality) {
        super(nationality); // Gọi constructor của Human
        this.name = name;
        this.age = age;
    }

    // Override method sayHello
    @Override
    protected void sayHello() {
        super.sayHello(); // Gọi sayHello của Human
        System.out.println("Hello from Person!");
    }
}

// Class hiện tại
public class Student extends Person {
    private String studentID;

    public Student(String name, int age, String nationality, String studentID) {
        super(name, age, nationality); // Gọi constructor của Person
        this.studentID = studentID;
    }

    // Override method sayHello một lần nữa
    @Override
    protected void sayHello() {
        super.sayHello(); // Gọi sayHello của Person, rồi đến lượt nó gọi sayHello của Human
        System.out.println("Hello from Student!");
    }
}

// Subclass mới extends Student
public class GraduateStudent extends Student {
    private String researchTopic;

    public GraduateStudent(String name, int age, String nationality, String studentID, String researchTopic) {
        super(name, age, nationality, studentID); // Gọi constructor của Student
        this.researchTopic = researchTopic;
    }

    public void introduce() {
        super.sayHello(); // Gọi sayHello của Student, rồi đến lượt nó gọi của Person, và sau đó là sayHello của Human
        System.out.println("I am a graduate student working on " + researchTopic + ".");
    }
}

```

Trong ví dụ này, class `GraduateStudent` dùng `super.sayHello()` trong method `introduce` của nó. Lời gọi này gọi method `sayHello` từ class `Student`, mà bản thân nó override method `sayHello` của `Person`. Method `sayHello` của class `Person` sau đó gọi method `sayHello` của `Human`. Điều này minh họa cách `super` có thể được dùng để gián tiếp truy cập các method ngược lên chuỗi inheritance, từ class `Human` tới class `GraduateStudent`, dù việc truy cập trực tiếp method của `Human` từ `GraduateStudent` bằng `super` là không thể.

Bây giờ hãy nói thêm về overriding và polymorphism.



## Polymorphism {#polymorphism}

### Giới thiệu về Polymorphism {#introducing-polymorphism}
Polymorphism là một trong những trụ cột của lập trình hướng đối tượng và là một khái niệm mạnh mẽ trong Java. Nói một cách đơn giản, polymorphism cho phép bạn xử lý các object thuộc những subclass khác nhau như thể chúng là object của cùng một superclass. Nó giống như việc có một chiếc remote duy nhất có thể điều khiển nhiều loại thiết bị: TV, dàn âm thanh và đầu DVD. Cũng giống như chiếc remote gửi tín hiệu đến từng thiết bị, và mỗi thiết bị thực hiện những chức năng khác nhau tùy theo thiết bị mà nó đang giao tiếp, trong Java, bạn có thể dùng một reference type duy nhất để tương tác với các object thuộc những class khác nhau, cho phép chúng thể hiện những hành vi riêng của mình thông qua một interface chung.

Tuy nhiên, polymorphism không có nghĩa là các method có thể tùy tiện thay đổi hành vi của mình. Thay vào đó, nó cho phép subclass cung cấp implementation riêng cho những method được định nghĩa trong superclass, một khái niệm được gọi là method overriding.

Như đã đề cập trước đó, khi bạn override một method trong subclass, bạn không xóa bỏ hay thay thế method gốc trong superclass. Method của superclass vẫn ở đó, nhưng khi bạn gọi method trên một object của subclass, phiên bản bị override trong subclass sẽ được thực thi thay thế. Cần lưu ý rằng overriding không giống với việc hiding member — chúng ta sẽ bàn về điều này sau.

Để override một method đúng cách, method trong subclass phải có cùng:
- Name
- Return type
- Parameter list

như method trong superclass. Xét ví dụ sau:

```java
class Animal {
    public void makeSound() {
        System.out.println("The animal makes a sound");
    }
}

class Pig extends Animal {
    @Override
    public void makeSound() {
        System.out.println("Oink");
    }
}

class Duck extends Animal {
    @Override
    public void makeSound() {
        System.out.println("Quack");
    }
}
```

Và một sơ đồ để hình dung hệ thống phân cấp này:
```
┌──────────────────────────────────────────┐
│            Animal makeSound()            │
└──────────────────────┬───────────────────┘
                       │
           ┌───────────┴─────────┐
           │                     │
┌──────────┴────────┐  ┌─────────┴─────────┐
│    Pig (Oink)     │  │   Duck (Quack)    │
└───────────────────┘  └───────────────────┘

```

Class `Animal` có một method tên `makeSound()`. Hai class `Pig` và `Duck` kế thừa `Animal`, override method `makeSound()` để cung cấp implementation riêng. Giờ hãy xem polymorphism hoạt động:

```java
Animal animal1 = new Pig();
Animal animal2 = new Duck();

animal1.makeSound(); // Output: Oink
animal2.makeSound(); // Output: Quack
```

Ở đây, chúng ta tạo hai biến có type `Animal` nhưng gán cho chúng object của class `Pig` và `Duck`. Khi gọi method `makeSound()` trên mỗi biến, method bị override tương ứng trong subclass sẽ được gọi. Đây chính là sức mạnh của polymorphism — khả năng xử lý object của những subclass khác nhau như object của một superclass chung.

Cần hiểu rõ rằng overriding không giống overloading. Overloading là việc có nhiều method cùng tên nhưng khác parameter list trong cùng một class. Ngược lại, overriding là việc cung cấp một implementation khác của một method trong subclass.

Một hiểu lầm phổ biến khác là overriding áp dụng cho tất cả member của class, kể cả variable. Tuy nhiên, điều đó không đúng. Overriding chỉ áp dụng cho method. Khi bạn khai báo một variable cùng tên trong subclass, thực ra bạn đang hiding variable của superclass chứ không phải overriding nó.

Hãy cùng khám phá một số quy tắc liên quan đến overriding.

### Các quy tắc Overriding {#overriding-rules}
Có một số quy tắc bạn cần tuân theo khi override method từ superclass:

**Quy tắc #1: Method Signatures**  
Quy tắc đầu tiên và quan trọng nhất là method signature phải khớp chính xác giữa superclass và subclass. Nghĩa là name, parameter và return type phải giống hệt nhau (với một ngoại lệ sẽ bàn sau). Bạn không thể thay đổi parameter hay return type tùy ý:

```java
// Superclass
class Cookie {
    // Định nghĩa method 'eat' trong superclass
    public String eat() {
        return "Eating a plain cookie";
    }
}

// Subclass
class ChocolateChipCookie extends Cookie {
    // Override method 'eat' trong subclass
    @Override
    public String eat() {
        return "Eating a chocolate chip cookie";
    }
}
```

Trong ví dụ này:
- Class `Cookie` định nghĩa một method tên `eat` trả về `String`.

- Class `ChocolateChipCookie` kế thừa `Cookie`, override method `eat`. Method override trong `ChocolateChipCookie` có cùng name, return type và parameter list (trong trường hợp này là không có) như method trong `Cookie`.

- Khi một instance của `ChocolateChipCookie` gọi `eat`, phiên bản bị override của method được thực thi, trả về `"Eating a chocolate chip cookie"`.

Tại sao method signature phải giữ nguyên? Hãy nghĩ về nó như một contract giữa superclass và subclass. Superclass định nghĩa một method cụ thể mà subclass có thể override nếu cần. Nếu bạn thay đổi signature, bạn đang phá vỡ contract đó. Method của subclass khi đó sẽ không còn là một override thực sự của method superclass nữa.

**Quy tắc #2: Access Modifiers**  
Khi override một method, bạn có thể nới lỏng access modifier nhưng không được thắt chặt hơn. Ví dụ, bạn có thể override một method `protected` trong superclass và chuyển nó thành `public` trong subclass. Nhưng bạn không thể làm ngược lại, chẳng hạn đổi một method `public` thành `private`:

```java
// Superclass
class Cookie {
    // Định nghĩa một method với access modifier 'protected' trong superclass
    protected String recipe() {
        return "Default cookie recipe";
    }
}

// Subclass
class ChocolateChipCookie extends Cookie {
    // Override method 'recipe' trong subclass và đổi access modifier thành 'public'
    @Override
    public String recipe() {
        return "Chocolate chip cookie recipe";
    }
}
```

Trong ví dụ này:
- Class `Cookie` định nghĩa method `recipe` với access modifier `protected`. Điều này nghĩa là method `recipe` chỉ có thể được truy cập trong chính class của nó, trong subclass hoặc trong cùng package.

- Class `ChocolateChipCookie` kế thừa `Cookie`, override method `recipe`, đổi access modifier của method override thành `public`, tức là ít hạn chế hơn `protected`.

- Cố gắng truy cập method `recipe` trực tiếp từ một instance `Cookie` sẽ gây compile-time error do kiểm soát truy cập `protected`. Tuy nhiên, truy cập method `recipe` thông qua instance của `ChocolateChipCookie` thì được vì nó là `public`.

Điều này thường khiến nhiều người bối rối. Họ nghĩ: "Vì đây là subclass của mình, chẳng lẽ mình không thể giới hạn truy cập vào method nếu muốn?" Tuy nhiên, điều này đi ngược lại nguyên tắc rằng subclass phải luôn hoạt động ở bất cứ đâu superclass của nó được dùng. Nếu bạn làm method bị hạn chế hơn trong subclass, bạn phá vỡ tính tương thích này.

**Quy tắc #3: Checked Exceptions**  
Chúng ta sẽ xem lại exception chi tiết hơn ở chương sau, nhưng nếu method của superclass khai báo bất kỳ checked exception nào trong mệnh đề `throws`, method bị override trong subclass chỉ được khai báo những exception giống như vậy hoặc cụ thể hơn. Nó không thể thêm bất kỳ checked exception mới nào không phải là subclass của những exception mà method superclass đã khai báo:

```java
class BakingException extends Exception {
    public BakingException(String message) {
        super(message);
    }
}

class OverBakingException extends BakingException {
    public OverBakingException(String message) {
        super(message);
    }
}

// Superclass
class Cookie {
    // Định nghĩa một method khai báo throw BakingException chung
    public String bake() throws BakingException {
        return "Cookie is baked";
    }
}

// Subclass
class ChocolateChipCookie extends Cookie {
    // Override method 'bake', khai báo một exception cụ thể hơn là OverBakingException
    @Override
    public String bake() throws OverBakingException {
        return "Chocolate chip cookie is baked";
    }
}
```

Trong ví dụ này:
- `BakingException` là một checked exception đại diện cho lỗi nướng bánh nói chung.

- `OverBakingException` là một checked exception cụ thể hơn, cho biết bánh đã bị nướng quá lửa, và nó kế thừa `BakingException`.

- Class `Cookie` có method `bake` khai báo rằng nó có thể throw `BakingException`.

- Class `ChocolateChipCookie` override method `bake` và khai báo rằng nó có thể throw `OverBakingException`, một subclass của `BakingException`.

Nhiều người thường nghĩ rằng họ được phép throw bất kỳ checked exception nào mình muốn trong một method bị override, đặc biệt khi superclass không khai báo exception nào. Nhưng không phải vậy. Một lần nữa, vấn đề nằm ở contract mà method superclass đã định nghĩa. Subclass không thể đột nhiên đưa thêm những checked exception mới mà caller không hề mong đợi phải xử lý.

**Quy tắc #4: Covariant Return Types**  
Đây là ngoại lệ duy nhất của quy tắc về method signature. Một method bị override được phép có covariant return type. Nghĩa là return type có thể là một subclass của return type được khai báo trong method superclass. Tuy nhiên, nó không có toàn quyền trả về bất cứ thứ gì chỉ có quan hệ lỏng lẻo.

Ví dụ, nếu method superclass trả về `Number`, subclass có thể trả về `Integer`, vì `Integer` là subclass của `Number`. Tuy nhiên, nó không thể trả về `String`, bất kể mối quan hệ lỏng lẻo mà bạn có thể hình dung với `Number` ban đầu. Các return type cần có quan hệ phân cấp trực tiếp đó.

Xét ví dụ sau để minh họa quy tắc này:

```java
class Cookie {
    // Một method trong superclass trả về một instance của Cookie
    public Cookie getCookie() {
        return new Cookie();
    }
}

class ChocolateChipCookie extends Cookie {
    // Một overriding method với covariant return type
    // Nó trả về ChocolateChipCookie, một subclass của Cookie
    @Override
    public ChocolateChipCookie getCookie() {
        return new ChocolateChipCookie();
    }
}
```

Trong ví dụ này:
- Class `Cookie` có method `getCookie` trả về một instance của `Cookie`.

- Class `ChocolateChipCookie` kế thừa `Cookie` và override method `getCookie`. Return type của method bị override là `ChocolateChipCookie`, một subclass của `Cookie`. Sự thay đổi return type này là một ví dụ của việc dùng covariant return type.

- Khi `getCookie` được gọi trên một instance của `ChocolateChipCookie`, nó trả về một instance của `ChocolateChipCookie`, minh họa method bị override với covariant return type đang hoạt động.

Được rồi.

Bạn có để ý thấy annotation `@Override` trong tất cả các ví dụ này không?

Annotation `@Override` đánh dấu rõ ràng những method được dự định là override một method của superclass. Nhưng dùng nó để làm gì? Chỉ để cho rõ ràng, hay nó có mục đích thực sự?

Dù đúng là `@Override` có thể làm code của bạn dễ đọc hơn nhờ chỉ rõ những method bị override, nó còn mang lại một lớp bảo vệ chống lại các lỗi vô ý. Xét tình huống sau:

```java
class Cookie {
    public String recipe() {
        return "Default cookie recipe";
    }
}

class ChocolateChipCookie extends Cookie {
    @Override
    public String recipes() { // Ối, gõ nhầm tên method!
        return "Chocolate chip cookie recipe";
    }
}
```

Trong trường hợp này, subclass định override `recipe` nhưng vô tình gõ sai tên thành `recipes`. Nếu không có annotation `@Override`, đoạn code này vẫn compile bình thường. Subclass sẽ chỉ đơn giản có hai method riêng biệt: `recipe` được kế thừa và `recipes` mới.

Nhưng với `@Override`, compiler sẽ phát hiện lỗi và báo lỗi, chỉ ra rằng `recipes` không override bất kỳ method nào. Annotation này buộc compiler xác minh rằng method thực sự override một method của superclass, mang lại thêm một lớp an toàn.

Giờ thì điều gì xảy ra nếu bạn khai báo lại một private method của superclass trong subclass? Đó có được coi là overriding không? Câu trả lời là không. Private method hoàn toàn không được kế thừa, nên không có gì để override cả.

Nếu bạn khai báo lại một private method trong subclass, nó thực chất là một method hoàn toàn tách biệt, chỉ tình cờ có cùng tên. Nó không tương tác với method của superclass theo bất kỳ cách nào. Ví dụ:

```java
class Cookie {
    private String recipe() {
        return "Default cookie recipe";
    }
}

class ChocolateChipCookie extends Cookie {
    private String recipe() {
        return "Chocolate chip cookie recipe";
    }
}
```

Trong trường hợp này, `Cookie` và `ChocolateChipCookie` mỗi class có `recipe` riêng của mình. Gọi `recipe` trên một instance `ChocolateChipCookie` sẽ luôn gọi phiên bản của subclass, không bao giờ gọi phiên bản của superclass.

Một nguồn nhầm lẫn khác là sự khác nhau giữa hiding và overriding đối với static method. Khi bạn khai báo lại một method `static` trong subclass, đó được gọi là hiding chứ không phải overriding. Method của subclass che khuất method của superclass nhưng không thực sự override nó.

Khác biệt then chốt là overriding là khái niệm ở runtime, còn hiding là khái niệm ở compile-time. Với overriding, method cụ thể được gọi do actual object type quyết định tại runtime. Nhưng với hiding, method được gọi do reference type quyết định tại compile-time.

Xét ví dụ sau để minh họa điều này:

```java
class Cookie {
    public static String bake() {
        return "Cookie is baked";
    }
}

class ChocolateChipCookie extends Cookie {
    public static String bake() {
        return "Chocolate chip cookie is baked";
    }
}
```

Giờ xét đoạn code sau:

```java
Cookie obj1 = new Cookie();
System.out.println(obj1.bake());  // Output: "Cookie is baked"

ChocolateChipCookie obj2 = new ChocolateChipCookie();
System.out.println(obj2.bake());  // Output: "Chocolate chip cookie is baked"

Cookie obj3 = new ChocolateChipCookie();
System.out.println(obj3.bake());  // Output: "Cookie is baked"
```

Ở trường hợp cuối, dù `obj3` thực chất là một instance `ChocolateChipCookie` tại runtime, reference type của nó là `Cookie`. Vì vậy nó gọi method `Cookie` bị hidden, chứ không gọi method `ChocolateChipCookie` bị override.

Tương tự static method, variable cũng có thể bị hidden trong subclass. Nếu subclass khai báo một variable cùng tên với variable trong superclass, nó che khuất variable của superclass trong scope của subclass.

Xét ví dụ sau:

```java
class Cookie {
    protected int size = 10;
}

class ChocolateChipCookie extends Cookie {
    private int size = 20;
}
```

Trong trường hợp này, variable `size` trong `ChocolateChipCookie` che khuất variable `size` của `Cookie`. Mọi tham chiếu đến `size` bên trong `ChocolateChipCookie` sẽ truy cập variable của subclass, không phải của superclass.

Nhưng đây là phần khó nhằn. Variable bị hidden của superclass không biến mất. Nó vẫn ở đó và có thể được truy cập thông qua một reference của superclass. Xét đoạn code sau:

```java
Cookie cookie = new ChocolateChipCookie();
System.out.println(cookie.size);  // Output: 10
```

Dù `cookie` thực chất là một instance `ChocolateChipCookie`, variable này được khai báo với type `Cookie`. Vì vậy nó truy cập variable `Cookie` bị hidden, không phải variable của `ChocolateChipCookie`.

Điều này có thể dẫn đến rất nhiều nhầm lẫn và những bug tinh vi. Nói chung, tốt nhất là tránh hiding variable hoàn toàn. Nếu bạn cần override một variable của superclass, hãy cân nhắc dùng method getter/setter thay thế, vì nó có thể được override đúng cách.

Cuối cùng (xin phép chơi chữ với từ `final`), hãy nói về keyword `final`. Khi áp dụng cho một method, `final` ngăn method đó bị override trong subclass. Nó khóa method lại, đảm bảo implementation của method không đổi trong suốt hệ thống phân cấp.

Một hiểu lầm phổ biến là method `final` hoàn toàn không thể được truy cập bởi subclass. Điều đó không đúng. Subclass vẫn có thể gọi và dùng method `final`; chỉ là chúng không thể override chúng mà thôi.

Ví dụ:

```java
class Cookie {
    public final void bake(int temp) {
        System.out.println("Baking at " + temp);
    }
}

class ChocolateChipCookie extends Cookie {
    // Cố gắng override bake() sẽ gây ra compile-time error
    // @Override
    // public void bake(int temp) { ... }
    
    public void extras() {
        bake(350);  // Gọi method final bake() được phép
    }
}
```

Method `bake()` trong `Cookie` là `final`, nên `ChocolateChipCookie` không thể override nó. Nhưng nó vẫn có thể gọi `bake()` bất cứ khi nào cần.

Vậy khi nào bạn nên dùng method `final`? Chỉ khi bạn có lý do quan trọng để ngăn việc override. Lạm dụng `final` có thể khiến code của bạn cứng nhắc và khó mở rộng. Trong hầu hết trường hợp, tốt hơn là để method cho phép override, vì điều đó thúc đẩy tính linh hoạt và khả năng tái sử dụng.

### Truy cập Java Object {#accessing-java-objects}
Ở chương trước, bạn đã biết rằng khi khai báo một field hay variable, reference type là một chuyện còn object type là chuyện khác.

Dựa trên điều đó, có ba cách chính để truy cập một object trong Java:
1. Dùng một reference có cùng type với object

2. Dùng một reference là superclass của type của object 

3. Dùng một reference định nghĩa một interface mà class của object implement hoặc kế thừa

Hãy cùng đi sâu vào từng cách một.

**Dùng Reference cùng Type với Object.**

Cách đơn giản nhất để truy cập một object là dùng một reference variable khớp chính xác với type của object.

Xét class sau:
```java
class Dog {    
    public void bark() {
        System.out.println("Woof!");
    }
}
```

Và đoạn code sau:
```java
Dog myDog = new Dog();
myDog.bark(); // Có thể truy cập tất cả public method của Dog
```

Ở đây, `myDog` là một reference variable có type `Dog`, và nó đang tham chiếu đến một object `Dog`. Với thiết lập này, chúng ta có thể truy cập bất kỳ method hay variable `public` nào được định nghĩa trong class `Dog` trực tiếp thông qua reference `myDog`.

Nếu bạn thắc mắc liệu polymorphism có xảy ra khi reference type và object type giống nhau không, câu trả lời là có. Ngay cả khi type khớp nhau, polymorphism vẫn hoạt động ngầm bên dưới. Reference type quyết định những method bạn có thể gọi, nhưng actual object type quyết định implementation nào của những method đó được dùng tại runtime.

**Dùng Reference là Superclass của Object.**

Mọi thứ trở nên thú vị hơn khi chúng ta đưa inheritance vào. Trong Java, hoàn toàn hợp lệ khi có một reference variable với type là superclass của actual object type.

Xét class này và subclass của nó:
```java
class Animal {
    public void eat() {
        System.out.println("Animal is eating.");
    }
}

class Dog extends Animal {
    public void eat() {
        System.out.println("Dog is eating.");
    }
    
    public void bark() {
        System.out.println("Woof!");
    }
}
```

Chúng ta có thể viết như sau:

```java
Animal myAnimal = new Dog();
```

Ở đây, chúng ta có một reference type `Animal` tham chiếu đến một object `Dog`. Vì `Dog` kế thừa `Animal`, điều này được cho phép. Nhưng điều này có ý nghĩa gì đối với việc truy cập các chức năng của object?

Khi bạn có một reference của superclass trỏ đến object của subclass, bạn có thể truy cập mọi method được định nghĩa trong superclass, nhưng không truy cập được những method riêng của subclass. Vậy trong ví dụ trên, chúng ta có thể gọi `myAnimal.eat()` vì `eat()` được định nghĩa trong `Animal`, nhưng không thể gọi `myAnimal.bark()` vì `bark()` chỉ được định nghĩa trong `Dog`. Reference type giới hạn bạn trong những method mà type đó định nghĩa. Tuy nhiên, Java cho chúng ta một cách để vượt qua điều này: casting.

Nếu bạn chắc chắn reference của superclass đang trỏ đến một object cụ thể của subclass, bạn có thể cast reference đó sang type subclass rồi gọi các method của subclass:

```java
Dog myDog = (Dog) myAnimal; // Casting từ Animal sang Dog
myDog.bark(); // Giờ chúng ta có thể gọi các method riêng của Dog
```

Casting thực chất là nói rằng: "Tôi biết trông nó có vẻ là một `Animal`, nhưng tin tôi đi, nó thực sự là một `Dog`." Tất nhiên, bạn cần cẩn thận, nếu bạn cố cast sang sai subclass, bạn sẽ nhận `ClassCastException` tại runtime.

Chúng ta sẽ tiếp tục tìm hiểu về casting ở phần tiếp theo, nhưng tóm lại, reference của superclass mang lại sự linh hoạt (bạn có thể dùng `Dog` ở bất cứ đâu cần `Animal`) nhưng hạn chế truy cập trực tiếp vào những chức năng riêng của subclass. Đây là một khía cạnh then chốt của polymorphism trong Java.

**Dùng Reference định nghĩa Interface mà Object implement.**

Cách thứ ba để truy cập một object trong Java là thông qua interface reference. Nếu một class implement một interface, bạn có thể tham chiếu đến instance của class đó bằng một reference variable có type là interface đó.

Xét interface này và các implementation của nó:
```java
interface Pet {
    void play();
}

class Dog implements Pet {
    public void play() {
        System.out.println("Dog is playing!");
    }
    
    public void bark() {
        System.out.println("Woof!");
    }
}

class Cat implements Pet {
    public void play() {
        System.out.println("Cat is playing!");
    }
    
    public void meow() {
        System.out.println("Meow!");
    }
}
```

Bằng cách này, chúng ta có thể viết như sau:

```java
Pet myPet = new Dog();
```

Trong ví dụ này, `Dog` implement interface `Pet`, nên chúng ta có thể tạo một reference `Pet` và trỏ nó đến một object `Dog`.

Giờ bạn có thể nghĩ rằng, tạo một interface reference đến một object có nghĩa là tôi chỉ có thể dùng những method được định nghĩa trong interface đó? Câu trả lời là đúng. Khi bạn có một interface reference, bạn chỉ có thể gọi trực tiếp những method được định nghĩa trong interface đó, kể cả khi actual object có sẵn những method khác.

```java
myPet.play(); // Hợp lệ, play() được định nghĩa trong Pet
myPet.bark(); // Không hợp lệ, bark() không thuộc Pet
```

Điều này nghe có vẻ hạn chế, nhưng thực ra lại là một tính năng mạnh mẽ. Bằng cách lập trình hướng đến interface, bạn có thể viết code linh hoạt và dễ bảo trì hơn. Bạn có thể thay đổi actual object type (ví dụ từ `Dog` sang `Cat`) mà không cần sửa bất kỳ code nào dùng interface reference đó:
```java
Pet myPet = new Dog();
myPet.play(); // Output: Dog is playing!
        
myPet = new Cat();
myPet.play(); // Output: Cat is playing!
```

Điểm mấu chốt trong ví dụ này là reference `myPet` không quan tâm nó đang làm việc với `Dog` hay `Cat`. Nó chỉ biết mình đang làm việc với một `Pet` nào đó. Chúng ta có thể đổi actual object type từ `Dog` sang `Cat` mà method `play` vẫn hoạt động không cần thay đổi gì.

Nhưng nếu bạn cần truy cập những method riêng của actual object type thì sao? Cũng như với reference của superclass, bạn có thể dùng casting:

```java
Dog myDog = (Dog) myPet; // Casting từ Pet sang Dog
myDog.bark(); // Giờ chúng ta có thể gọi các method riêng của Dog
```

Một lần nữa, bạn cần chắc chắn rằng interface reference của mình thực sự đang trỏ đến object `Dog` trước khi thực hiện cast này, nếu không bạn sẽ nhận runtime exception.

Và hãy nhớ, interface không có instance, bạn không thể tạo object với type là interface trực tiếp. Tuy nhiên, bất kỳ object nào của class implement interface đó đều có thể được tham chiếu bằng type interface. Theo nghĩa đó, object *là một* dạng của interface type.

Cũng cần nhớ rằng một class có thể implement nhiều interface. Nếu một class implement nhiều interface, bạn có thể dùng reference thuộc bất kỳ interface type nào trong số đó để tham chiếu đến instance của class:

```java
interface Trainable {
    void doTrick();
}

class Dog implements Pet, Trainable {
    // Triển khai các method từ cả hai interface
}

Pet myPet = new Dog();
Trainable myStudent = (Trainable) myPet;
```

Trong ví dụ này, một object `Dog` duy nhất có thể được tham chiếu với cả `Pet` và `Trainable`, vì `Dog` implement cả hai interface.

Như vậy, interface reference mang lại cách viết code trừu tượng và linh hoạt hơn. Chúng cho phép bạn tập trung vào một tập hành vi cụ thể mà object có thể thực hiện, bất kể actual class type của nó là gì. Đây là một nguyên lý nền tảng của thiết kế hướng đối tượng.

Một lưu ý cuối cùng, hãy nhớ rằng interface không thuộc hệ thống phân cấp inheritance của object. Chúng là một cấu trúc riêng. Vì vậy, dù một object `Dog` có thể được tham chiếu như `Pet`, reference `Pet` không phải là superclass của `Dog`. Đó là một kiểu quan hệ khác.

### Type Casting {#type-casting}
Để hiểu type casting, bạn có thể hình dung các variable như những diễn viên. Mỗi variable có một vai diễn cụ thể, được quyết định bởi data type của nó. Nhưng đôi khi, cũng như trong một bộ phim, một variable cần tạm thời nhận một vai mới để phù hợp với nhu cầu của một cảnh cụ thể trong code. Đó là lúc type casting xuất hiện.

Với primitive type, type casting cho phép bạn gán giá trị của một primitive data type cho một type khác. Với object, nó cho phép bạn xử lý object của class này như object của class khác, miễn là giữa hai class có quan hệ inheritance.

Vậy, cast một object có làm thay đổi type thực sự của nó không? Không hẳn. Khi bạn cast một object, bạn không thay đổi type bên dưới của nó, bạn chỉ tạm thời xử lý nó như một type khác trong một ngữ cảnh cụ thể. Nó giống như một diễn viên mặc trang phục cho một cảnh phim. Bên trong, họ vẫn là chính mình, nhưng họ đang đóng một vai khác trong khoảnh khắc đó. Khi cảnh quay kết thúc, variable quay trở lại type gốc của nó. Nó giống như diễn viên cởi bỏ trang phục sau khi cảnh phim hoàn tất. Họ lại trở về là chính họ.

Giờ bạn có thể thắc mắc, liệu có thể cast bất kỳ type nào sang bất kỳ type nào khác không? Suy cho cùng, tất cả cũng chỉ là dữ liệu thôi mà? Không hẳn. Java là ngôn ngữ strongly-typed, nghĩa là nó có những quy tắc nghiêm ngặt về tính tương thích của type. Bạn không thể tùy tiện cast giữa những type không liên quan, kiểu như cố cast một `int` sang `String`. Compiler sẽ báo lỗi nếu bạn cố làm điều gì đó như vậy.

Các quy tắc type casting trong Java như sau:

1. Cast reference từ subtype lên supertype không cần explicit cast.

2. Cast reference từ supertype xuống subtype cần explicit cast.

3. Tại runtime, một cast không hợp lệ của reference sang type không tương thích sẽ dẫn đến `ClassCastException` được throw. 

4. Compiler không cho phép cast sang những type không liên quan.

Hãy phân tích từng quy tắc một.

Quy tắc đầu tiên nói rằng cast reference từ subtype lên supertype không cần explicit cast. Đây được gọi là upcasting. Nếu bạn có một hệ thống phân cấp class trong đó class `B` kế thừa class `A`, bạn có thể gán một reference type `B` cho một variable type `A` mà không cần explicit cast:

```java
class A {}
class B extends A {}

B b = new B();
A a = b; // upcasting, không cần cast tường minh
```

Upcasting an toàn vì subclass luôn chứa tất cả các đặc điểm của superclass. Vì vậy, xử lý object của subclass như object của superclass sẽ không bao giờ gây ra vấn đề.

Quy tắc thứ hai nói rằng cast reference từ supertype xuống subtype cần explicit cast. Đây được gọi là downcasting. Nếu bạn có một variable thuộc supertype và muốn xử lý nó như subtype, bạn cần cast tường minh:

```java
A a = new B(); // upcasting
B b = (B) a; // downcasting, cần explicit cast
```

Downcasting là cần thiết khi bạn muốn truy cập những method hay variable riêng của subclass mà không có trong superclass.

Tuy nhiên, downcasting đi kèm với rủi ro. Nếu object được tham chiếu thực ra không phải là instance của subclass mà bạn đang cố cast sang thì sao? Điều này dẫn chúng ta đến quy tắc thứ ba.

Tại runtime, một cast không hợp lệ của reference sang type không tương thích sẽ dẫn đến `ClassCastException` được throw:

```java
A a = new A();
B b = (B) a; // Compile được nhưng throw ClassCastException at runtime
```

Trong ví dụ này, `a` đang tham chiếu đến một instance của class `A`, không phải class `B`. Khi chúng ta cố cast nó sang `B`, đoạn code compile không lỗi vì compiler cho phép khả năng `a` có thể đang tham chiếu đến object `B`. Nhưng tại runtime, khi cast thực sự được thực hiện, Java nhận ra `a` thực ra không phải là `B` và throw `ClassCastException`.

Đây là một điểm quan trọng: casting không biến đổi object thành một thứ gì đó khác một cách thần kỳ. Nếu bạn cố cast một object sang type không tương thích, kết quả sẽ là runtime exception. Explicit casting thực chất nói với compiler rằng: "Tin tôi đi, tôi biết mình đang làm gì." Nhưng nếu bạn sai, Java sẽ cho bạn biết ngay tại runtime.

Tuy nhiên, quy tắc thứ tư nói rằng compiler không cho phép cast sang những type không liên quan. Nếu bạn cố cast giữa hai class không cùng hệ thống phân cấp inheritance, compiler sẽ báo lỗi:

```java
class A {}
class C {}

A a = new A();
C c = (C) a; // Lỗi compile
```

Class `A` và `C` không có quan hệ inheritance, nên compiler biết rằng một object `A` không bao giờ có thể là object `C`. Nó thậm chí không cho đoạn code này compile.

Vậy nếu casting không hoạt động, đó là vấn đề ở compile-time hay runtime? Có thể là cả hai, tùy tình huống. Nếu bạn cố cast sang một type không liên quan, đó là compile-time error. Nếu bạn cố cast sang type có liên quan nhưng object thực ra không phải là instance của type đó, đó là runtime exception.

Giờ bạn có thể nghĩ rằng, chẳng phải việc casting này rất nguy hiểm sao? Chẳng phải nó về cơ bản bỏ qua hệ thống kiểm tra type của Java sao? Không hẳn. Hệ thống type của Java vẫn có hiệu lực, và compiler sẽ không để bạn làm bất cứ điều gì quá thiếu an toàn. Explicit casting là cách nói với compiler rằng bạn có thêm hiểu biết về type của một object, nhưng nó vẫn được kiểm tra tại runtime.

Dù vậy, nói chung nên tránh cast quá nhiều, đặc biệt là downcasting. Nếu bạn thấy mình downcast rất nhiều, đó có thể là dấu hiệu cho thấy hệ thống phân cấp class của bạn cần được thiết kế lại.

Vậy khi nào casting thực sự hữu ích? Upcasting rất phổ biến và là một phần quan trọng của polymorphism trong Java. Nó cho phép bạn xử lý một type cụ thể hơn như một type tổng quát hơn, điều này an toàn và thường cần thiết.

Ví dụ, giả sử bạn có một method nhận parameter type `List`. Bạn có thể truyền vào `ArrayList`, `LinkedList` hoặc bất kỳ subclass nào khác của `List`, và mọi thứ sẽ hoạt động tốt nhờ upcasting.

```java
void processNames(List<String> names) {
    // code ở đây
}

ArrayList<String> nameList = new ArrayList<>();
processNames(nameList); // upcasting từ ArrayList sang List
```

Downcasting ít phổ biến hơn và nên được dùng tiết chế hơn. Nó cần thiết khi bạn có một reference của superclass nhưng cần truy cập những method hay variable chỉ có trong subclass.

```java
class Shape {
    void draw() { /* ... */ }
}

class Circle extends Shape {
    void drawCircle() { /* ... */ }
}

Shape shape = new Circle();
shape.draw(); // OK, draw() được định nghĩa trong Shape
((Circle)shape).drawCircle(); // Downcast để truy cập drawCircle()
```

Trong trường hợp này, downcast an toàn vì chúng ta biết `shape` thực sự đang tham chiếu đến object `Circle`. 

Tóm lại, type casting trong Java cho phép bạn tạm thời xử lý một object như một type khác, có thể là superclass (upcasting) hoặc subclass (downcasting), miễn là có quan hệ inheritance. Upcasting an toàn và phổ biến, còn downcasting cần explicit cast và nên được dùng cẩn thận. Compiler kiểm tra những cast không hợp lệ sang type không liên quan, còn những cast không hợp lệ sang type có liên quan dẫn đến runtime exception. Và hãy luôn nhớ, bên dưới lớp cast, bản thân object không thay đổi, nó chỉ được nhìn qua một lăng kính khác.

Nhưng để an toàn hơn, bạn có thể dùng operator `instanceof` để kiểm tra type trước khi cast. Hãy cùng bàn về nó tiếp theo.

### Operator `instanceof` {#the-instanceof-operator}
Trong Java, operator `instanceof` được dùng để kiểm tra xem một object có phải là instance của một class cụ thể hay implement một interface cụ thể hay không. Nó trả về giá trị `boolean`: `true` nếu object là instance của class/interface đó, ngược lại là `false`.

Cú pháp sử dụng `instanceof` là:
```java
objectReference instanceof ClassName/InterfaceName  
```

Ví dụ:
```java
Object obj = "Hello";
if(obj instanceof String) {
    System.out.println("obj is a String");
}
```

Đoạn code này sẽ in ra `"obj is a String"` vì object được `obj` tham chiếu là một instance của class `String`.

Cần lưu ý rằng dùng `instanceof` không thực sự thay đổi object hay type của nó theo bất kỳ cách nào. Nó chỉ kiểm tra object với class hoặc interface được chỉ định và trả về kết quả `boolean`. `instanceof` không thể dùng với primitive type như `int` hay `double`, nó chỉ hoạt động với object reference.

Vượt qua kiểm tra `instanceof` với một class nghĩa là object là instance của chính class đó hoặc một trong các subclass của nó. Mọi object trong Java đều kế thừa từ class `Object`, nên `instanceof Object` sẽ luôn trả về `true`:
```java
String str = "abc";
if(str instanceof Object) {
    System.out.println("This will always print");
}
```

Một ngoại lệ của quy tắc này là khi reference là `null`:
```java
String str = null;
if(str instanceof String) {
    System.out.println("This will never be executed");
}
```

`instanceof` cũng có thể kiểm tra xem một object có implement một interface cụ thể hay không. Nếu một class implement một interface trực tiếp hoặc thông qua inheritance, `instanceof` sẽ trả về `true` với interface đó:
```java
interface Trainable {
    void doTrick();
}

interface Pet extends Trainable {
    void play();
}

class Dog implements Pet {
    // Implement các method từ cả hai interface
}

Pet dog = new Dog();
if(dog instanceof Pet) {
    System.out.println("A Dog is a Pet");
}
if(dog instanceof Trainable) {
    System.out.println("A Dog is a Trainable");
}
```

Cả hai câu lệnh print này đều được thực thi, vì `Dog` implement trực tiếp `Pet`, và `Pet` kế thừa `Trainable`.

Một use case phổ biến của `instanceof` là downcast một object một cách an toàn trước khi gọi một method riêng của subclass. Hãy nhớ, downcast là khi bạn cast một reference từ type superclass sang type subclass:
```java
Object obj = getSomeObject();
if(obj instanceof String) {
    String str = (String) obj;
    System.out.println(str.toUpperCase());
}
```  

Ở đây chúng ta kiểm tra `obj` có thực sự là `String` trước khi downcast và gọi method `toUpperCase()` riêng của `String`. Explicit cast `(String)` vẫn là bắt buộc dù chúng ta đã xác nhận type bằng `instanceof`. 

Tuy nhiên, chúng ta có thể dùng pattern matching cho operator `instanceof` để đơn giản hóa quá trình kiểm tra và cast type của object.

Vậy thay vì explicit cast, bạn có thể kết hợp kiểm tra type và cast trong một thao tác duy nhất bằng cú pháp sau:
```java
if (objectReference instanceof ClassName variableName) {
    // Dùng variableName ở đây, nó sẽ tự động được cast thành ClassName
}
``` 

Cú pháp này kiểm tra xem `objectReference` có phải là instance của `ClassName` không. Nếu đúng, `objectReference` được cast sang `ClassName`, và object đã cast được gán cho `variableName` trong scope của câu lệnh `if`. Nếu kiểm tra thất bại, không có exception nào được throw. Code trong block đơn giản là không được thực thi, và pattern variable vẫn không thể truy cập. Điều này loại bỏ nhu cầu explicit cast và giảm bớt code rườm rà.

Đây là ví dụ downcast trước đó được viết lại bằng pattern matching:
```java
Object obj = getSomeObject();
if(obj instanceof String str) {
    System.out.println(str.toUpperCase());
}
``` 

Trong ví dụ này, `str` là pattern variable được tự động cast sang `String` nếu `obj` là instance của `String`. Pattern variable được khởi tạo ngầm khi match thành công. Không cần thêm bất kỳ cast nào.

Pattern variable có scope giới hạn. Chúng chỉ có thể truy cập ở nơi mà việc match của chúng được đảm bảo. `str` trong ví dụ trên không khả dụng bên ngoài block `if`. Lựa chọn thiết kế này đảm bảo pattern variable chỉ được dùng trong những ngữ cảnh mà type của chúng được đảm bảo, loại bỏ một nguồn lỗi phổ biến.

Tuy nhiên, điều này không phải lúc nào cũng có nghĩa scope là block `if` nơi chúng được định nghĩa. Khi dùng pattern matching với `instanceof`, nếu điều kiện là `true`, nghĩa là object là instance của type được chỉ định, pattern variable thực sự thuộc scope và có thể truy cập trong block theo sau điều kiện. Tuy nhiên, hãy xét ví dụ này, nơi pattern matching được dùng với phép phủ định:

```java
Object obj = getSomeObject();
if (!(obj instanceof String str)) {
    // pattern variable str KHÔNG truy cập được ở đây
    return "";
}
// Nhưng vì execution chỉ chạy tới điểm này nếu str LÀ một instance của String,
// nên pattern variable str truy cập được ở đây.
return str.toUpperCase();
```

Trong ví dụ này, câu lệnh `if` kiểm tra xem `obj` có không phải là instance của `String` hay không. Nếu `obj` không phải là `String`, method trả về `false` ngay lập tức, và pattern variable `str` không thể truy cập trong block `if` vì điều kiện để nó được khởi tạo (`obj` là instance của `String`) là `false`.

Tuy nhiên, ngay sau block `if` này, việc thực thi code chỉ tiếp tục nếu `obj` thực sự là instance của `String`, nghĩa là `str` đã được match thành công và giờ có thể truy cập và sử dụng bên ngoài, nhưng ngay sau, block `if` chứa pattern matching. Đây là một tình huống đặc biệt mà luồng chương trình đảm bảo pattern variable `str` được khởi tạo và có thể dùng an toàn vì method sẽ thoát sớm nếu điều kiện là `false`.

Bạn cũng có thể dùng pattern variable theo cách này:
```java
Object obj = getSomeObject();
if(obj instanceof String str && str.length() > 3) {
    System.out.println(str.toUpperCase());
}
``` 

Bởi vì, do operator conditional-AND (`&&`) có tính short-circuiting, chương trình chỉ có thể đi đến biểu thức `str.length() > 3` nếu biểu thức `instanceof` trả về `true`.

Tuy nhiên, bạn không thể dùng operator OR (`||`):
```java
Object obj = getSomeObject();
if(obj instanceof String str || str.length() > 3) { // Lỗi
    System.out.println(str.toUpperCase());
}
``` 

Đoạn code này sẽ gây lỗi vì biểu thức `str.length() > 3` có thể được thực thi khi `obj` không phải là instance của `String`, dẫn đến việc cố truy cập `str` khi nó có thể chưa được khởi tạo.

Ngoài ra, pattern matching với `instanceof` được thiết kế cho một type tại một thời điểm. Nó đơn giản hóa quá trình kiểm tra và cast cho một type duy nhất nhưng không mở rộng cho nhiều type cùng lúc:
```java
Object obj = getSomeObject();

if (obj instanceof String str) {
    // obj là một String, dùng str ở đây
    System.out.println("String length: " + str.length());
} else if (obj instanceof Integer intVal) {
    // obj là một Integer, dùng intVal ở đây
    System.out.println("Integer value: " + intVal);
} else if (obj instanceof List<?> list) {
    // obj là một List, dùng list ở đây
    System.out.println("List size: " + list.size());
}
```

Trong ví dụ này, `obj` được kiểm tra với nhiều type: `String`, `Integer` và `List`. Tùy theo actual type của `obj`, block code tương ứng sẽ được thực thi. Trong mỗi block, object `obj` được tự động cast sang type đang được kiểm tra, và bạn có thể dùng object đã cast trực tiếp mà không cần explicit cast.

Cách tiếp cận này giữ code của bạn sạch sẽ và type-safe, cho phép viết code dễ đọc và dễ bảo trì hơn khi xử lý nhiều type khả dĩ cho một object reference duy nhất.

Nói chung, dùng `instanceof` một cách tiết chế và ưu tiên polymorphism khi có thể là thực hành tốt. Việc kiểm tra `instanceof` thường xuyên có thể là dấu hiệu của thiết kế hướng đối tượng kém. Nhưng nó có những ứng dụng hợp lý như downcast an toàn, code dùng reflection và một số phép so sánh equality.

Cuối cùng, đây là hai sự thật quan trọng khác về `instanceof`:

- Class con được coi là instance của class cha, nhưng class cha không được coi là instance của class con.

- Nó có thể kiểm tra việc implement interface, nhưng không thể phân biệt giữa implement trực tiếp trong một class và implement kế thừa từ class cha. 


## Encapsulation {#encapsulation}

### Encapsulation là gì? {#what-is-encapsulation}
Encapsulation là một trong những nguyên lý nền tảng của lập trình hướng đối tượng trong Java. Nó bao gồm việc gói dữ liệu (attribute) và các method (hành vi) thao tác trên dữ liệu đó vào trong một đơn vị duy nhất (như một class) và hạn chế truy cập vào hoạt động bên trong của class từ bên ngoài. 

Encapsulation trong Java có thể được hình dung như một chiếc máy bán hàng tự động. Cũng như bạn tương tác với máy bán hàng qua các nút bấm để chọn đồ ăn vặt hay đồ uống, mà không cần hiểu hay truy cập vào cơ chế bên trong thực sự nhả hàng, encapsulation cho phép bạn tương tác với một object thông qua các public method của nó, trong khi trạng thái bên trong và chi tiết implementation vẫn được ẩn đi và bảo vệ khỏi sự can thiệp từ bên ngoài.

Mục đích chính của encapsulation là bảo vệ dữ liệu khỏi truy cập và sửa đổi trái phép, đồng thời tách interface của một class (cách nó có thể được dùng) khỏi implementation (cách nó thực sự hoạt động bên trong). Bằng cách đóng gói trạng thái bên trong của một object, chúng ta đảm bảo nó không thể bị code bên ngoài đưa vào trạng thái không hợp lệ hay không nhất quán.

Một số lập trình viên có thể thắc mắc: "Chẳng phải cứ để mọi thứ `public` cho đơn giản quá trình code hay sao? Tại sao phải bận tâm che giấu nội bộ của class?" 

Dù cách tiếp cận này có vẻ đơn giản hơn trong ngắn hạn, nó nhanh chóng dẫn đến code cứng nhắc, dễ vỡ và khó bảo trì. Encapsulation giúp quản lý độ phức tạp bằng cách giảm sự phụ thuộc lẫn nhau giữa các phần khác nhau của chương trình. Khi một class được đóng gói tốt, những thay đổi trong implementation bên trong của nó không ảnh hưởng đến phần còn lại của codebase, cho phép bảo trì, refactor và cập nhật class dễ dàng hơn mà không gây hiệu ứng dây chuyền khắp chương trình. 

Vậy chính xác thì chúng ta implement encapsulation trong Java như thế nào? Cơ chế chính là thông qua việc dùng access modifier cho các member của class. 

Hãy nhớ, có bốn access modifier quyết định khả năng hiển thị và truy cập của class, field và method:
- `private`: Chỉ truy cập được trong cùng class.

- `default` (package-private): Truy cập được trong cùng class và từ bất kỳ class nào khác trong cùng package. 

- `protected`: Truy cập được trong cùng class, từ bất kỳ class nào khác trong cùng package, và từ subclass (kể cả ở package khác).

- `public`: Truy cập được từ bất kỳ đâu.

Bạn có thể áp dụng những modifier này cho class, attribute và method theo bảng sau:

| Access Modifier | Class/Interface | Class Attribute | Class Method | Interface Attribute | Interface Method |
|-----------------|-----------------|-----------------|--------------|---------------------|------------------|
| **public**      | ✓               | ✓               | ✓            | ✓                   | ✓                |
| **private**     |                 | ✓               | ✓            |                     |                  |
| **protected**   |                 | ✓               | ✓            |                     |                  |
| **default**     | ✓               | ✓               | ✓            | ✓                   | ✓                |

Và đây là tóm tắt các quy tắc về access modifier:

| Access Modifier | Cùng Class | Subclass (cùng Package) | Subclass (khác Package) | Class khác (cùng Package) | Class khác (khác Package) |
|-----------------|------------|-------------------------|------------------------------|------------------------------|-----------------------------------|
| **public**      | ✓          | ✓                       | ✓                            | ✓                            | ✓                                 |
| **private**     | ✓          |                         |                              |                              |                                   |
| **protected**   | ✓          | ✓                       | ✓                            | ✓                            |                                   |
| **default**     | ✓          | ✓                       |                              | ✓                            |                                   |

Để đóng gói một class, chúng ta thường:
1. Khai báo các field (instance variable) của class là `private`. Điều này ngăn truy cập trực tiếp vào field từ bên ngoài class.

2. Cung cấp các method getter `public` để lấy giá trị của field, và method setter để sửa đổi chúng nếu cần. Những method này mang lại quyền truy cập có kiểm soát vào field và cho phép thêm validation, logging hay bất kỳ logic nào khác khi field được truy cập hoặc sửa đổi.

Đây là ví dụ về class `BankAccount` được đóng gói tốt:

```java
public class BankAccount {
    private String accountNumber;
    private double balance;

    public String getAccountNumber() {
        return accountNumber;
    }

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        } else {
            throw new IllegalArgumentException("Deposit amount must be positive.");
        }
    }

    public void withdraw(double amount) {
        if (amount > balance) {
            throw new IllegalArgumentException("Insufficient funds.");
        } else if (amount < 0) {
            throw new IllegalArgumentException("Withdrawal amount must be positive.");
        } else {
            balance -= amount;
        }
    }
}
```

Và một sơ đồ để hình dung:
```
┌─────────────────────────────────────────┐
│              BankAccount                │
├─────────────────────────────────────────┤
│ - accountNumber: String                 │
│ - balance: double                       │
├─────────────────────────────────────────┤
│ + getAccountNumber(): String            │
│ + getBalance(): double                  │
│ + deposit(amount: double): void         │
│ + withdraw(amount: double): boolean     │
└─────────────────────────────────────────┘
```

Trong ví dụ này, các field `accountNumber` và `balance` được khai báo `private`, nên chúng không thể bị truy cập hay sửa đổi trực tiếp từ bên ngoài class `BankAccount`. Các method `public` là `getAccountNumber()` và `getBalance()` cho phép lấy giá trị của những field này một cách có kiểm soát, trong khi các method `deposit()` và `withdraw()` cho phép sửa đổi field `balance` có kiểm soát với logic validation được thêm vào.

Giờ bạn có thể thắc mắc: "Nếu tôi dùng getter và setter cho tất cả field của mình, điều đó có tự động nghĩa là class của tôi được đóng gói tốt không?" 

Không hẳn. Dù dùng getter và setter là cách phổ biến để đóng gói field, chỉ có những method này không đảm bảo encapsulation tốt. Encapsulation không chỉ là che giấu dữ liệu. Nó còn là việc đảm bảo trạng thái bên trong của object luôn hợp lệ và nhất quán. Getter và setter chỉ là một công cụ để đạt được điều đó.

Ví dụ, xét class `Rectangle` sau:

```java
public class Rectangle {
    private double width;
    private double height;

    public double getWidth() {
        return width;
    }

    public void setWidth(double width) {
        this.width = width;
    }

    public double getHeight() {
        return height;
    }

    public void setHeight(double height) {
        this.height = height;
    }

    public double getArea() {
        return width * height;
    }
}
```

Dù class này dùng getter và setter, nó thực sự chưa được đóng gói tốt. `width` và `height` có thể được đặt thành bất kỳ giá trị nào, kể cả số âm, điều không hợp lý với một hình chữ nhật. Cách làm tốt hơn là validate dữ liệu đầu vào trong setter:

```java
public void setWidth(double width) {
    if (width > 0) {
        this.width = width;
    } else {
        throw new IllegalArgumentException("Width must be positive.");
    }
}

public void setHeight(double height) {
    if (height > 0) {
        this.height = height;
    } else {
        throw new IllegalArgumentException("Height must be positive.");
    }
}
```

Bằng cách thêm logic validation này, chúng ta đảm bảo trạng thái bên trong của object `Rectangle` luôn hợp lệ, từ đó đạt được encapsulation tốt hơn.

Tóm lại, encapsulation là về việc quản lý độ phức tạp, bảo vệ tính toàn vẹn của dữ liệu và tách interface của class khỏi implementation. Nó đạt được chủ yếu thông qua việc dùng access modifier, với pattern phổ biến là field `private` cùng getter và setter `public`. Tuy nhiên, encapsulation tốt vượt xa việc chỉ dùng getter và setter; nó đòi hỏi thiết kế cẩn thận interface `public` của class và đảm bảo trạng thái bên trong của class luôn hợp lệ và nhất quán.

### Immutable Objects {#immutable-objects}
Trong lập trình hướng đối tượng, immutability là khả năng tạo ra những object mà state của chúng không thể bị thay đổi sau khi được tạo. 

Immutable object trong Java giống như một cuốn sách đã in: một khi nội dung được xuất bản (hay object được tạo), nó không thể bị sửa đổi. Cũng như bạn không thể thay đổi những chữ trên một trang đã in mà không tạo ra một cuốn sách mới, bạn không thể sửa đổi một immutable object mà không tạo ra một instance mới với những thay đổi mong muốn.

Vậy điều gì khiến một object trở nên immutable trong Java? Nó không đơn giản chỉ là bỏ đi các setter method. Có một vài yêu cầu chính:

1. Đánh dấu class là `final` hoặc để tất cả constructor là `private`. Điều này ngăn việc subclassing, vốn có thể tạo điều kiện cho tính mutable lẻn vào. 

2. Đánh dấu tất cả instance variable là `private` và `final`. Điều này đảm bảo state không thể bị sửa đổi trực tiếp từ bên ngoài class. Nhưng chỉ riêng điều này liệu đã đủ cho immutability chưa?

3. Không định nghĩa bất kỳ setter method nào. Mọi method làm thay đổi state, kể cả gián tiếp, đều phá vỡ immutability.

4. Không cho phép các mutable object được reference bị sửa đổi. Nếu class của bạn giữ một reference tới một mutable object (như `Date` hay `Collection`), bạn phải đảm bảo reference đó không thể được dùng để thay đổi state của object.

5. Dùng một constructor để set mọi property của object, tạo defensive copy nếu cần. Một khi immutable object đã được khởi tạo, state của nó không bao giờ có thể thay đổi. Constructor phải thiết lập các invariant.

Hãy đi sâu hơn vào từng yêu cầu này.

Việc đánh dấu class là `final` ngăn nó bị subclass. Nếu cho phép subclassing, một subclass có thể thêm mutable state hoặc override method để trở nên mutable, phá vỡ contract immutability.

```java
public final class ImmutableExample {
    // định nghĩa class ở đây
}
```

Một cách khác, chúng ta có thể để các constructor là `private` và kiểm soát việc khởi tạo thông qua factory method:

```java
public class ImmutableExample {
    private ImmutableExample() {
        // private constructor
    }
    
    public static ImmutableExample create() {
        return new ImmutableExample();
    }
}
```

Nhưng việc để một class là `final` không tự động khiến nó immutable. Ta cũng cần đảm bảo mọi field của nó là `private` và `final`:

```java
public final class ImmutableExample {
    private final int value;
    
    public ImmutableExample(int value) {
        this.value = value;
    }
    
    public int getValue() {
        return value;
    }
}
```

Bằng cách để các field là `private`, chúng ta ngăn truy cập trực tiếp từ bên ngoài class. Và bằng cách để chúng là `final`, chúng ta đảm bảo chúng chỉ có thể được set một lần duy nhất, trong constructor.

Nhưng ngay cả với các field `private final`, immutability vẫn có thể bị vi phạm nếu class có những method thay đổi state:

```java
public final class NotActuallyImmutable {
    private final int value;
    
    public NotActuallyImmutable(int value) {
        this.value = value; 
    }
    
    public void setValue(int value) {
        this.value = value; // Thay đổi state - không ổn!
    }
}
```

Để thực sự immutable, một class không được có bất kỳ setter method nào hay bất kỳ method nào khác làm thay đổi field của nó sau khi được khởi tạo.

Tuy nhiên, immutability không chỉ dừng ở state trực tiếp của object. State của một immutable object bao gồm cả state của bất kỳ object nào khác mà nó giữ reference.

Xét class sau:

```java
public final class NotImmutable {
    private final Date start;
    
    public NotImmutable(Date start) {
        this.start = start;
    }
    
    public Date getStart() {
        return start;
    }
}
```

Thoạt nhìn, nó có vẻ immutable: field start là `private` và `final`, và không có setter. Nhưng class `Date` là mutable. Ai đó có thể làm thế này:

```java
NotImmutable example = new NotImmutable(new Date());
example.getStart().setTime(0); // Thay đổi internal state của example!
```

Để khắc phục điều này, chúng ta cần tạo một defensive copy của `Date` trong constructor:

```java
public final class ActuallyImmutable {
    private final Date start;
    
    public ActuallyImmutable(Date start) {
        this.start = new Date(start.getTime()); // Defensive copy
    }
    
    public Date getStart() {
        return new Date(start.getTime()); // Defensive copy
    }
}
```

Giờ đây state của instance `ActuallyImmutable` không thể bị thay đổi thông qua reference mà nó giữ.

Nguyên lý tương tự cũng áp dụng cho collection và array: nếu một immutable class giữ reference tới một mutable collection hay array, nó phải defensive copy và không cung cấp bất kỳ cách nào để collection nội bộ bị sửa đổi.

Việc dùng constructor đúng cách cũng là yếu tố then chốt cho immutability. State của một immutable object nên được định nghĩa đầy đủ bởi các argument truyền vào constructor của nó. Và constructor phải thiết lập mọi invariant của object.

Điều này nghĩa là một immutable class không nên có no-arg constructor, vì khi đó state của nó sẽ không được định nghĩa đầy đủ khi kết thúc construction. Mọi property nên được set thông qua argument của constructor.

Đây là một ví dụ về immutable class có chứa một collection:

```java
public final class ImmutableCollection {
    private final List<String> strings;
    
    public ImmutableCollection(List<String> strings) {
        this.strings = List.copyOf(strings); // Immutable copy
    }
    
    public List<String> getStrings() {
        return strings;
    }
}
```

Bằng cách tuân theo những quy tắc này — để class và field là final, không cung cấp mutator method, defensive copy các mutable component, và set toàn bộ state trong constructor — chúng ta có thể tạo ra những immutable object thực sự trong Java.

Immutable object có nhiều lợi thế, đặc biệt trong ngữ cảnh concurrent. Vì state của chúng không bao giờ thay đổi, chúng vốn dĩ thread-safe. Chúng có thể được chia sẻ tự do giữa các thread mà không cần synchronization.

Chúng cũng đơn giản hơn để suy luận, vì bạn biết state của chúng sẽ luôn giữ nguyên. Và chúng có thể đóng vai trò là building block cho những cấu trúc thread-safe phức tạp hơn.

Tuy nhiên, immutability cũng đi kèm một số chi phí. Immutable object có thể tốn kém hơn khi tạo, vì chúng thường yêu cầu tạo defensive copy. Và nếu bạn cần thực hiện bất kỳ thay đổi nào, bạn phải tạo một instance mới, điều này có thể tốn kém với những object lớn.


## Các điểm chính {#key-points}

- Variable scope đề cập đến visibility và khả năng truy cập của một variable trong code. Bốn scope chính trong Java là local variable, method parameter, field (instance variable) và class variable (static field).

- Local variable được khai báo bên trong một method hoặc block và chỉ có thể được truy cập trong block đó. Chúng vào scope tại điểm khai báo và ra khỏi scope ở cuối block bao quanh.

- Method parameter cũng được coi là local variable, với scope bao trùm toàn bộ thân method. Chúng vào scope khi method được gọi và ra khỏi scope khi method hoàn tất.

- Field, hay instance variable, là những variable được khai báo ở cấp class. Chúng vào scope khi object được khởi tạo và vẫn trong scope chừng nào object còn trong memory.

- Class variable, hay static field, là những static variable được khai báo ở cấp class. Chúng vào scope khi class được load và vẫn trong scope cho đến khi chương trình kết thúc.

- Field tự động nhận giá trị mặc định nếu không được khởi tạo tường minh, trong khi local variable phải được khởi tạo tường minh trước khi dùng.

- Keyword `var` cho phép type inference cho local variable. Compiler suy luận type dựa trên biểu thức khởi tạo.

- Inheritance cho phép một class mới được xây dựng dựa trên một class đã tồn tại, kế thừa các attribute và method của nó. Keyword `extends` được dùng để tạo subclass.

- Abstract class không thể được khởi tạo và được thiết kế để được subclass. Chúng có thể chứa abstract method, vốn không có implementation trong abstract class và phải được các concrete subclass triển khai.

- Interface định nghĩa một contract gồm các method mà một class phải triển khai. Keyword `implements` được dùng để triển khai một interface. Một class có thể triển khai nhiều interface.

- Sealed class giới hạn những class khác có thể extends chúng. Các permitted subclass được chỉ định bằng keyword `permits`. Subclass của một sealed class phải được khai báo là `final`, `sealed` hoặc `non-sealed`.

- Keyword `this` là một reference tới instance hiện tại của một class. Nó được dùng để phân biệt giữa local variable và instance variable, để truyền instance hiện tại làm argument cho method, và để gọi một constructor khác từ bên trong một constructor.

- Keyword `super` là một reference tới parent class (superclass) của class hiện tại. Nó được dùng để truy cập các member của superclass và để gọi superclass constructor từ subclass constructor.

- Polymorphism cho phép bạn xử lý các object thuộc những subclass khác nhau như thể chúng là object của cùng một superclass.

- Method overriding là một khái niệm then chốt trong polymorphism, trong đó một subclass cung cấp implementation riêng của một method được định nghĩa trong superclass.

- Để override một method đúng cách, method trong subclass phải có cùng name, return type và parameter list như method trong superclass.

- Khi override method, bạn có thể làm access modifier thoáng hơn trong subclass, nhưng không được chặt hơn. Method bị override cũng chỉ được declare những exception giống hoặc cụ thể hơn những exception mà method của superclass declare.

- Một overridden method được phép có covariant return type, nghĩa là return type có thể là một subclass của return type được declare trong method của superclass.

- Annotation `@Override` đánh dấu tường minh những method nhằm override một superclass method và mang lại sự bảo vệ chống lại những lỗi vô ý.

- Việc khai báo lại một private method từ superclass trong một subclass không được coi là overriding. Private method không được kế thừa.

- Việc khai báo lại một static method trong một subclass được gọi là hiding, không phải overriding. Method của subclass che khuất method của superclass, nhưng thực ra không override nó.

- Variable cũng có thể bị hidden trong subclass nếu một subclass khai báo một variable cùng tên với một variable trong superclass.

- Có ba cách chính để truy cập một object trong Java: dùng một reference cùng type với object, dùng một reference là superclass của type của object, và dùng một reference định nghĩa một interface mà class của object triển khai hoặc kế thừa.

- Type casting cho phép bạn gán giá trị của một primitive data type cho một type khác hoặc xử lý một object của class này như object của class khác, miễn là có quan hệ inheritance giữa hai class.

- Cast một reference từ subtype lên supertype (upcasting) không yêu cầu cast tường minh, trong khi cast một reference từ supertype xuống subtype (downcasting) yêu cầu cast tường minh.

- Toán tử `instanceof` được dùng để kiểm tra xem một object có phải là instance của một class cụ thể hay có triển khai một interface cụ thể hay không. Nó trả về một giá trị `boolean`.

- Pattern matching cho toán tử `instanceof` cho phép bạn kết hợp type check và cast trong một thao tác duy nhất, giảm bớt boilerplate code.
