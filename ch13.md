## Giới thiệu {#introduction}

Một trong những thay đổi quan trọng nhất được giới thiệu trong Java 9 là Java Platform Module System (JPMS). Nhưng JPMS chính xác là gì, và tại sao chúng ta nên quan tâm đến nó?

Hãy bắt đầu bằng việc hiểu module là gì trong ngữ cảnh này.

Một module trong Java giống như một khu vực trong một thư viện được tổ chức tốt. Mỗi module có một nhãn rõ ràng (tên của nó) và chứa những cuốn sách cụ thể (các package Java). Tuy nhiên, bạn không thể truy cập bất kỳ cuốn sách nào mà không có thẻ thư viện (khai báo dependency) cho khu vực cụ thể đó.

Trong ví dụ này:
```java
module com.myapp.core {
    requires java.base;
    exports com.myapp.core.api;
}
```

Chúng ta đang khai báo một module tên là `com.myapp.core`. Nó requires module `java.base` (giống như có thẻ thư viện cho khu vực Java cơ bản) và exports package `com.myapp.core.api` (khiến một số cuốn sách của nó trở nên khả dụng cho các module khác).

Trong khi package nhóm các class liên quan, module đưa khái niệm này tiến xa hơn bằng cách nhóm các package liên quan và khai báo tường minh các dependency cũng như những API được expose.

Hãy xem xét những lợi ích của việc dùng JPMS:

- **Encapsulation tốt hơn:** Module cho phép bạn che giấu chi tiết triển khai hiệu quả hơn so với chỉ dùng package, giảm rủi ro vô tình sử dụng các API nội bộ.
- **Dependency rõ ràng hơn:** Module khai báo tường minh các dependency, giúp cấu trúc của hệ thống rõ ràng hơn và giúp tránh *JAR hell* với các dependency xung đột.
- **Hiệu năng tốt hơn:** JVM có thể tối ưu thời gian khởi động và mức sử dụng bộ nhớ vì nó biết chính xác đoạn code nào là cần thiết.
- **Bảo mật tốt hơn:** Bằng cách kiểm soát truy cập, bạn có thể giảm bề mặt tấn công của ứng dụng.

JPMS bao gồm:

- File `module-info.java`: Định nghĩa module của bạn, các dependency của nó và những gì nó exports.
- Keyword mới: `module`, `requires`, `exports`, `opens`, `uses` và `provides`.
- Các tool để làm việc với module: Như `jlink`, dùng để tạo runtime image tùy chỉnh.

Đây là một file `module-info.java` mẫu phức tạp hơn:

```java
module com.myapp.core {
    requires java.base;
    requires java.sql;
    
    exports com.myapp.core.api;
    exports com.myapp.core.util to com.myapp.plugin;
    
    opens com.myapp.core.model;
    
    uses com.myapp.core.spi.Plugin;
    provides com.myapp.core.spi.Logger 
        with com.myapp.core.logging.FileLogger;
}
```

Khai báo module này cho thấy:
- Nhiều module được require.
- Export một package cho tất cả các module và một package khác chỉ cho một module cụ thể.
- Open một package cho reflection.
- Dùng một service interface và provides một implementation.

Dù bạn vẫn có thể dùng classpath, bạn sẽ bỏ lỡ những lợi ích của JPMS. Classpath giống như một đống sách lớn, không được sắp xếp, còn module path giống như một thư viện được tổ chức tốt với truy cập được kiểm soát và dependency rõ ràng.

Ngay cả trong những dự án nhỏ, module vẫn có thể cải thiện encapsulation và khả năng bảo trì. Xét ví dụ nhỏ sau:

```java
// Trong module com.myapp.core
module com.myapp.core {
    exports com.myapp.core.api;
}

package com.myapp.core.api;
public interface UserService {
    User getUser(String id);
}

package com.myapp.core.internal;
class UserServiceImpl implements UserService {
    public User getUser(String id) {
        // Phần triển khai
    }
}

// Trong module com.myapp.web
module com.myapp.web {
    requires com.myapp.core;
}

package com.myapp.web;
import com.myapp.core.api.UserService;
// import com.myapp.core.internal.UserServiceImpl; // Điều này sẽ gây compile-time error

public class UserController {
    private UserService userService;
    // ...
}
```

Trong ví dụ này, module `web` chỉ có thể truy cập package `api` của module `core`, chứ không thể truy cập implementation nội bộ của nó.

Module cung cấp các tool để thực thi và thể hiện kiến trúc hệ thống của bạn ở cấp ngôn ngữ và JVM.

Hãy thử nghĩ thế này: Bạn thích một hộp lớn đầy gạch LEGO lộn xộn hay những bộ LEGO được sắp xếp gọn gàng với hướng dẫn rõ ràng? Cả hai cách đều có thể tạo nên những thứ tuyệt vời, nhưng một cách giúp quá trình suôn sẻ hơn nhiều và ít lỗi hơn.


## Các loại module {#types-of-modules}
Giờ khi đã nắm được module là gì và vì sao chúng hữu ích, hãy cùng đi sâu vào các loại module khác nhau trong JPMS. Cũng giống như không phải mọi cuốn sách trong thư viện đều giống nhau, không phải mọi module đều giống nhau. JPMS giới thiệu ba loại module: 

- Named module
- Automatic module
- Unnamed module

### Named Module {#named-modules}
Named module giống như những cuốn sách được đánh mục lục đàng hoàng trong thư viện của chúng ta, với tiêu đề rõ ràng, thông tin tác giả và một chỗ trên kệ. Theo thuật ngữ Java, một named module được định nghĩa bởi file `module-info.java` ở thư mục gốc của module.

Đây là ví dụ về nội dung của file này:

```java
module com.myapp.core {
    requires java.base;
    exports com.myapp.core.api;
}
```

File `module-info.java` này là chứng minh nhân dân của module bạn. Nó đặt tên cho module (`com.myapp.core` trong trường hợp này), liệt kê các dependency (`requires java.base`) và khai báo những phần nào của nó mà nó sẵn sàng chia sẻ với các module khác (`exports com.myapp.core.api`).

Named module là loại module mạnh mẽ và linh hoạt nhất. Chúng cho bạn toàn quyền kiểm soát các dependency của module và những gì nó expose ra thế giới bên ngoài. Nếu bạn đang bắt đầu một dự án mới hoặc refactor một dự án hiện có để dùng JPMS, named module chính là thứ bạn sẽ làm việc cùng phần lớn thời gian.

### Automatic Module {#automatic-modules}

Nhưng còn tất cả những thư viện bên thứ ba chưa được modular hóa thì sao? Đây là lúc automatic module xuất hiện. Chúng giống như những cuốn sách trong thư viện chưa có mục lục đàng hoàng, nhưng chúng ta vẫn muốn có thể mượn chúng.

Khi bạn đặt một JAR file không phải module lên module path, Java runtime tự động coi nó như một module. Module này được gọi là automatic module.

Trong ví dụ này:
```java
module com.myapp.core {
    requires java.base;
    requires commons.lang; // Đây là một automatic module
    exports com.myapp.core.api;
}
```

`commons.lang` là một automatic module. Chúng ta có thể require nó giống như require một named module, dù nó không có file `module-info.java`.

Nhưng Java xác định tên của một automatic module như thế nào? Quá trình diễn ra đại khái như sau:

1. Đầu tiên, nó tìm entry `Automatic-Module-Name` trong file `MANIFEST.MF` của JAR. Nếu có, đó chính là tên module.
2. Nếu không có, nó suy ra tên từ tên file JAR. Nó loại bỏ phần mở rộng file và số phiên bản, rồi thay các ký tự không phải chữ-số bằng dấu chấm.

Ví dụ:
- `commons-lang3-3.14.jar` trở thành automatic module `commons.lang3`
- `guava-33.2.1-jre.jar` trở thành `guava`

Bạn có thể thấy điều này trong thực tế bằng lệnh `jar`:

```
$ jar --describe-module --file=guava-28.0-jre.jar
No module descriptor found. Derived automatic module.

Automatic module name: guava
...
```

### Unnamed Module {#unnamed-modules}
Cuối cùng nhưng không kém phần quan trọng, chúng ta có unnamed module. Chúng giống như chiếc hộp đựng đồ linh tinh trong thư viện, nơi mọi tờ giấy rời và bookmark không vừa ở bất kỳ đâu khác được cất giữ.

Khi bạn chạy ứng dụng trên classpath (không phải module path), toàn bộ code không thuộc named module hay automatic module sẽ nằm trong một unnamed module lớn. Unnamed module này reads tất cả các module khác, nghĩa là nó có thể truy cập mọi package được export bởi tất cả các module khác.

Trong lệnh này:

```
java -cp app.jar:lib/* com.myapp.Main
```

`app.jar` và mọi thứ trong directory `lib` sẽ là một phần của unnamed module.

Unnamed module rất quan trọng cho khả năng tương thích ngược, cho phép code Java hiện hữu chạy mà không cần sửa đổi trên Java 9 và các phiên bản sau. Tuy nhiên, code trong unnamed module không nhận được lợi ích của strong encapsulation mà named module mang lại.

Đây là một so sánh nhanh:

| Loại module | Có module-info.java | Trên module path | Trên classpath |
|-------------|----------------------|------------------|----------------|
| Named       | Có                   | Có               | Không          |
| Automatic   | Không                | Có               | Không          |
| Unnamed     | Không                | Không            | Có             |

Hiểu rõ các loại module khác nhau này là chìa khóa để làm việc hiệu quả với JPMS. Named module cho bạn nhiều quyền kiểm soát và lợi ích nhất, automatic module giúp bạn tích hợp các thư viện không phải module, còn unnamed module đảm bảo code hiện hữu của bạn tiếp tục chạy.

Đây là một sơ đồ tóm tắt các loại module:

## Tạo một module {#creating-a-module}

Giờ khi đã khám phá các loại module, hãy tự tạo một module. Tạo một module giống như thiết lập một khu vực mới trong thư viện của bạn. Chúng ta cần quyết định cấu trúc của nó, những cuốn sách (class) nào nó sẽ chứa, và những quy tắc nào (`module-info.java`) sẽ chi phối việc sử dụng nó.

### Cấu trúc directory {#directory-structure}

Cấu trúc directory cho một module khá đơn giản, nhưng điều quan trọng là phải làm cho đúng. Đây là một bố cục điển hình:

```
mymodule/
├── src/
│   ├── module-info.java
│   ├── com/
│   │   └── mycompany/
│   │       └── mymodule/
│   │           ├── MyClass.java
│   │           └── AnotherClass.java
│   └── resources/
│       └── config.properties
```

Hãy phân tích chi tiết:

- Directory cấp cao nhất (`mymodule/`) thường được đặt theo tên module của bạn.
- Bên trong, chúng ta có một directory `src/`. Đây là nơi chứa tất cả source file của chúng ta.
- File `module-info.java` nằm ngay dưới `src/`. Điều này quan trọng, nó định nghĩa module của chúng ta.
- Cấu trúc package Java thực tế của chúng ta (`com.mycompany.mymodule`) được biểu diễn bằng các directory lồng nhau dưới `src/`.
- Resource (các file không phải Java) có thể được đặt trong một directory riêng

Cấu trúc này có thể trông quen thuộc, nó rất giống cách chúng ta tổ chức các dự án Java không phải module. Điểm khác biệt chính là sự hiện diện của file `module-info.java`.

### Các class file {#the-class-files}

Giờ hãy xem bên trong các file Java của chúng ta có gì. Đây là ví dụ về nội dung mà `MyClass.java` có thể có:

```java
package com.mycompany.mymodule;

public class MyClass {
    public void doSomething() {
        System.out.println("MyClass is doing something!");
    }
}
```

Đây chỉ là một class Java thông thường. Tuy nhiên, khai báo `package` ở đầu file rất quan trọng, vì nó quyết định vị trí của class này trong cấu trúc module của chúng ta.

Đây là `AnotherClass.java`:

```java
package com.mycompany.mymodule;

public class AnotherClass {
    private MyClass myClass = new MyClass();

    public void doSomethingElse() {
        System.out.println("AnotherClass is doing something else!");
        myClass.doSomething();
    }
}
```

Một lần nữa, đây là một class Java tiêu chuẩn. Lưu ý cách nó có thể dùng `MyClass` mà không cần import đặc biệt vì chúng cùng package.

### File `module-info.java` {#the-module-infojava-file}

File này là thứ biến tập hợp các package của chúng ta thành một module đúng nghĩa. Nó giống như danh mục thẻ cho khu vực thư viện của chúng ta, định nghĩa những gì có sẵn và những gì cần thiết.

Đây là nội dung của một file `module-info.java` cơ bản:

```java
module com.mycompany.mymodule {
    exports com.mycompany.mymodule;
    requires java.base;
}
```

Hãy phân tích chi tiết:

- `module com.mycompany.mymodule`: Dòng này khai báo tên module của chúng ta. Theo quy ước, tên này thường trùng với tên root package của chúng ta.
- `exports com.mycompany.mymodule`: Dòng này khiến package của chúng ta có thể truy cập được từ các module khác. Nếu không có nó, các class của chúng ta sẽ bị ẩn khỏi thế giới bên ngoài.
- `requires java.base`: Dòng này khai báo dependency vào module Java cơ sở. Thực ra, dòng này là tùy chọn, mọi module đều ngầm requires `java.base`.

Nhưng chúng ta có thể làm phức tạp hơn. Giả sử chúng ta muốn dùng một logging framework và provides một service:

```java
module com.mycompany.mymodule {
    exports com.mycompany.mymodule;
    requires java.base;
    requires org.apache.logging.log4j;
    
    provides com.mycompany.service.MyService 
        with com.mycompany.mymodule.MyServiceImpl;
    
    uses com.mycompany.service.AnotherService;
}
```

Ở đây, chúng ta requires module Log4j, provides một implementation của `MyService`, và khai báo rằng chúng ta sẽ uses `AnotherService` (sẽ được provides bởi một module nào đó khác).

File `module-info.java` này có phải hơi giống nhãn dinh dưỡng trên vỏ hộp thực phẩm không? Nó cho bạn biết bên trong có gì (exports), nó cần gì (requires), nó có thể làm gì cho bạn (provides), và nó dự kiến dùng gì (uses).

Một điều cần lưu ý: nếu bạn đang dùng IDE, hãy đảm bảo nó được thiết lập để làm việc với Java module. Một số IDE có thể tự động tạo file `module-info.java` khi bạn tạo một module mới, trong khi những IDE khác có thể yêu cầu bạn tạo thủ công.

Ví dụ, giả sử có một class `Main` như sau:
```java
package com.mycompany.mymodule;

public class Main {
    public static void main(String[] args) {
        System.out.println("Main class is running!");
        
        MyClass myClass = new MyClass();
        myClass.doSomething();
        
        AnotherClass anotherClass = new AnotherClass();
        anotherClass.doSomethingElse();
    }
}

```

Đây là cách bạn có thể compile và chạy module này từ command line:

```
javac -d mods/com.mycompany.mymodule 
    src/module-info.java 
    src/com/mycompany/mymodule/*.java

java --module-path mods -m com.mycompany.mymodule/com.mycompany.mymodule.Main
```

Lệnh đầu tiên compile module của chúng ta, lệnh thứ hai chạy nó. Lưu ý cách chúng ta chỉ định module path (`--module-path mods`) và main class (`-m com.mycompany.mymodule/com.mycompany.mymodule.Main`). Ngoài ra, với cả lệnh `javac` và `java`, bạn có thể dùng option ngắn hơn `-p` thay cho `--module-path`.


## Khai báo Module {#module-declaration}

Giờ khi đã thiết lập xong cấu trúc module, hãy cùng xem lại bản thân khai báo module trong file `module-info.java`.

### Export một Package {#exporting-a-package}

Keyword `exports` được dùng để làm cho các package của module chúng ta có thể truy cập được từ các module khác. Đây là một ví dụ:

```java
module com.mycompany.mymodule {
    exports com.mycompany.mymodule.api;
}
```

Trong ví dụ này, chúng ta đang cho phép các module khác sử dụng package `com.mycompany.mymodule.api`. Mọi public type trong package này giờ đây đều có thể được truy cập bởi các module khác require nó.

Nhưng nếu chúng ta muốn chọn lọc hơn thì sao? Java module cũng cho phép điều đó:

```java
module com.mycompany.mymodule {
    exports com.mycompany.mymodule.api to com.mycompany.anothermodule, com.mycompany.yetanothermodule;
}
```

Khai báo này export package, nhưng chỉ cho các module được chỉ định. Đây là một cách kiểm soát quyền truy cập vào phần nội bộ của module.

### Kiểm soát truy cập với Module {#access-control-with-modules}

Module thêm một tầng kiểm soát truy cập bổ sung bên trên các access modifier `public`, `protected`, package-private và `private` sẵn có của Java. Cách nó hoạt động như sau:

1. Public type trong các package được export thì các module khác có thể truy cập.
2. Public type trong các package không được export chỉ có thể truy cập trong nội bộ module.
3. Protected member trong các package được export có thể được truy cập trong các subclass thuộc module khác.
4. Mọi quy tắc truy cập khác (`protected`, package-private, `private`) vẫn áp dụng như bình thường.

Hãy xem điều này trong thực tế:

```java
// Trong module com.mycompany.mymodule
module com.mycompany.mymodule {
    exports com.mycompany.mymodule.api;
}

// Trong package com.mycompany.mymodule.api
public class PublicAPI {
    public void doSomething() { ... }
}

// Trong package com.mycompany.mymodule.internal
public class InternalClass {
    public void doSomethingElse() { ... }
}

// Trong một module khác
import com.mycompany.mymodule.api.PublicAPI; // Cách này hoạt động
import com.mycompany.mymodule.internal.InternalClass; // Cách này thất bại!
```

Dù `InternalClass` là public, nó vẫn không thể được truy cập từ bên ngoài module vì package của nó không được export. Giống như việc có một phòng đọc public nhưng chỉ nhân viên mới được vào vậy.

### Require một Module {#requiring-a-module}

Keyword `requires` là cách chúng ta khai báo dependency lên các module khác. Xét ví dụ sau:

```java
module com.mycompany.mymodule {
    requires java.sql;
}
```

Dòng này cho Java runtime biết rằng module của chúng ta phụ thuộc vào module `java.sql`.

Nhưng nếu chúng ta đang xây dựng dựa trên một module khác và muốn expose chức năng của nó thông qua module của mình thì sao? Đó là lúc `requires transitive` phát huy tác dụng:

```java
module com.mycompany.mymodule {
    requires transitive java.sql;
}
```

Giờ đây, bất kỳ module nào require module của chúng ta cũng sẽ tự động require `java.sql`. Giống như nói rằng "nếu bạn mượn sách từ khu vực của chúng tôi, bạn cũng sẽ nhận được thẻ thư viện cho khu vực SQL."

Điều này đặc biệt hữu ích khi bạn tạo một API được xây dựng dựa trên module khác. Người dùng của bạn không cần biết về các dependency bên dưới, họ chỉ cần require module của bạn, và mọi thứ khác tự động đi kèm.

### Open một Package {#opening-a-package}

Đôi khi, chúng ta cần cho phép truy cập reflection vào một package tại runtime, kể cả khi nó không được export. Đây là lúc keyword `opens` tỏ ra hữu dụng. Xét ví dụ sau:

```java
module com.mycompany.mymodule {
    opens com.mycompany.mymodule.internal;
}
```

Điều này cho phép truy cập reflection tới mọi type trong package tại runtime, nhưng không cho phép truy cập tại compile-time từ các module khác.

Bạn cũng có thể open một package cho các module cụ thể:

```java
module com.mycompany.mymodule {
    opens com.mycompany.mymodule.internal to com.mycompany.testmodule;
}
```

Điều này đặc biệt hữu ích cho các testing framework hoặc thư viện dependency injection cần truy cập vào phần nội bộ của module.

Nếu bạn cần open tất cả package trong module cho reflection, bạn có thể dùng keyword `open` ngay trên khai báo module:

```java
open module com.mycompany.mymodule {
    // Các khai báo module
}
```

Hệ thống module này có phải hơi giống việc thiết lập thẩm quyền bảo mật trong một thư viện tuyệt mật không? Bạn có các khu vực public (package được export), các khu vực hạn chế (package không được export), đặc quyền truy cập riêng (opens), và thậm chí cả thẩm quyền bảo mật chuyển tiếp (requires transitive). Nó mang lại cho bạn khả năng kiểm soát chi tiết ai có thể truy cập cái gì trong codebase của mình.

Đây là một ví dụ phức tạp hơn kết hợp mọi thứ lại:

```java
module com.mycompany.mymodule {
    exports com.mycompany.mymodule.api;
    exports com.mycompany.mymodule.util to com.mycompany.partnermodule;
    
    requires java.base; // Đây là ngầm định
    requires transitive com.mycompany.commonmodule;
    requires org.apache.logging.log4j;
    
    opens com.mycompany.mymodule.internal to org.junit.jupiter.api;
}
```

Module này export một package cho toàn bộ và một package khác cho một module cụ thể, require một số module (một trong đó là transitive), và open một package cho việc testing.



## Các Module tích hợp sẵn {#built-in-modules}

Sau khi đã khám phá việc tạo module và service của riêng mình, hãy cùng nhìn vào các module được tích hợp sẵn trong Java platform. Những module tích hợp sẵn này cung cấp các service và tài nguyên thiết yếu để mọi thứ khác xây dựng dựa trên đó.

### Các Module Java lõi {#core-java-modules}

Các module bắt đầu bằng `java` là những module lõi của Java SE Platform. Những module này chứa các API nền tảng mà hầu hết ứng dụng Java đều dựa vào.

Dưới đây là một số module `java` được dùng phổ biến nhất:

1. `java.base`: Đây là module nền tảng của Java SE Platform. Nó được tất cả module khác tự động require, giống như mọi khu vực của thư viện đều dựa trên các nguyên tắc tổ chức cơ bản vậy.

   ```java
   // Bạn không cần require java.base một cách tường minh
   module com.mycompany.app {
       // java.base được require một cách ngầm định
   }
   ```

2. `java.sql`: Cung cấp API để truy cập và xử lý dữ liệu được lưu trong một data source (thường là relational database) bằng ngôn ngữ lập trình Java.

   ```java
   module com.mycompany.app {
       requires java.sql;
   }
   ```

3. `java.xml`: Chứa các API để xử lý XML.

   ```java
   module com.mycompany.app {
       requires java.xml;
   }
   ```

4. `java.desktop`: Định nghĩa các API để tạo các ứng dụng desktop phong phú, bao gồm AWT và Swing.

   ```java
   module com.mycompany.app {
       requires java.desktop;
   }
   ```

5. `java.logging`: Cung cấp các class và interface của Java Logging API.

   ```java
   module com.mycompany.app {
       requires java.logging;
   }
   ```

Những module `java` này cung cấp chức năng cốt lõi mà hầu hết ứng dụng Java dựa vào. Chúng ổn định, được tài liệu hóa đầy đủ và tạo nên xương sống của hệ sinh thái Java.

### Các Module JDK {#jdk-modules}

Các module bắt đầu bằng `jdk` cũng là một phần của Java Development Kit, nhưng chúng không được xem là một phần của đặc tả Java SE Platform lõi. Chúng cung cấp các công cụ và API bổ sung hữu ích cho một số loại hệ thống nhất định nhưng không cần thiết cho mọi ứng dụng.

Dưới đây là một vài ví dụ về các module `jdk`:

1. `jdk.httpserver`: Cung cấp một API HTTP server đơn giản.

   ```java
   module com.mycompany.app {
       requires jdk.httpserver;
   }
   ```

2. `jdk.jshell`: Chứa JShell API, cho phép bạn tạo một Java shell tương tác.

   ```java
   module com.mycompany.app {
       requires jdk.jshell;
   }
   ```

3. `jdk.security.auth`: Cung cấp các implementation của các interface javax.security.auth.*.

   ```java
   module com.mycompany.app {
       requires jdk.security.auth;
   }
   ```

Điều quan trọng cần lưu ý là trong khi các module `java` được đảm bảo có mặt trong mọi implementation của Java SE, các module `jdk` có thể không có sẵn. Chúng là một phần của JDK nhưng không thuộc đặc tả Java SE. Điều này nghĩa là nếu bạn đang dùng một module `jdk`, code của bạn có thể không portable trên mọi implementation Java SE.

Đây là ví dụ về cách bạn có thể dùng cả hai loại module:

```java
module com.mycompany.app {
    requires java.base;  // Đây là ngầm định
    requires java.sql;   // Dùng cho các thao tác database
    requires java.logging;  // Dùng cho logging
    requires jdk.httpserver;  // Để tạo một HTTP server đơn giản
    
    exports com.mycompany.app.api;
}
```

Trong khai báo module này, chúng ta dùng cả module `java` lẫn `jdk`. Chúng ta dựa vào chức năng Java lõi cho các thao tác database và logging, nhưng cũng dùng HTTP server đơn giản của JDK cho một số chức năng bổ sung.



## Sử dụng Command Line {#using-the-command-line}

Dù IDE rất tuyệt cho năng suất, việc hiểu cách dùng các lệnh `javac` và `java` vẫn quan trọng. Nó giống như biết nấu một bữa ăn từ đầu thay vì chỉ hâm lại đồ ăn chế biến sẵn.

Có nhiều lý do chính đáng để học cách compile và chạy code Java từ command line:

- Hiểu được những gì đang diễn ra bên dưới.
- Khắc phục sự cố build.
- Viết build script hoặc thiết lập CI/CD pipeline.
- Làm việc trong môi trường không có IDE.

Hãy nghĩ về nó như việc học thay lốp xe. Bạn có thể không cần làm thường xuyên, nhưng khi cần, bạn sẽ mừng vì mình biết cách.

### Compile Class với `javac` {#compiling-classes-with-javac}

Hãy bắt đầu với những điều cơ bản. Đây là cách bạn compile một file Java đơn giản:

```
javac MyClass.java
```

Lệnh này compile `MyClass.java` trong default package. Nhưng còn khi bạn có package thì sao?

```
javac com/mycompany/myapp/MyClass.java
```

Lệnh này compile `MyClass.java` trong package `com.mycompany.myapp`.

Việc gõ từng tên file có thể rất mệt. May thay, bạn có thể dùng wildcard:

```
javac com/mycompany/myapp/*.java
```

Lệnh này compile tất cả file `.java` trong thư mục `com/mycompany/myapp`.

Thường thì chúng ta muốn giữ các file source tách biệt khỏi các class đã compile. Tùy chọn `-d` cho phép chúng ta chỉ định thư mục output:

```
javac -d bin com/mycompany/myapp/*.java
```

Lệnh này compile tất cả file `.java` và đặt các file `.class` kết quả vào thư mục `bin`, giữ nguyên cấu trúc package.

Khi code của chúng ta phụ thuộc vào các thư viện bên ngoài, chúng ta cần cho compiler biết nơi tìm chúng. Đó là lúc tùy chọn classpath xuất hiện:

```
javac -cp lib/dependency.jar com/mycompany/myapp/*.java
```

Lệnh này bảo compiler tìm các class trong `dependency.jar` khi compile code của chúng ta. Bạn có thể chỉ định nhiều file JAR hoặc thư mục bằng cách phân tách chúng bằng dấu hai chấm (`:`) trên các hệ thống kiểu Unix hoặc dấu chấm phẩy (`;`) trên Windows.

Nhắc đến file JAR, đây là cách bạn compile với nhiều JAR:

```
javac -cp lib/dependency1.jar:lib/dependency2.jar com/mycompany/myapp/*.java
```

Lệnh này compile code của chúng ta sử dụng các class từ cả `dependency1.jar` và `dependency2.jar`.

Khi làm việc với module, chúng ta cần chỉ định module path:

```
javac --module-path mods -d out src/module-info.java src/com/mycompany/myapp/*.java
```

Lệnh này compile module của chúng ta, tìm các dependency trong thư mục `mods` và xuất kết quả ra thư mục `out`.

### Chạy Class với `java` {#running-classes-with-java}

Sau khi đã compile một class, bạn có thể chạy nó bằng:

```
java com.mycompany.myapp.MyClass
```

Lệnh này chạy `MyClass` trong package `com.mycompany.myapp`. Lưu ý rằng chúng ta không bao gồm phần mở rộng `.class`.

Cũng giống như khi compile, chúng ta có thể cần chỉ định classpath khi chạy code:

```
java -cp bin:lib/dependency.jar com.mycompany.myapp.MyClass
```

Lệnh này chạy `MyClass`, tìm các class trong cả thư mục `bin` và `dependency.jar`.

Để chạy một ứng dụng dạng module, chúng ta dùng các tùy chọn `--module-path` và `-m`:

```
java --module-path out:mods -m com.mycompany.myapp/com.mycompany.myapp.MyClass
```

Lệnh này chạy `MyClass` từ module `com.mycompany.myapp`, tìm các module trong thư mục `out` và `mods`.

### Đóng gói với `jar` {#packaging-with-jar}

Thường thì bạn sẽ muốn đóng gói ứng dụng của mình thành file JAR. Lệnh `jar` giúp bạn làm điều này:

```
jar -cvf myapp.jar -C bin .
```

Hãy phân tích lệnh này:
- `-c` hoặc `--create`: Tạo một archive mới
- `-v` hoặc `--verbose`: Tạo output chi tiết (verbose)
- `-f` hoặc `--file`: Chỉ định tên file archive
- `-C bin`: Chuyển đến thư mục `bin` trước khi thêm file
- `.`: Thêm tất cả file trong thư mục hiện tại (lúc này là `bin`)

Với một ứng dụng dạng module, bạn có thể đóng gói module của mình thành một modular JAR:

```
jar --create --file mods/com.mycompany.myapp.jar --main-class com.mycompany.myapp.MyClass -C out .
```

Lệnh này tạo một file modular JAR, tùy chọn chỉ định `MyClass` làm main class.

Đây là một ví dụ phức tạp hơn kết hợp tất cả lại:

```bash
# Compile the module
javac --module-path mods -d out \
    src/module-info.java \
    src/com/mycompany/myapp/*.java

# Package the module
jar --create --file mods/com.mycompany.myapp.jar \
    --main-class com.mycompany.myapp.MyClass \
    -C out .

# Run the module
java --module-path mods \
    -m com.mycompany.myapp/com.mycompany.myapp.MyClass
```

Chuỗi lệnh này compile module, đóng gói nó thành JAR, rồi chạy nó.

Theo quy ước, chúng ta lưu các module đã compile trong thư mục `mods`. Khi dùng `--module-path mods` trong các lệnh Java, chúng ta đang bảo Java tìm các module trong thư mục `mods` này.


## Nhiều Module {#multiple-modules}
Cho đến nay, chúng ta đã làm việc với một module đơn, giống như việc sắp xếp một giá sách đơn lẻ trong thư viện của mình. Nhưng các ứng dụng thực tế thường cần nhiều module phối hợp với nhau, giống như việc tổ chức cả một thư viện với nhiều khu vực vậy.

### Thiết kế một ứng dụng đa Module {#designing-a-multi-module-application}

Thiết kế một ứng dụng đa module giống như lập kế hoạch bố trí một thư viện lớn. Bạn cần suy nghĩ về cách các khu vực khác nhau (module) sẽ tương tác với nhau, chúng sẽ chia sẻ những tài nguyên gì, và tổ chức chúng như thế nào để dễ điều hướng và bảo trì.

Đây là một ví dụ đơn giản về cấu trúc ứng dụng đa module:

```
myapp/
├── core/
│   └── src/
│       ├── main/
│       │   └── java/
│       │       ├── module-info.java
│       │       └── com/mycompany/core/
│       └── test/
├── api/
│   └── src/
│       ├── main/
│       │   └── java/
│       │       ├── module-info.java
│       │       └── com/mycompany/api/
│       └── test/
└── app/
    └── src/
        ├── main/
        │   └── java/
        │       ├── module-info.java
        │       └── com/mycompany/app/
        └── test/
```

Trong cấu trúc này:
- `core` chứa chức năng cốt lõi và domain logic
- `api` định nghĩa các public interface cho ứng dụng của bạn
- `app` là ứng dụng chính kết nối mọi thứ lại với nhau

Khi làm việc với nhiều module, điều quan trọng là hiểu rõ các dependency giữa chúng.

Hãy xem cách chúng ta có thể định nghĩa các dependency cho ví dụ của mình:

```java
// core/src/main/java/module-info.java
module com.mycompany.core {
    exports com.mycompany.core;
}

// api/src/main/java/module-info.java
module com.mycompany.api {
    requires com.mycompany.core;
    exports com.mycompany.api;
}

// app/src/main/java/module-info.java
module com.mycompany.app {
    requires com.mycompany.core;
    requires com.mycompany.api;
}
```

Trong thiết lập này, cả `api` và `app` đều phụ thuộc vào `core`, và `app` cũng phụ thuộc vào `api`. Điều này tạo ra một hệ thống phân cấp dependency ảnh hưởng đến cách bạn phát triển và bảo trì ứng dụng:

- Thay đổi trong `core` có thể ảnh hưởng đến cả `api` và `app`.
- Thay đổi trong `api` có thể ảnh hưởng đến `app`, nhưng không ảnh hưởng đến `core`.
- Thay đổi trong `app` không ảnh hưởng trực tiếp đến các module khác.

Tuy nhiên, cấu trúc dependency này giúp thực thi một kiến trúc sạch, ngăn các module cấp thấp phụ thuộc vào các module cấp cao.

Khi tổ chức code xuyên qua nhiều module, hãy nghĩ đến separation of concerns và information hiding. Mỗi module nên có một mục đích rõ ràng, tập trung, và chỉ nên expose những gì cần thiết để các module khác sử dụng.

Đây là ví dụ về cách bạn có thể tổ chức một số class:

```java
// Trong core module
public class User { ... }
public class UserService { ... }

// Trong api module
public interface UserAPI { ... }

// Trong app module
public class UserController { ... }
```

Module `core` định nghĩa các domain object và service nền tảng. Module `api` định nghĩa các public interface mà các phần khác của ứng dụng (hoặc hệ thống bên ngoài) sẽ sử dụng. Module `app` chứa logic đặc thù của ứng dụng để kết nối mọi thứ lại với nhau.

Cách tổ chức này cho phép bạn thay đổi phần nội bộ của module `core` mà không ảnh hưởng đến các client của `api`, miễn là `api` vẫn ổn định.

Dù vậy, việc quyết định mức độ chi tiết phù hợp cho các module có thể là một thử thách. Quá ít module thì bạn mất đi lợi ích của việc module hóa; quá nhiều thì bạn tạo ra sự phức tạp không cần thiết. Dưới đây là một số best practice:

1. **Single Responsibility Principle:** Mỗi module nên có một, và chỉ một, lý do để thay đổi.

2. **Encapsulation:** Module nên che giấu phần nội bộ của mình và chỉ expose những gì cần thiết.

3. **Stable Dependencies:** Module nên phụ thuộc vào những module ổn định hơn chính nó.

4. **Reusability:** Nếu một tập chức năng có thể hữu ích trong các ngữ cảnh khác, hãy cân nhắc tách nó thành một module riêng.

5. **Size:** Dù không có quy tắc cứng nhắc nào, module quá lớn sẽ trở nên cồng kềnh, trong khi module quá nhỏ có thể dẫn đến *dependency hell*. Hãy hướng tới những module mà một team nhỏ có thể hiểu và bảo trì một cách hợp lý.

Đây là ví dụ về việc refactor cấu trúc trước đó của chúng ta, sử dụng một cách tiếp cận khác để cải thiện độ chi tiết:

```
myapp/
├── core/
│   ├── domain/
│   └── services/
├── api/
│   ├── internal/
│   └── public/
├── infrastructure/
│   ├── persistence/
│   └── messaging/
└── app/
    ├── web/
    └── cli/
```

Trong cấu trúc đã refactor này:
- Chúng ta đã tách `core` thành `domain` và `services` để tách biệt các entity khỏi business logic.
- `api` được chia thành `internal` (để dùng trong nội bộ ứng dụng) và `public` (cho các consumer bên ngoài).
- Chúng ta đã thêm module `infrastructure` để xử lý các mối quan tâm xuyên suốt (cross-cutting concerns).
- `app` được tách thành `web` và `cli` cho các giao diện người dùng khác nhau.

Độ chi tiết này cho phép có những module tập trung hơn, mỗi module có trách nhiệm rõ ràng, mà vẫn duy trì được một cấu trúc tổng thể dễ quản lý.

### Giao tiếp giữa các Module {#inter-module-communication}

Khi làm việc với nhiều module, giao tiếp giữa chúng trở nên quan trọng. Trong Java, giao tiếp giữa các module thường diễn ra thông qua các API được định nghĩa rõ ràng.

Đây là cách bạn có thể thiết lập điều này:

```java
// Trong api module
module com.mycompany.api {
    exports com.mycompany.api;
}

public interface UserService {
    User getUser(String id);
    void updateUser(User user);
}

// Trong core module
module com.mycompany.core {
    requires com.mycompany.api;
    provides com.mycompany.api.UserService 
        with com.mycompany.core.UserServiceImpl;
}

public class UserServiceImpl implements UserService {
    public User getUser(String id) { ... }
    public void updateUser(User user) { ... }
}

// Trong app module
module com.mycompany.app {
    requires com.mycompany.api;
    uses com.mycompany.api.UserService;
}

public class UserController {
    @Inject
    private UserService userService;

    public void handleUserUpdate(String id, UserUpdateRequest request) {
        User user = userService.getUser(id);
        // Cập nhật user dựa trên request
        userService.updateUser(user);
    }
}
```

Trong thiết lập này:
- Module `api` định nghĩa interface `UserService`.
- Module `core` cung cấp một implementation của `UserService`.
- Module `app` sử dụng `UserService` mà không cần biết về implementation của nó.

Cách tiếp cận này cho phép các module giao tiếp thông qua những interface được định nghĩa rõ ràng, thúc đẩy loose coupling và giúp việc thay đổi implementation trở nên dễ dàng hơn mà không ảnh hưởng đến các module khác.

### Giải quyết xung đột giữa các Module {#resolving-conflicts-between-modules}

Khi ứng dụng của bạn phát triển, bạn có thể gặp xung đột giữa các module. Dưới đây là một số xung đột thường gặp và cách giải quyết chúng:

1. **Version Conflicts:** Khi hai module require các version khác nhau của cùng một dependency.
   **Solution:** Dùng directive `requires` với một version cụ thể, hoặc dùng các công cụ build như Maven hay Gradle để quản lý version.

   ```
   module com.mycompany.moduleA {
       requires com.fasterxml.jackson.databind;
   }

   module com.mycompany.moduleB {
       requires com.fasterxml.jackson.databind@2.11.0;
   }
   ```

2. **Split Packages:** Khi các class trong cùng một package nằm rải rác ở nhiều module.
   **Solution:** Refactor code của bạn để đảm bảo mỗi package nằm trọn trong một module duy nhất.

3. **Naming Conflicts:** Khi hai module export cùng một tên package.
   **Solution:** Đổi tên một trong các package để đảm bảo tính duy nhất trong toàn ứng dụng.

4. **Cyclic Dependencies:** Khi các module phụ thuộc lẫn nhau theo vòng tròn.
   **Solution:** Giới thiệu một module mới mà cả hai đều có thể phụ thuộc vào, hoặc dùng pattern Service Provider Interface (SPI).

   ```java
   // Trước (cyclic dependency)
   module com.mycompany.moduleA {
       requires com.mycompany.moduleB;
   }
   module com.mycompany.moduleB {
       requires com.mycompany.moduleA;
   }

   // Sau (dùng SPI)
   module com.mycompany.api {
       exports com.mycompany.api;
   }
   module com.mycompany.moduleA {
       requires com.mycompany.api;
       provides com.mycompany.api.ServiceA with com.mycompany.moduleA.ServiceAImpl;
   }
   module com.mycompany.moduleB {
       requires com.mycompany.api;
       uses com.mycompany.api.ServiceA;
   }
   ```

Để hiểu rõ hơn về giải pháp này, hãy xem lại service chi tiết hơn.


## Tạo một Service {#creating-a-service}

Hãy đi sâu vào một trong những tính năng mạnh mẽ nhất của Java Module System: service. Service cho phép chúng ta tạo ra những ứng dụng linh hoạt, dễ mở rộng bằng cách tách rời interface khỏi implementation của chúng.

Trong ngữ cảnh Java Module System, service là một tập hợp được định nghĩa rõ ràng gồm các programming interface và class cung cấp quyền truy cập vào một chức năng hoặc tính năng cụ thể của ứng dụng. Nó giống như một bộ phận chuyên trách trong thư viện của chúng ta cung cấp một service cụ thể, chẳng hạn như phục chế sách.

Mô hình service gồm ba thành phần chính:

1. **The Service Provider Interface (SPI):** Đây là contract định nghĩa service làm gì.
2. **The Service Provider:** Đây là implementation của SPI.
3. **The Service Consumer:** Đây là code sử dụng service.

Sự tách biệt này cho phép loose coupling giữa các module. Consumer không cần biết về implementation cụ thể của service, chỉ cần biết interface mà nó sử dụng.

Hãy bắt đầu bằng việc khai báo Service Provider Interface của chúng ta. Chúng ta sẽ dùng `UserService` từ phần trước làm service mẫu:

```java
// Trong api module
module com.mycompany.api {
    exports com.mycompany.api;
}

package com.mycompany.api;

public interface UserService {
    User getUser(String id);
    void updateUser(User user);
}
```

Interface `UserService` này định nghĩa contract cho service quản lý người dùng. Bất kỳ module nào implement interface này đều có thể cung cấp chức năng quản lý người dùng.

Giờ khi đã có Service Provider Interface, chúng ta cần một cách để khám phá và load các implementation của service này. Đó là lúc Service Locator xuất hiện. Từ Java 9 trở lên, chúng ta có thể dùng class `ServiceLoader` cho mục đích này.

Đây là cách chúng ta có thể tạo một `UserServiceLocator`:

```java
// Trong app module
module com.mycompany.app {
    requires com.mycompany.api;
    uses com.mycompany.api.UserService;
}

package com.mycompany.app;

import com.mycompany.api.UserService;
import java.util.ServiceLoader;

public class UserServiceLocator {
    private static final ServiceLoader<UserService> loader = ServiceLoader.load(UserService.class);

    public static UserService getUserService() {
        return loader.findFirst().orElseThrow(() -> new IllegalStateException("No UserService implementation found"));
    }
}
```

Hãy phân tích đoạn code này:

- Chúng ta dùng method `ServiceLoader.load()` để tạo một `ServiceLoader` cho interface `UserService`.
- Method `getUserService()` dùng `findFirst()` để lấy implementation đầu tiên có sẵn của `UserService`.
- Nếu không tìm thấy implementation nào, chúng ta throw một `IllegalStateException`.

Lưu ý directive `uses` trong khai báo module. Nó cho module system biết rằng module này sẽ sử dụng service `UserService`.

Cách tiếp cận này mang lại một số lợi ích:

- **Loose coupling:** Module `app` không cần biết về implementation cụ thể của `UserService`.
- **Flexibility:** Chúng ta có thể dễ dàng thay thế các implementation khác nhau của `UserService` mà không cần thay đổi code tiêu thụ nó.
- **Extensibility:** Các module bên thứ ba có thể cung cấp implementation riêng của `UserService`, mở rộng chức năng của ứng dụng.

Đây là cách chúng ta có thể dùng nó trong `UserController`:

```java
package com.mycompany.app;

public class UserController {
    private final UserService userService;

    public UserController() {
        this.userService = UserServiceLocator.getUserService();
    }

    public void handleUserUpdate(String id, UserUpdateRequest request) {
        User user = userService.getUser(id);
        // Cập nhật user dựa trên request
        userService.updateUser(user);
    }
}
```

Trong thiết lập này, `UserController` không cần biết bất cứ điều gì về cách `UserService` được implement hay nó đến từ đâu. Nó chỉ dùng service locator để lấy một instance rồi sử dụng.

Tuy nhiên, chúng ta vẫn chưa thực sự cung cấp một implementation nào. Hãy làm điều đó ngay bây giờ.

Đầu tiên, chúng ta sẽ tạo một implementation của `UserService`:

```java
// Trong core module
package com.mycompany.core;

import com.mycompany.api.User;
import com.mycompany.api.UserService;
import java.util.HashMap;
import java.util.Map;
import java.util.UUID;

public class UserServiceImpl implements UserService {
    private final Map<String, User> users = new HashMap<>();

    @Override
    public User getUser(String id) {
        return users.get(id);
    }

    @Override
    public void updateUser(User user) {
        if (user.getId() == null) {
            user.setId(UUID.randomUUID().toString());
        }
        users.put(user.getId(), user);
    }
}
```

Giờ, chúng ta cần cho module system biết rằng implementation này cung cấp `UserService`. Chúng ta làm điều này trong file `module-info.java` của module core:

```java
module com.mycompany.core {
    requires com.mycompany.api;
    provides com.mycompany.api.UserService with com.mycompany.core.UserServiceImpl;
}
```

Mệnh đề `provides ... with` cho module system biết rằng module này cung cấp một implementation của `UserService` sử dụng class `UserServiceImpl`.

Giờ đây, khi `ServiceLoader` trong `UserServiceLocator` của chúng ta tìm kiếm các implementation của `UserService`, nó sẽ tìm thấy và dùng `UserServiceImpl` này.

Sự tách biệt giữa interface và implementation này mang lại cho chúng ta sự linh hoạt đáng kinh ngạc. Chúng ta có thể dễ dàng thay `UserServiceImpl` bằng một implementation khác mà không phải thay đổi bất kỳ code tiêu thụ nào. Có thể là một implementation dùng database thay vì map in-memory:

```java
// Trong core module
package com.mycompany.core;

import com.mycompany.api.User;
import com.mycompany.api.UserService;
import java.sql.*;
import java.util.UUID;

public class DatabaseUserServiceImpl implements UserService {
    private static final String DB_URL = "jdbc:sqlite:users.db";

    @Override
    public User getUser(String id) {
        String sql = "SELECT * FROM users WHERE id = ?";
        // ...
    }

    @Override
    public void updateUser(User user) {
        String sql = "INSERT OR REPLACE INTO users(id, username, email, active) VALUES(?,?,?,?)";
        // ...
    }
}
```

Giờ, để dùng implementation mới này, chúng ta chỉ cần thay đổi mệnh đề `provides` trong file `module-info.java`:

```java
module com.mycompany.core {
    requires com.mycompany.api;
    requires java.sql;  // Chúng ta cần cái này cho JDBC
    provides com.mycompany.api.UserService with com.mycompany.core.DatabaseUserServiceImpl;
}
```

Vậy là xong! Chúng ta vừa thay implementation in-memory bằng một implementation dựa trên database. Vẻ đẹp của cách tiếp cận này là chúng ta không phải thay đổi bất kỳ code nào trong `UserController` hay bất kỳ class tiêu thụ nào khác. Chúng vẫn làm việc với interface `UserService`, mà không hề hay biết rằng implementation bên dưới đã thay đổi.

Để thêm một implementation khác của `UserService` mà không thay thế cái hiện có, trước tiên chúng ta sẽ sửa module core để bao gồm cả hai implementation:

```java
// Trong core module
module com.mycompany.core {
    requires com.mycompany.api;
    requires java.sql;  // Chúng ta cần cái này cho JDBC

    provides com.mycompany.api.UserService with 
        com.mycompany.core.UserServiceImpl,
        com.mycompany.core.DatabaseUserServiceImpl;
}
```

Giờ đây, module system biết rằng có hai provider cho `UserService`.

Tiếp theo, chúng ta có thể cập nhật `UserServiceLocator` để trả về tất cả implementation có sẵn:

```java
// Trong app module
module com.mycompany.app {
    requires com.mycompany.api;
    uses com.mycompany.api.UserService;
}

package com.mycompany.app;

import com.mycompany.api.UserService;
import java.util.ServiceLoader;
import java.util.List;
import java.util.stream.Collectors;

public class UserServiceLocator {
    private static final ServiceLoader<UserService> loader = ServiceLoader.load(UserService.class);

    public static List<UserService> getUserServices() {
        return loader.stream()
                     .map(ServiceLoader.Provider::get)
                     .collect(Collectors.toList());
    }
}
```

Method này trả về một list gồm tất cả implementation `UserService` có sẵn.

Giờ, chúng ta có thể cập nhật `UserController` để sử dụng, chẳng hạn, tất cả service có sẵn:

```java
package com.mycompany.app;

import com.mycompany.api.User;
import com.mycompany.api.UserService;

import java.util.List;

public class UserController {
    private final List<UserService> userServices;

    public UserController() {
        this.userServices = UserServiceLocator.getUserServices();
    }

    public void handleUserUpdate(String id, UserUpdateRequest request) {
        for (UserService userService : userServices) {
            User user = userService.getUser(id);
            // Cập nhật user dựa trên request
            userService.updateUser(user);
        }
    }
}
```

Trong thiết lập này, `UserController` sẽ lặp qua tất cả implementation `UserService` có sẵn và gọi các method `getUser` và `updateUser` trên từng cái.

Cách tiếp cận hướng service này cho phép chúng ta xây dựng những ứng dụng module hóa và linh hoạt hơn. Một ứng dụng được thiết kế tốt sử dụng tính năng service của Java Module System có thể dễ dàng mở rộng và thay đổi chức năng của mình theo thời gian.


## Xem chi tiết module {#getting-module-details}

Khi application dạng module của bạn ngày càng lớn, bạn có thể cần kiểm tra các module để hiểu cấu trúc, dependency và cách chúng được resolve. Java cung cấp một vài command-line tool hỗ trợ việc này.

### Mô tả một module {#describing-a-module}

Hãy bắt đầu với việc mô tả một module. Lệnh `java` với option `--describe-module` (hoặc `-d`) cho phép chúng ta xem chi tiết về một module cụ thể:

```bash
java --describe-module java.sql
```

Output có thể trông giống như sau:

```
java.sql@18.0.3
exports java.sql
exports javax.sql
requires java.logging transitive
requires java.transaction.xa transitive
requires java.base mandated
requires java.xml transitive
uses java.sql.Driver
```

Output này cho chúng ta biết module export những package nào, require những module nào khác và use những service nào. Đây là cách nhanh để có cái nhìn tổng quan về cấu trúc và dependency của một module.

Bạn cũng có thể mô tả những module không thuộc Java runtime. Ví dụ, nếu bạn có một module `com.mycompany.core` trong một file JAR:

```bash
java --module-path mods --describe-module com.mycompany.core
```

Output có thể là:

```
com.mycompany.core@1.0
requires java.base mandated
requires com.mycompany.api
provides com.mycompany.api.UserService with com.mycompany.core.DatabaseUserServiceImpl
```

### Liệt kê các module có sẵn {#listing-available-modules}

Đôi khi, bạn có thể muốn xem tất cả module mà application của mình có thể dùng. Bạn có thể làm điều này với option `--list-modules`:

```bash
java --list-modules
```

Lệnh này sẽ liệt kê tất cả module trong Java runtime. Nếu bạn muốn bao gồm cả module của riêng mình, bạn có thể dùng:

```bash
java --module-path mods --list-modules
```

Lệnh này sẽ liệt kê cả các module của Java runtime lẫn mọi module trong directory `mods` (theo quy ước, đây là directory nơi bạn lưu các module đã compile).

### Module resolution {#module-resolution}

Khi xử lý những dependency module phức tạp, sẽ rất hữu ích nếu bạn thấy được cách module system resolve những dependency này. Bạn có thể làm điều đó với option `--show-module-resolution`:

```bash
java --show-module-resolution --module-path mods -m com.mycompany.app/com.mycompany.app.Main
```

Lệnh này sẽ hiển thị thông tin chi tiết về cách từng module được resolve khi application khởi động. Nó đặc biệt hữu ích để debug các vấn đề liên quan đến dependency module.

### Dùng lệnh `jar` {#using-the-jar-command}

Trong khi lệnh `java` rất phù hợp để mô tả module at runtime, đôi khi bạn muốn kiểm tra một module mà không cần chạy nó. Lệnh `jar` có thể giúp việc này:

```bash
jar --describe-module --file mods/com.mycompany.core.jar
```

Output có thể trông giống như sau:

```
com.mycompany.core jar:file:///.../mods/com.mycompany.core.jar/!module-info.class
requires java.base mandated
requires com.mycompany.api
provides com.mycompany.api.UserService with com.mycompany.core.DatabaseUserServiceImpl
```

Lệnh này cung cấp thông tin tương tự lệnh `java --describe-module`, nhưng nó làm việc trực tiếp trên file JAR mà không cần thiết lập module path.

Đây là một ví dụ phức tạp hơn. Giả sử chúng ta có một application nhiều module và muốn hiểu cách tất cả các phần khớp với nhau:

```bash
# List all modules
java --module-path mods --list-modules

# Describe each of our modules
java --module-path mods --describe-module com.mycompany.api
java --module-path mods --describe-module com.mycompany.core
java --module-path mods --describe-module com.mycompany.app

# Show module resolution for our main application
java --show-module-resolution --module-path mods -m com.mycompany.app/com.mycompany.app.Main

# Describe our core module JAR file
jar --describe-module --file mods/com.mycompany.core.jar
```

Bằng cách chạy những lệnh này, bạn có thể có cái nhìn toàn diện về cấu trúc module của application, từ danh sách tổng quan tất cả module, qua chi tiết từng module, cho tới quá trình resolution từng bước khi bạn chạy application.


## Phân tích dependency với `jdeps` {#analyzing-dependencies-with-jdeps}
`jdeps` là một tool cung cấp khả năng mạnh mẽ để phân tích và visualize dependency ở cả cấp module lẫn cấp class. Nó cho phép bạn xem xét mối quan hệ giữa các module, package và class, giúp bạn đưa ra những quyết định sáng suốt về cấu trúc và tổ chức của codebase.

Để bắt đầu với `jdeps`, hãy cùng khám phá cú pháp cơ bản và các option phổ biến của nó. Định dạng chung để chạy `jdeps` như sau:
```
jdeps [options] path
```

Ở đây, `path` đại diện cho vị trí của các Java class file, JAR file hoặc directory mà bạn muốn phân tích. Các `options` cho phép bạn tùy chỉnh hành vi của jdeps theo nhu cầu cụ thể của mình.

Đây là một số general option quan trọng nhất:
- `-dotoutput dir or --dot-output dir`: Chỉ định directory đích cho output DOT file. Nếu option này được chỉ định thì lệnh `jdeps` sẽ sinh một file .dot cho mỗi archive được phân tích, tên là `archive-file-name.dot`, liệt kê các dependency, cùng một file tóm tắt tên `summary.dot` liệt kê dependency giữa các archive file.
- `-s or -summary`: Chỉ in tóm tắt dependency.
- `-v or -verbose`: In tất cả dependency ở cấp class. Tương đương với `-verbose:class -filter:none`
- `-verbose:package`: In dependency ở cấp package, mặc định loại trừ các dependency trong cùng package.
- `-verbose:class`: In dependency ở cấp class, mặc định loại trừ các dependency trong cùng archive.
- `-apionly or --api-only`: Giới hạn phân tích ở API, ví dụ dependency từ signature của các member public và protected của public class, bao gồm kiểu field, kiểu tham số method, kiểu trả về và kiểu checked exception.
- `-jdkinternals or --jdk-internals`: Tìm dependency ở cấp class trong các JDK internal API. Mặc định, option này phân tích tất cả class được chỉ định trong option `--classpath` và các input file, trừ khi bạn chỉ định option `-include`. Bạn không thể dùng option này với các option `-p`, `-e` và `-s`.
- `-cp path, -classpath path, or --class-path path`: Chỉ định nơi tìm class file.
- `--module-path module-path`: Chỉ định module path.
- `--add-modules module-name[, module-name...]`: Thêm module vào root set để phân tích.
- `-q or -quiet`: Không hiển thị các dependency bị thiếu từ output `-generate-module-info`.

Đây là các option phân tích module dependency:
- `-m module-name or --module module-name`: Chỉ định root module để phân tích.
- `--generate-module-info dir`: Sinh `module-info.java` trong directory được chỉ định. Các JAR file được chỉ định sẽ được phân tích. Option này không thể dùng với các option --dot-output hoặc `--class-path`. Dùng option `--generate-open-module` cho open module.
- `--generate-open-module dir`: Sinh `module-info.java` cho các JAR file được chỉ định trong directory được chỉ định dưới dạng open module. Option này không thể dùng với các option `--dot-output` hoặc `--class-path`.
- `--check module-name [, module-name...]`: Phân tích dependence của các module được chỉ định. Nó in module descriptor, các module dependence thu được sau phân tích và graph sau transition reduction. Nó cũng nhận diện mọi qualified export không được dùng đến.
- `--list-deps`: Liệt kê các module dependence cùng tên package của các JDK internal API (nếu có tham chiếu). Option này phân tích transitively các library trên class path và module path nếu có tham chiếu. Dùng option `--no-recursive` để phân tích dependency không transitive.
- `--list-reduced-deps`: Giống `--list-deps` nhưng không liệt kê các implied reads edge từ module graph. Nếu module M1 reads M2, và M2 requires transitive trên M3, thì việc M1 reads M3 là implied và không được hiển thị trong graph.
- `--print-module-deps`: Giống --list-reduced-deps nhưng in ra danh sách module dependence phân tách bằng dấu phẩy. Output có thể được dùng bởi jlink --add-modules để tạo custom image chứa các module đó và các transitive dependence của chúng.
- `--ignore-missing-deps`: Bỏ qua các dependence bị thiếu.

Đây là các option để lọc dependency:
- `-p pkg_name, -package pkg_name, or --package pkg_name`: Tìm các dependency khớp với package name được chỉ định. Bạn có thể chỉ định option này nhiều lần cho các package khác nhau. Các option `-p` và `-e` loại trừ lẫn nhau.
- `-e regex, -regex regex, or --regex regex`: Tìm các dependency khớp với pattern được chỉ định. Các option `-p` và `-e` loại trừ lẫn nhau.
- `--require module-name`: Tìm các dependency khớp với module name đã cho (có thể được cung cấp nhiều lần). Các option `--package`, `--regex` và `--require` loại trừ lẫn nhau.
- `-f regex or -filter regex`: Lọc các dependency khớp với pattern đã cho. Nếu cung cấp nhiều lần, lần cuối cùng sẽ được chọn.
- `-filter:package`: Lọc các dependency trong cùng package. Đây là mặc định.
- `-filter:archive`: Lọc các dependency trong cùng archive.
- `-filter:module`: Lọc các dependency trong cùng module.
- `-filter:none`: Không lọc theo `-filter:package` và `-filter:archive`. Việc lọc được chỉ định qua option `-filter` vẫn được áp dụng.
- `--missing-deps`: Tìm các dependency bị thiếu. Option này không thể dùng với các option `-p`, `-e` và `-s`.

Và đây là các option để lọc các class được phân tích:
- `-include regex`: Giới hạn phân tích ở các class khớp pattern. Option này lọc danh sách class cần phân tích. Nó có thể được dùng cùng với `-p` và `-e`, những option áp dụng pattern lên các dependency.
- `-P or -profile`: Hiển thị profile chứa một package.
- `-R or --recursive`: Duyệt đệ quy tất cả run-time dependence. Option `-R` ngụ ý `-filter:none`. Nếu các option `-p`, `-e` hoặc `-f` được chỉ định, chỉ những dependency khớp mới được phân tích.
- `--no-recursive`: Không duyệt dependence một cách đệ quy.
-- `I or --inverse`: Phân tích các dependence theo những option đã cho khác, sau đó tìm tất cả artifact phụ thuộc trực tiếp và gián tiếp vào các node khớp. Điều này tương đương với nghịch đảo của phân tích compile-time view và bản in dependency summary. Option này phải được dùng với các option `--require`, `--package` hoặc `--regex`.
- `--compile-time`: Phân tích compile-time view của các transitive dependency, chẳng hạn như compile-time view của option `-R`. Phân tích các dependence theo những option được chỉ định khác. Nếu tìm thấy một dependency từ một directory, một JAR file hoặc một module thì tất cả class trong archive chứa nó sẽ được phân tích.

Một trong những use case chính của `jdeps` là phân tích module dependency. Khi chạy `jdeps` trên một module, bạn có thể nhận được báo cáo chi tiết về những module mà nó phụ thuộc cùng những package nó dùng từ mỗi module:
```
jdeps --module-path mods --add-modules com.example.myapp mymodule.jar
```

Trong ví dụ này, chúng ta chỉ định module path bằng option `--module-path`, trỏ đến directory chứa các module definition. Option `--add-modules` được dùng để chỉ định main module của application. Cuối cùng, chúng ta cung cấp đường dẫn tới JAR file đại diện cho module của mình.

`jdeps` sẽ phân tích các dependency và sinh ra một báo cáo trông giống như sau:
```
mymodule.jar -> java.base
   com.example.myapp                         -> java.io
   com.example.myapp                         -> java.lang
   com.example.myapp                         -> java.util
mymodule.jar -> java.desktop
   com.example.myapp                         -> java.awt
   com.example.myapp                         -> javax.swing
```

Báo cáo này cho thấy các dependency của `mymodule.jar` lên những module khác, chẳng hạn `java.base` và `java.desktop`. Nó cũng liệt kê những package cụ thể bên trong `mymodule.jar` phụ thuộc vào package từ các module đó.

Ngoài phân tích ở cấp module, `jdeps` còn cho phép bạn xem xét dependency ở cấp class. Khi chạy `jdeps` trên từng class file hoặc directory chứa class file, bạn có thể hiểu rõ hơn mối quan hệ giữa các class và package.

Xét ví dụ sau:
```
jdeps --verbose --class-path lib/* com/example/MyClass.class
```

Ở đây, chúng ta dùng option `--class-path` để chỉ định classpath chứa các dependency cần thiết. Cờ `--verbose` cung cấp output chi tiết hơn, hiển thị các class và member cụ thể đang được dùng.

Báo cáo dependency ở cấp class do `jdeps` sinh ra sẽ bao gồm thông tin như sau:
```
com.example.MyClass -> java.lang.Object
com.example.MyClass -> java.lang.String
com.example.MyClass -> java.util.ArrayList
com.example.MyClass -> java.util.List
com.example.MyClass -> com.example.HelperClass
```

Báo cáo này cho thấy `MyClass` phụ thuộc vào các class từ package `java.lang` và `java.util`, cũng như một class khác tên `HelperClass` từ cùng package.

`jdeps` cũng có khả năng sinh các báo cáo dependency toàn diện ở nhiều định dạng khác nhau. Bằng cách dùng option `--dot-output`, bạn có thể sinh một DOT file visualize các dependency dưới dạng graph. Biểu diễn đồ họa này cực kỳ hữu ích trong việc hiểu những cấu trúc dependency phức tạp và nhận ra các vấn đề tiềm ẩn.
```
jdeps --dot-output docs --module-path mods --add-modules com.example.myapp mymodule.jar
```

Trong ví dụ này, `jdeps` sẽ sinh một DOT file mang tên module trong directory `docs`. Sau đó bạn có thể dùng những tool như [Graphviz](https://graphviz.org) để render DOT file thành một graph trực quan.

Một tính năng hữu ích khác của `jdeps` là khả năng nhận diện việc dùng internal API. Cờ `--jdk-internals` giúp bạn phát hiện và phân tích việc dùng internal JDK API trong code của mình. Điều này quan trọng vì phụ thuộc vào internal API có thể dẫn đến vấn đề tương thích và hành vi bất ngờ khi nâng cấp lên các phiên bản Java mới hơn.
```
jdeps --jdk-internals --class-path lib/* com/example/MyClass.class
```

Nếu `MyClass` dùng bất kỳ internal JDK API nào, `jdeps` sẽ báo cáo chúng trong output, cho phép bạn thực hiện những hành động cần thiết để refactor hoặc loại bỏ dependency vào internal API.

Nếu bạn cung cấp đường dẫn tới một JAR file hoặc directory, `jdeps` sẽ phân tích đệ quy tất cả class bên trong nó và sinh một báo cáo dependency toàn diện.

Đây là một ví dụ:
```
jdeps --recursive lib/myapp.jar
```

Option `--recursive` đảm bảo rằng `jdeps` duyệt qua tất cả class và directory lồng nhau bên trong JAR file hoặc directory được chỉ định, mang lại bức tranh đầy đủ về các dependency.

`jdeps` cũng cung cấp một tính năng gọi là phân tích dependency đệ quy, cho phép bạn hiểu các transitive dependency của code mình. Bằng cách phân tích không chỉ các dependency trực tiếp mà cả dependency của những dependency đó, `jdeps` giúp bạn nhận ra những vấn đề và xung đột tiềm ẩn.

Xét ví dụ sau:
```
jdeps --recursive --module-path mods --add-modules com.example.myapp mymodule.jar
```

Với cờ `--recursive`, `jdeps` sẽ duyệt toàn bộ dependency graph, bắt đầu từ module hoặc JAR file được chỉ định. Nó sẽ sinh một báo cáo bao gồm tất cả transitive dependency, cho bạn cái nhìn toàn diện về cấu trúc dependency của project.


## Làm việc với module file bằng `jmod` {#using-module-files-with-jmod}
`jmod` là một command-line tool thao tác trên một định dạng file gọi là JMOD. JMOD file tương tự JAR file ở chỗ chúng đóng gói Java class, resource và metadata. Tuy nhiên, JMOD file được thiết kế riêng để làm việc với module system và cung cấp thêm khả năng so với JAR file truyền thống.

### Định dạng file JMOD {#the-jmod-file-format}
Định dạng file JMOD được tối ưu cho JPMS và đóng vai trò container cho nội dung module. Nó đóng gói không chỉ Java class đã compile và resource mà còn bao gồm module descriptor, native library và thông tin khác dành riêng cho module. JMOD file có phần mở rộng `.jmod` và tuân theo một cấu trúc directory cụ thể để tổ chức nội dung.

JMOD file không thay thế JAR file.

JAR (Java Archive) file là định dạng phổ biến và được dùng rộng rãi nhất để đóng gói Java class và resource. Về bản chất chúng là những file zip chứa Java class đã compile, metadata và resource. Ngoài ra, JAR file có thể được đặt trên classpath để các chương trình Java dễ dàng truy cập.

Có một số khác biệt chính giữa JAR và JMOD file:
- **Modularity:** JMOD file chủ yếu được dùng cho phát triển Java dạng module, trong khi JAR file được dùng cho cả code modular lẫn non-modular.

- **Native code:** JMOD file có thể chứa native library và executable, điều mà JAR file không thể làm được.

- **Versioning:** JMOD file hỗ trợ versioning module thông qua option `--module-version`, cho phép quản lý phiên bản tốt hơn.

- **Optimization:** JMOD file được tối ưu cho module system và mang lại hiệu năng cùng khả năng encapsulation tốt hơn so với JAR file.

- **Usage:** JAR file được dùng rộng rãi để phân phối library và application, trong khi JMOD file chủ yếu dùng để tạo và đóng gói module.

Vậy khi nào bạn nên dùng JMOD file thay vì JAR file? Dưới đây là một số hướng dẫn:
- Nếu bạn đang phát triển application Java dạng module bằng JPMS, JMOD file là định dạng được khuyến nghị để đóng gói module.

- Nếu module của bạn cần native library hoặc executable, JMOD file cung cấp cách thuận tiện để bao gồm chúng cùng với code Java.

- Nếu bạn cần tạo custom runtime image hoặc JRE (Java Runtime Environment) riêng cho application, JMOD file được dùng làm input cho tool `jlink` để tạo runtime image được tối ưu.

Tuy nhiên, nếu bạn đang phát triển application Java non-modular hoặc một library cần tương thích với các phiên bản Java cũ hơn thì JAR file vẫn là lựa chọn được ưu tiên.

Một trong những lợi thế chính của JMOD file là khả năng bao gồm native library và executable. Điều này đặc biệt hữu ích cho các module có dependency theo nền tảng hoặc cần tích hợp native code. Bằng cách đóng gói native library trong JMOD file, module có thể dễ dàng được phân phối và triển khai trên nhiều nền tảng khác nhau.

JMOD file cũng hỗ trợ versioning, cho phép module chỉ định thông tin phiên bản của mình. Điều này quan trọng để quản lý dependency và đảm bảo tương thích giữa các phiên bản module khác nhau. Module descriptor trong file `module-info.class` có thể bao gồm những annotation liên quan đến phiên bản để cung cấp metadata phiên bản.

### Các operation mode {#operation-modes}
Đây là cú pháp cơ bản của lệnh `jmod`:
```
jmod (create|extract|list|describe|hash) [options] jmod-file
```

Các operation mode chính là:
- `create`: Tạo một JMOD archive file mới.
- `extract`: Giải nén tất cả file từ JMOD archive file.
- `list`: In tên của tất cả entry.
- `describe`: In chi tiết module.
- `hash`: Xác định leaf module và ghi lại hash của những dependency trực tiếp và gián tiếp require chúng.

Đây là những option quan trọng nhất:
- `--class-path path`: Chỉ định vị trí của JAR file application hoặc directory chứa class để copy vào JMOD file kết quả.
- `--cmds path`: Chỉ định vị trí của native command để copy vào JMOD file kết quả.
- `--config path`: Chỉ định vị trí của file cấu hình người dùng có thể sửa để copy vào JMOD file kết quả.
- `--dir path`: Chỉ định vị trí nơi jmod đặt các file được giải nén từ JMOD archive được chỉ định.
- `--dry-run`: Thực hiện dry run của hash mode. Nó xác định leaf module và các module được require mà không ghi lại bất kỳ giá trị hash nào.
- `--hash-modules regex-pattern`: Xác định leaf module và ghi lại hash của những dependency trực tiếp và gián tiếp require chúng, dựa trên module graph của các module khớp với regex-pattern đã cho. Các hash được ghi vào JMOD archive file đang được tạo, hoặc một JMOD archive hay modular JAR trên module path được chỉ định bởi lệnh `jmod hash`.
- `--help or -h`: In thông báo hướng dẫn sử dụng.
- `--libs path`: Chỉ định vị trí của native library để copy vào JMOD file kết quả.
- `--main-class class-name`: Chỉ định main class cần ghi vào file `module-info.class`.
- `--module-version ersion`: Chỉ định module version cần ghi vào file `module-info.class`.
- `--module-path path or -p path`: Chỉ định module path. Option này là bắt buộc nếu bạn cũng chỉ định `--hash-modules`.
- `--target-platform platform`: Chỉ định nền tảng đích.
- `--version`: In thông tin phiên bản của lệnh `jmod`.

Dưới đây là một số ví dụ minh họa cách dùng cơ bản của từng operation mode:

1. **Create mode:**
    ```
    jmod create \
        --class-path classes \
        --main-class com.example.Main \
        --module-version 1.0 \
        --module-path lib \
        mymodule.jmod
    ```

    Lệnh này tạo một JMOD archive file mới tên `mymodule.jmod`. Nó bao gồm các class từ directory `classes`, đặt main class là `com.example.Main`, chỉ định module version là 1.0 và dùng directory `lib` làm module path.

2. **Extract mode:**
    ```
    jmod extract --dir extracted_files mymodule.jmod
    ```

    Lệnh này giải nén tất cả file từ `mymodule.jmod` vào một directory tên `extracted_files`.

3. **List mode:**
    ```
    jmod list mymodule.jmod
    ```

    Lệnh này in tên của tất cả entry trong `mymodule.jmod`.

4. **Describe mode:**
    ```
    jmod describe mymodule.jmod
    ```

    Lệnh này in chi tiết module của `mymodule.jmod`.

5. **Hash mode:**
    ```
    jmod hash --module-path lib \
        --hash-modules java.base \
        mymodule.jmod
    ```

    Lệnh này xác định leaf module và ghi lại hash của những dependency trực tiếp và gián tiếp require chúng. Nó dùng directory `lib` làm module path và xét các module khớp với pattern `java.base`.


### Best practice và hạn chế {#best-practices-and-limitations}
Khi làm việc với JMOD file, có một số best practice cần ghi nhớ:
- Dùng tên mô tả và có ý nghĩa cho JMOD file, tuân theo quy ước đặt tên cho module.

- Bao gồm file `module-info.java` trong source code của module để định nghĩa tên, dependency và package export của module.

- Tổ chức class, resource và native library của module trong các directory phù hợp bên trong JMOD file.

- Dùng option `--module-version` khi tạo JMOD file để chỉ định phiên bản module.

- Lưu JMOD file trong một cấu trúc directory riêng, tách biệt với source code và các project artifact khác.

- Dùng tool jmod để tạo, giải nén và thao tác với JMOD file khi cần.

- Khi phân phối application dạng module, hãy cân nhắc dùng `jlink` để tạo runtime image được tối ưu chỉ bao gồm những module cần thiết.

Trong khi JMOD file mang lại nhiều lợi ích cho phát triển Java dạng module, có một số hạn chế và lưu ý cần ghi nhớ:

- JMOD file gắn liền với Java Platform Module System và không tương thích ngược với các phiên bản Java cũ hơn.

- Không phải mọi Java library và framework đều đã được module hóa hoặc cung cấp JMOD file. Bạn có thể phải dựa vào JAR file truyền thống cho những dependency chưa được module hóa.

- Tooling và build system cho phát triển Java dạng module vẫn đang phát triển, và có thể cần một chút thời gian học cùng cấu hình để tận dụng đầy đủ JMOD file trong project của bạn.

- JMOD file không nhằm được dùng làm định dạng phân phối cho end-user. Chúng thường được dùng như định dạng trung gian để tạo runtime image hoặc tích hợp với build tool.

## Tạo runtime image với `jlink` {#creating-runtime-images-with-jlink}
Theo truyền thống, các application Java phụ thuộc vào Java Runtime Environment (JRE) để thực thi. JRE bao gồm rất nhiều module và library, trong đó nhiều module có thể không cần thiết cho một application cụ thể. Điều này có thể dẫn đến kích thước phân phối lớn hơn và những dependency có thể không cần thiết.

Với `jlink`, chúng ta có thể tạo những custom runtime image chỉ bao gồm các module mà application của mình cần. Những custom runtime image này khép kín và có thể được phân phối dưới dạng standalone executable. Chúng mang lại nhiều lợi ích như giảm kích thước phân phối, cải thiện thời gian khởi động và tăng cường bảo mật bằng cách giảm thiểu attack surface.

### Cú pháp và các option của `jlink` {#syntax-and-options-of-jlink}
Để tạo custom runtime image bằng `jlink`, chúng ta dùng cú pháp cơ bản sau:
```
jlink [options] --module-path <modulepath> --add-modules <modules>
```

Hãy phân tích các thành phần chính của lệnh `jlink`:
- `[options]`: Các option bổ sung để cấu hình hành vi của `jlink`, chẳng hạn compression, debugging, v.v.
- `--module-path <modulepath>`: Chỉ định module path nơi có thể tìm thấy các module cần thiết. Bao gồm các application module và mọi dependency.
- `--add-modules <modules>`: Chỉ định các module cần đưa vào runtime image. Có thể là danh sách tên module phân tách bằng dấu phẩy hoặc keyword `ALL-MODULE-PATH` để bao gồm tất cả module tìm thấy trên module path.

Một trong những mục tiêu chính của việc tạo custom runtime image là giảm thiểu kích thước và chỉ bao gồm những module cần thiết. `jlink` cung cấp các option để tạo một runtime tối giản chỉ chứa những module thiết yếu mà application cần để chạy.

Dưới đây là một số option quan trọng nhất:
- `--add-modules mod [, mod...]`: Thêm các module có tên `mod` vào default set của root module. Default set của root module là rỗng.
- `--bind-services`: Link các service provider module và dependency của chúng.
- `-c ={0|1|2} or --compress={0|1|2}`: Bật compression cho resource.
- ` --disable-plugin pluginname`: Vô hiệu hóa plug-in được chỉ định.
- `--endian {little|big}`: Chỉ định byte order của image được tạo. Giá trị mặc định là định dạng kiến trúc hệ thống của bạn.
- `-h or --help`: In thông báo hướng dẫn sử dụng.
- `--ignore-signing-information`: Ngăn chặn fatal error khi các modular JAR đã ký được link vào runtime image. Các file liên quan đến chữ ký của modular JAR đã ký không được copy vào runtime image.
- `--launcher command=module or --launcher command=module/main`: Chỉ định tên launcher command cho module hoặc tên command cho module và main class (tên module và main class phân tách bằng ký tự slash).
- `--limit-modules mod [, mod...]`: Giới hạn tập module có thể quan sát được (observable) trong transitive closure của các module có tên `mod`, cộng với main module (nếu có), cộng với bất kỳ module nào khác được chỉ định trong option `--add-modules`.
- `--list-plugins`: Liệt kê các plug-in có sẵn, mà bạn có thể truy cập qua command-line option.
- `-p or --module-path modulepath`: Chỉ định module path. Nếu option này không được chỉ định thì module path mặc định là `$JAVA_HOME/jmods`. Directory này chứa module `java.base` cùng các module chuẩn và JDK khác. Nếu option này được chỉ định nhưng module `java.base` không thể được resolve từ đó thì lệnh jlink sẽ thêm `$JAVA_HOME/jmods` vào module path.
- `--output path`: Chỉ định vị trí của runtime image được tạo.
- `--suggest-providers [name, ...]`: Gợi ý các provider triển khai những service type đã cho từ module path.
- `--version`: In thông tin phiên bản.

Để tạo một runtime tối giản, chúng ta có thể dùng lệnh sau:
```
jlink --module-path <modulepath> \
      --add-modules <modules> \
      --compress 2 \
      --strip-debug \
      --no-header-files \
      --no-man-pages \
      --output <path>
```

Trong lệnh này, chúng ta dùng một vài option để tối ưu runtime image:
- `--compress 2`: Bật compression cho runtime image được tạo, giúp giảm kích thước.
- `--strip-debug`: Loại bỏ debug information khỏi runtime image, tiếp tục giảm kích thước.
- `--no-header-files`: Loại trừ header file khỏi runtime image.
- `--no-man-pages`: Loại trừ manual page khỏi runtime image.

Bằng cách chỉ định những module cần thiết với `--add-modules` và dùng những option tối ưu này, chúng ta có thể tạo một runtime image tối giản được thiết kế riêng cho các yêu cầu cụ thể của application.

`jlink` cũng cho phép chúng ta chủ động include hoặc exclude module khỏi runtime image. Điều này cho phép kiểm soát chi tiết các module được đóng gói vào image.

Để include những module cụ thể, chúng ta có thể dùng option `--add-modules` theo sau là danh sách tên module phân tách bằng dấu phẩy. Ví dụ:
```
jlink --module-path <modulepath> \
      --add-modules module1,module2,module3 \
      --output <path>
```

Lệnh này sẽ tạo một runtime image chỉ bao gồm `module1`, `module2` và `module3`, cùng các transitive dependency của chúng.

Ngược lại, nếu muốn exclude một số module khỏi runtime image, chúng ta có thể dùng option `--exclude-modules` theo sau là danh sách tên module phân tách bằng dấu phẩy. Ví dụ:
```
jlink --module-path <modulepath> \
      --add-modules ALL-MODULE-PATH \
      --exclude-modules module4,module5 \
      --output <path>
```

Trong trường hợp này, jlink sẽ bao gồm tất cả module tìm thấy trên module path ngoại trừ `module4` và `module5`.

### Plugin {#plugins}
Plugin là những thành phần bổ sung mở rộng chức năng của tool `jlink`. Chúng cho phép developer tùy chỉnh việc tạo runtime image theo nhiều cách khác nhau, chẳng hạn tối ưu image được tạo, thêm hoặc bớt resource, và cấu hình cách image được bố trí.

Nếu bạn chạy:
```
jlink --list-plugins
```

Bạn sẽ nhận được danh sách tất cả plugin có sẵn. Ví dụ:

- `--add-options <options>`: Thêm chuỗi `<options>` được chỉ định, có thể chứa khoảng trắng, vào trước mọi option khác khi gọi virtual machine trong image kết quả.
- `--compress <compress>`: Compression dùng để nén resource. Các giá trị được chấp nhận là `zip-[0-9]`, trong đó `zip-0` không nén, và `zip-9` nén tốt nhất. Mặc định là `zip-6`.
- `--exclude-files <pattern-list>`: Chỉ định các file cần loại trừ. Ví dụ: `**.java`, `glob:/java.base/lib/client/**`
- `--exclude-jmod-section <section-name>`: Chỉ định một JMOD section cần loại trừ. Trong đó `<section-name>` là `man` hoặc `headers`.
- `--exclude-resources <pattern-list>`: Chỉ định resource cần loại trừ. Ví dụ: `**.jcov`, `glob:**/META-INF/**`
- `--include-locales <langtag>[,<langtag>]*`: Các language tag BCP 47 phân tách bằng dấu phẩy, cho phép locale matching được định nghĩa trong RFC 4647. Ví dụ: `en`, `ja`, `*-IN`
- `--strip-debug`: Loại bỏ debug information khỏi output image
- `--strip-java-debug-attributes`: Loại bỏ Java debug attribute khỏi các class trong output image
- `--strip-native-commands`: Loại trừ native command (chẳng hạn `java/java.exe`) khỏi image.
- `--vm <client|server|minimal|all>`: Chọn HotSpot VM trong output image. Mặc định là `all`.

Dưới đây là một vài ví dụ về cách bạn có thể dùng những plugin này với lệnh `jlink`:
```
# Create a runtime image with maximum compression,
# exclude specific files, and strip debug information
jlink --module-path $JAVA_HOME/jmods \
      --add-modules java.base \
      --compress zip-9 \
      --exclude-files "**.java,glob:/java.base/lib/client/**" \
      --strip-debug \
      --output custom-runtime-image

# Create a runtime image that includes only the
# specified locales and uses the server VM
jlink --module-path $JAVA_HOME/jmods \
      --add-modules java.base \
      --include-locales en,ja \
      --vm server \
      --output custom-runtime-image
```

### Tối ưu runtime image {#optimizing-runtime-images}
Ngoài việc tạo runtime image tối giản, `jlink` còn cung cấp các option để tối ưu thêm runtime được tạo. Những tối ưu này có thể giúp giảm kích thước runtime image và cải thiện hiệu năng của nó.

Một tối ưu quan trọng là compression. Mặc định, `jlink` không nén runtime image được tạo. Tuy nhiên, chúng ta có thể bật compression bằng option `--compress` theo sau là mức compression. Mức compression có thể được đặt là 0 (không nén), 1 (constant string sharing) hoặc 2 (ZIP compression). Ví dụ:
```
jlink --module-path <modulepath> 
      --add-modules <modules> \
      --compress 2 \
      --output <path>
```

Dùng `--compress 2` sẽ áp dụng ZIP compression cho runtime image được tạo, giúp giảm đáng kể kích thước của nó.

Một tối ưu khác là loại bỏ debug information khỏi runtime image. Debug information hữu ích trong quá trình phát triển nhưng không cần thiết cho việc triển khai production. Chúng ta có thể loại bỏ debug information bằng option `--strip-debug`:
```
jlink --module-path <modulepath> 
      --add-modules <modules> \
      --strip-debug \
      --output <path>
```

Bằng cách này, chúng ta có thể giảm thêm kích thước của runtime image.


## Migration một application {#migrating-an-application}
Migration một application hiện có sang dùng module có thể là một task đầy thách thức. Điều đó là khả thi, nhưng đòi hỏi lập kế hoạch và thực hiện cẩn thận.

Trước khi bắt tay vào quá trình migration, điều quan trọng là hiểu cách các package và library trong application hiện tại được cấu trúc. Việc này bao gồm phân tích codebase và nhận diện các dependency giữa những phần khác nhau của application.

Một cách để có hiểu biết sâu sắc về cấu trúc application là dùng `jdeps`. Khi chạy `jdeps` trên các JAR file hoặc class file của application, chúng ta có thể sinh một báo cáo dependency cung cấp thông tin giá trị về mối quan hệ giữa các package và class.

Đây là một ví dụ chạy `jdeps` trên JAR file của application:
```
jdeps -s -recursive application.jar
```

Option `-s` sinh output tóm tắt, và option `-recursive` cũng phân tích tất cả JAR file phụ thuộc.

Output của jdeps sẽ cho chúng ta cái nhìn tổng quan về các package và dependency của chúng. Nó sẽ làm nổi bật mọi dependency vào JDK internal API, điều quan trọng cần lưu ý vì những API này có thể không truy cập được trong các phiên bản Java tương lai.

Nếu bạn muốn chi tiết hơn, bạn có thể dùng option `-verbose`:
```
jdeps -verbose application.jar
```

Output sẽ hiển thị các dependency giữa package và class, cũng như dependency vào các library bên ngoài.

Điều quan trọng là phải nhận diện và giải quyết mọi circular dependency hoặc dependency không cần thiết ở giai đoạn này. Circular dependency có thể gây ra vấn đề khi module hóa application, vì module không thể có cyclic dependency. Những dependency không cần thiết có thể làm application phình to và khiến việc module hóa hiệu quả trở nên khó khăn hơn.

Giờ chúng ta đã có bản đồ dependency của application, đã đến lúc bắt đầu lập kế hoạch migration. Một chiến lược phổ biến là chia project lớn của chúng ta thành những module nhỏ hơn, dễ quản lý hơn. Quá trình này bao gồm nhận diện các ranh giới logic bên trong application và tách code thành những module riêng biệt dựa trên chức năng và dependency.

JPMS cung cấp cho chúng ta một vài công cụ để giảm nhẹ quá trình chuyển đổi này: unnamed module và automatic module.

Giả sử chúng ta có một application nguyên khối lớn tên `BigApp`. Chúng ta có thể bắt đầu bằng cách chạy nó theo cách truyền thống trên classpath:

```
java -cp BigApp.jar:lib/* com.example.MainClass
```

Lệnh này đặt `BigApp` và tất cả dependency của nó vào **unnamed module**. Đây là cách các application trước JPMS chạy, mọi thứ trên classpath đều trở thành một phần của unnamed module.

Như một bước đầu tiên hướng tới module hóa, chúng ta có thể chuyển `BigApp` sang module path mà không định nghĩa file `module-info.java`:

```
java --module-path BigApp.jar 
     --add-modules ALL-MODULE-PATH
     com.example.MainClass
```

Điều này biến `BigApp` thành một **automatic module**. Nó chưa phải là một module JPMS đúng nghĩa, nhưng đó là một khởi đầu, giờ nó đã có tên module (được suy ra từ tên JAR) và có thể require những module khác.

Với các third-party library chưa được module hóa, chúng ta có thể dùng automatic module. Giả sử chúng ta đang dùng một library tên `CoolLib`. Chúng ta có thể đặt nó trên module path cùng với application của mình:

```
java --module-path BigApp.jar:CoolLib.jar 
     --add-modules ALL-MODULE-PATH
     com.example.MainClass
```

Giờ cả `BigApp` và `CoolLib` đều trở thành automatic module. Module system suy ra tên của chúng từ tên file JAR, và chúng export tất cả package của mình. Nhưng hãy nhớ, đây chỉ là những giải pháp tạm thời. Mục tiêu cuối cùng của chúng ta là có những module explicit đúng nghĩa với file `module-info.java` cho mọi thứ.

Khi chia project thành các module, điều quan trọng là phải xem xét dependency giữa các module. Hãy nhắm đến việc giảm thiểu coupling giữa các module và thúc đẩy loose coupling với những interface và API được định nghĩa rõ ràng.

Dưới đây là một số chiến lược để chia một project lớn thành các module một cách hợp lý:

1. **Chia theo package:** Một cách tiếp cận là tạo module dựa trên cấu trúc package hiện có. Mỗi package hoặc một nhóm các package liên quan có thể được chuyển thành một module riêng. Điều này giúp duy trì sự tách biệt rõ ràng về mối quan tâm (separation of concerns) và encapsulation.

2. **Kiến trúc phân lớp:** Nếu application theo kiến trúc phân lớp (presentation layer, business logic layer, data access layer), mỗi layer có thể được tách thành module riêng của nó. Điều này cho phép modularity tốt hơn và bảo trì từng layer độc lập dễ dàng hơn.

3. **Chia theo feature:** Một cách tiếp cận khác là chia application dựa trên các feature hoặc vùng chức năng của nó. Mỗi feature hoặc chức năng chính có thể được đóng gói trong module riêng, thúc đẩy khả năng tái sử dụng và bảo trì.

4. **Chia theo dependency:** Phân tích dependency giữa những phần khác nhau của application có thể giúp nhận diện ranh giới module tự nhiên. Những thành phần coupled chặt chẽ có thể được nhóm lại thành một module, trong khi những thành phần coupled lỏng lẻo có thể được tách thành các module riêng biệt.

Nhưng bạn có thể đang thắc mắc chúng ta có thể dùng những chiến lược nào cho việc migration nói chung. Dưới đây là một vài cách tiếp cận:

1. **Migration tăng dần:** Theo cách này, migration được thực hiện dần dần, mỗi lần một module. Bắt đầu bằng việc nhận diện một module phù hợp để migration trước, thường là module có ít dependency nhất vào những phần khác của application. Sau khi module đó được migration thành công, chuyển sang module tiếp theo, và cứ thế.

2. **Migration bottom-up:** Chiến lược này bắt đầu migration từ những module cấp thấp nhất và dần dần đi lên theo hệ thống phân cấp dependency. Bắt đầu bằng việc module hóa những module không có dependency vào module khác, sau đó tiếp tục với những module phụ thuộc vào các module đã được module hóa.

3. **Migration top-down:** Ngược với cách tiếp cận bottom-up, migration top-down bắt đầu với những module cấp cao và đi xuống theo chuỗi dependency. Chiến lược này hữu ích khi các module cấp cao có sự tách biệt rõ ràng về mối quan tâm và có thể dễ dàng được module hóa.

4. **Phát triển song song:** Nếu thời gian và nguồn lực cho phép, có thể áp dụng phát triển song song. Theo cách này, một branch hoặc codebase riêng được tạo cho phiên bản đã module hóa của application, trong khi phiên bản chưa module hóa hiện tại vẫn tiếp tục được bảo trì. Quá trình phát triển có thể diễn ra đồng thời trên cả hai phiên bản, dần dần chuyển các module sang branch đã module hóa.

Ví dụ, chúng ta có thể bắt đầu module hóa một phần của application bằng cách tiếp cận bottom-up:

```java
module com.myapp.core {
    requires java.base;
    requires com.coollib;  // Đây là automatic module của chúng ta
    exports com.myapp.core.api;
}
```

File `module-info.java` này định nghĩa một module mới `com.myapp.core`. Chúng ta bắt đầu với một core module có lẽ có ít dependency hơn, đặc trưng của cách tiếp cận bottom-up. Nó requires module `java.base` (vốn là implicit nhưng ở đây chúng ta viết tường minh) và `CoolLib`, một automatic module. Nó cũng exports package `com.myapp.core.api` để các module khác sử dụng.

Khi tạo thêm nhiều module, chúng ta sẽ cần suy nghĩ cẩn thận về ranh giới module của mình.

Một điều quan trọng cần ghi nhớ là trong giai đoạn này, chúng ta có thể cần mở nhiều hơn mong muốn. Ví dụ:

```java
open module com.myapp.core {
    requires java.base;
    requires com.coollib;
    exports com.myapp.core.api;
}
```

Bằng cách biến module này thành open module, chúng ta cho phép deep reflection vào tất cả package của nó. Điều này không lý tưởng về mặt bảo mật, nhưng có thể cần thiết trong quá trình migration để mọi thứ tiếp tục hoạt động. Khi tiến xa hơn trong migration, chúng ta sẽ muốn siết chặt những quyền này, chỉ export và open những gì cần thiết.

Hãy nhớ, migration là một quá trình. Việc dùng unnamed module và automatic module như những bước đệm là chuyện bình thường. Điều quan trọng là có một kế hoạch migration rõ ràng và tiến đều đặn tới một hệ thống được module hóa hoàn toàn. Chia nhỏ quá trình migration thành những task nhỏ hơn, dễ quản lý giúp theo dõi tiến độ và nhận diện mọi thách thức hay trở ngại trên đường đi.

## Các điểm chính {#key-points}
- Module trong Java là một tập hợp code và dữ liệu có tên, tự mô tả chính nó. Nó được định nghĩa trong file `module-info.java`.

- Các thành phần chính của một module declaration gồm:
  - `module`: Khai báo tên module
  - `requires`: Chỉ định các dependency của module
  - `exports`: Cho phép các module khác truy cập package
  - `provides`: Khai báo các service implementation
  - `uses`: Cho biết một module sử dụng một service

- Có ba loại module:
  1. Named module: Được định nghĩa tường minh bằng một file `module-info.java`
  2. Automatic module: Được tạo từ các file JAR được đặt trên module path
  3. Unnamed module: Chứa tất cả class trên classpath

- Những lợi ích chính của JPMS bao gồm encapsulation được cải thiện, dependency rõ ràng hơn, hiệu năng tốt hơn và bảo mật được tăng cường.

- Keyword `exports` kiểm soát những package nào có thể được truy cập bởi các module khác. Bạn cũng có thể dùng `exports...to` để giới hạn quyền truy cập cho những module cụ thể.

- Keyword `requires` khai báo các dependency của module. Dùng `requires transitive` để các dependency của một module trở nên khả dụng cho những module phụ thuộc vào nó.

- Keyword `opens` cho phép truy cập reflection vào một package tại runtime.

- Service trong JPMS gồm:
  1. Service Provider Interface (SPI): Định nghĩa contract của service
  2. Service Provider: Triển khai SPI
  3. Service Consumer: Sử dụng service

- Mệnh đề `provides...with` trong module declaration chỉ định rằng một module cung cấp một service implementation.

- Mệnh đề `uses` cho biết một module tiêu thụ một service.

- `ServiceLoader` được dùng để khám phá và load các service implementation tại runtime.

- Các module built-in của Java bắt đầu bằng `java` (core SE Platform) hoặc `jdk` (các API bổ sung riêng của JDK).

- Khi thiết kế multi-module application, hãy cân nhắc separation of concerns, encapsulation, dependency ổn định, khả năng tái sử dụng và kích thước module phù hợp.

- Compile module bằng `javac` với option `--module-path`. Chạy modular application bằng `java` với các option `--module-path` và `-m`.

- Dùng lệnh `jar` để đóng gói module thành các modular JAR file.

- Giải quyết xung đột giữa các module bằng cách quản lý version, tránh split package, đảm bảo tên package duy nhất giữa các module và phá vỡ các cyclic dependency.

- Lệnh `java` với option `--describe-module` cung cấp thông tin chi tiết về một module cụ thể, bao gồm exports, requirements và services.

- Option `--list-modules` liệt kê tất cả module khả dụng trong Java runtime và các custom module.

- Option `--show-module-resolution` giúp debug các dependency module phức tạp bằng cách hiển thị cách mỗi module được resolve.

- Lệnh `jar` có thể được dùng để kiểm tra module mà không cần chạy chúng, bằng option `--describe-module`.

- `jdeps` là một tool để phân tích và trực quan hóa dependency ở cả cấp module lẫn cấp class.

- Đây là cú pháp cơ bản của nó: `jdeps [options] path`. Dưới đây là một số option quan trọng nhất:
    - Option `--dot-output` tạo file DOT để trực quan hóa dependency graph.
    - Cờ `--jdk-internals` giúp xác định việc sử dụng các internal JDK API.
    - Option `--recursive` cung cấp phân tích transitive dependency.

- File JMOD được thiết kế cho Java Platform Module System (JPMS) và có phần mở rộng `.jmod`.

- File JMOD có thể chứa compiled class, resource, native library và module descriptor.

- `jmod` có một số mode: create, extract, describe, list và hash.

- Best practice bao gồm dùng tên mô tả rõ ràng, bao gồm cả `module-info.java`, và tổ chức nội dung module đúng cách.

- `jlink` tạo custom runtime image chỉ chứa những module cần thiết.

- Đây là cú pháp cơ bản của `jlink`: `jlink [options] --module-path <modulepath> --add-modules <modules>`

- Plugin có thể mở rộng chức năng của `jlink` để có thêm các tối ưu hóa hoặc tùy chỉnh.

- Các option như `--compress`, `--strip-debug`, `--no-header-files` và `--no-man-pages` giúp tối ưu runtime image.

- Để migrate một application sang dùng module:
    - Dùng `jdeps` để phân tích cấu trúc và dependency hiện có của application trước khi migrate.

    - Các chiến lược chia project thành module: dựa trên package, kiến trúc phân lớp (layered architecture), dựa trên feature và dựa trên dependency.

    - Các hướng tiếp cận migration: incremental, bottom-up, top-down và parallel development.

    - Unnamed module và automatic module có thể được dùng như giải pháp tạm thời trong quá trình migration.

    - Cân nhắc dùng open module trong quá trình migration để cho phép reflection, nhưng hãy cố thắt chặt quyền hạn dần khi migration tiến triển.

    - Migration là cả một quá trình; việc dùng unnamed và automatic module như bước đệm để tiến tới modularization hoàn chỉnh là điều bình thường.
